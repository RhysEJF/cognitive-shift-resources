# Voyager: An Open-Ended Embodied Agent with Large Language Models

**Authors:** Guanzhi Wang, Yuqi Xie, Yunfan Jiang, Ajay Mandlekar, Chaowei Xiao, Yuke Zhu, Linxi "Jim" Fan, Anima Anandkumar (NVIDIA / Caltech / UT Austin / Stanford / UW Madison)
**Published:** May 2023 (v2: Oct 2023) · [Source](https://arxiv.org/abs/2305.16291)
**Lens:** `generic` · **Digested:** 2026-05-20

## TLDR

Voyager is the first LLM-powered embodied agent that *lifelong-learns* inside Minecraft without any gradient updates. It wraps a frozen GPT-4 with three orchestrated components: (1) an **automatic curriculum** that prompts GPT-4 to propose the next task given the agent's current world state and history of completed/failed tasks; (2) a **skill library** in which every successfully completed task is stored as a JavaScript function (Mineflayer API) and indexed by the embedding of its natural-language description, so future tasks can retrieve the top-5 most relevant skills as in-context examples; and (3) an **iterative prompting mechanism** that runs the generated code against the live game, feeds environment messages ("I need 2 more sticks"), execution errors, and a separate GPT-4 *critic* agent's self-verification back into the prompt for up to 4 refinement rounds, after which it either commits the program to the library or asks the curriculum for a new task. Against ReAct, Reflexion, and AutoGPT inside MineDojo (160 prompting iterations, 3 trials each), Voyager obtains **3.3× more unique items** (63 vs ~19), unlocks the wooden/stone/iron tech tree **15.3× / 8.5× / 6.4× faster**, traverses **2.3× longer distances**, and is **the only method that ever crafts a diamond tool** (1/3 trials in 102 iterations; all baselines: 0/3). In a separate zero-shot test, Voyager's learned skill library transferred cleanly to a fresh world — solving all four held-out tasks (Diamond Pickaxe, Golden Sword, Lava Bucket, Compass) in 18-21 iterations while ReAct/Reflexion/AutoGPT solved zero. Ablations show **self-verification is the single most important feedback channel** (removing it drops item discovery by 73%) and **GPT-4 → GPT-3.5 collapses performance by 5.7×**, so the result depends heavily on the underlying coding model.

## Key Takeaway

Voyager's core thesis is that a **separate, structured procedural memory** (executable code indexed by description embeddings) plus a **curiosity-driven curriculum** plus **closed-loop self-verification** lets you turn a frozen, gradient-free LLM into a continually-improving agent — *without* the catastrophic-forgetting and reward-engineering problems that have historically blocked open-ended RL agents in Minecraft. The three components are co-essential: ablating the skill library causes Voyager to plateau in late training (because new skills can't be built on old ones), ablating the curriculum drops item discovery 93% (because tasks attempted out-of-order are too hard), and ablating self-verification drops it 73% (because the agent can't tell when to move on). The paper effectively reframes "lifelong learning" from a *parameter*-update problem (regularization, replay buffers, EWC) to a *retrieval-augmented program-synthesis* problem — which is significant because it means lifelong learning becomes commoditized the moment your code-LLM is good enough.

## Implications

- **Procedural memory ≠ conversational memory.** Most LLM-agent memory work in 2023-2026 (Reflexion, Generative Agents, MemGPT, A-MEM, MIRIX) stores experiences as *text* — episodic traces, summaries, reflections. Voyager stores them as *code*. The distinction matters: code is directly *executable* on retrieval (no re-interpretation), *compositional* (functions call other functions), and *verifiable* (the interpreter is ground truth). This is a different architectural commitment than the dominant text-memory line, and one that has been underexploited in the subsequent agent-memory literature.

- **Description-embedded code-as-key is a load-bearing detail.** The skill library uses GPT-3.5-generated natural-language descriptions as the *key* (embedded with `text-embedding-ada-002`) and the code as the *value*. At retrieval time, a fresh GPT-3.5 query plus environment context is embedded against those keys, returning top-5 relevant skills. This decouples *what the code does* (description) from *how it does it* (implementation) — and means the retrieval system never has to embed code directly.

- **The curriculum is a novelty-search proxy.** Section 2.1 frames the automatic curriculum as "an in-context form of novelty search" — but operationally it's just a prompt instruction ("My ultimate goal is to discover as many diverse things as possible") plus a list of completed and failed tasks. There is no explicit diversity metric, no MAP-Elites grid, no behavioral characterization. GPT-4 alone, given the prompt constraints in Sec A.3.4, produces a diverse curriculum. This is a striking demonstration that *coherent open-ended exploration* can emerge from prompt-level scaffolding alone if the underlying model is strong enough.

- **The skill library is a plug-and-play asset.** Table 2 shows that AutoGPT *equipped with Voyager's learned skill library* improves dramatically (from 0/3 on all held-out tasks to 1/3 or 2/3 on three of four). This suggests skill libraries built by one agent could be exported, shared, or pretrained — opening an "agent app store" pattern that the subsequent 2024-2025 literature has only partially explored.

- **Cost economics are real.** The authors flag GPT-4 as 15× more expensive than GPT-3.5 and admit the result requires GPT-4-level code generation. The 160-iteration runs and 3-trial averaging are non-trivial budget commitments. Practically, this paper's recipe became cheap to replicate only after GPT-4o-mini / Claude Haiku / Llama-3-coder reached parity (2024-2025).

- **Hallucination is the unaddressed failure mode.** Section 4 admits the curriculum sometimes proposes nonexistent items ("copper sword"), and the code agent sometimes uses cobblestone as fuel (invalid). The system has no grounded knowledge base of Minecraft mechanics — it relies on GPT-4's pretraining knowledge plus the wiki-knowledge-base self-Q&A. Subsequent embodied-agent work (e.g., the DEPS line) tightens this by injecting an explicit recipe/mechanic database.

## How to Apply It (method)

To implement a Voyager-style lifelong learning agent in a new domain:

1. **Define a code-action interface.** Pick a programming environment where the LLM can write a function whose execution corresponds to taking an extended action in the world. Voyager uses Mineflayer JS APIs on top of MineDojo. For robotics it would be the controller API; for web agents, browser-automation primitives; for terminal agents, shell commands wrapped in a function.

2. **Stand up three GPT-4 agents with disjoint roles:**
   - *Curriculum agent* — system prompt instructs GPT-4 to propose the next task given (current inventory/state, list of completed tasks, list of failed tasks, optional self-Q&A context from a domain wiki). Temperature ≈ 0.1 for slight task diversity.
   - *Action agent* — system prompt instructs GPT-4 to write a JS (or Python) function solving the proposed task, given (control-primitive API docs, top-5 retrieved skills as in-context examples, last round's code + environment feedback + execution errors + critique). Temperature 0. Use chain-of-thought.
   - *Critic agent* — system prompt instructs GPT-4 to inspect (task description, post-execution agent state) and return success: True/False plus a natural-language critique if False.

3. **Build the skill library as a vector DB.** Each successful function is stored with: function code (value), function description (key, generated by a cheaper model like GPT-3.5), embedding of the description (via `text-embedding-ada-002` or any other text embedder). On retrieval, embed `current_task + GPT-3.5-suggested-approach + environment-feedback` and return top-5 by cosine similarity.

4. **Run the inner loop.** For each curriculum-proposed task: retrieve top-5 skills → action agent writes code → execute in environment → collect environment feedback (e.g., `bot.chat()` messages) and execution errors → critic verifies → if success, commit code to skill library and ask curriculum for next task; if fail, feed feedback/errors/critique into action agent for round 2. Cap at 4 rounds; if still failing, mark task as failed and move on.

5. **Warm-up the curriculum prompt.** Voyager uses a schedule (Table A.1) that only feeds *core inventory* + nearby blocks + equipment + position in the first 5 tasks; nearby entities at 5 completed tasks; full inventory at 7; biome and recent blocks at 10; health/hunger/time/wiki-context at 15. This is non-obvious — without it, the agent gets distracted by irrelevant state early on.

6. **Use the right model.** GPT-4-0314 for code (the 5.7× advantage over GPT-3.5 is large enough to matter operationally); cheaper GPT-3.5-turbo-0301 for the curriculum's self-Q&A side-tasks; `text-embedding-ada-002` for the skill index. As of 2026, equivalent open models (Claude Sonnet, GPT-4o, Llama-3.1-405B-instruct) should match or exceed.

The cycle is what produces compounding lifelong learning. Also notable: the code shown (`async function combatZombie(bot) { ... }`) is itself a successfully-learned Voyager skill, not a hand-written example — which is the implicit claim of the paper.

## What Experts Overlook

Reading Voyager in 2026, with three years of subsequent agent literature in the background, three details get understated by both the original authors and the citing community:

1. **The critic agent is doing more work than "self-verification" suggests.** Section 2.3 frames the critic as a binary "did the task succeed?" check. But the critic also produces a natural-language *critique* on failure ("Find and mine an amethyst shard underground" when the agent attempted to craft a spyglass without one). That critique re-enters the action agent's prompt in the next round. This is not just verification — it's *planning correction* via a separate cognitive role. The Reflexion paper (which Voyager cites and outperforms) does something similar with self-reflection, but Voyager's two-agent split (action vs critic) is cleaner, because the critic has no prior commitment to defending the last code attempt. The subsequent multi-agent debate / actor-critic literature traces partly to this design.

2. **The "warm-up schedule" is doing more work than it gets credit for.** Table A.1 shows the curriculum doesn't see full inventory until 7 tasks are complete, biome until 10, health/hunger/time until 15. The paper presents this in one paragraph as a tuning detail. But this is effectively a *prompted curriculum over the agent's own input space* — limiting GPT-4's information access to keep early proposals manageable. Without it, GPT-4 would presumably propose tasks tuned to hunger/biome state before the agent has the skills to act on them. This is an underdocumented technique with broad applicability to any LLM-agent system: stage the information density of the prompt to match the agent's competence level.

3. **The 1/3 diamond success rate is fragile.** Table 1 shows Voyager unlocks diamond tools in 1 of 3 trials (the only baseline to ever do so). The 2 failed trials are not discussed in the body — what went wrong? The 4-round cap on code refinement (Sec 2.3) means the agent gives up on a task after 4 attempts and moves on. For diamond mining, this likely means the agent never finds a deep enough cave, or self-verification mistakes "have iron pickaxe" for "have used iron pickaxe in the right biome." The headline 15.3× speedup on the wooden level is robust (3/3); the diamond claim is much more wobbly. Reading the paper carefully, the strong result is *steady tech-tree progression to iron*, not *reliable diamond*.

A fourth, more meta observation: Voyager establishes a pattern — frozen LLM + structured external memory + closed feedback loop — that the 2024-2026 agent-memory literature has spent enormous effort *re-discovering* in conversational rather than procedural form. Papers on episodic memory, working memory, hierarchical memory for LLM agents often cite Voyager but rarely engage with its central architectural commitment: storing memory as *executable artifacts* rather than as text to be re-interpreted. The procedural-memory line is comparatively underdeveloped.

**Curriculum agent system prompt (Sec A.3.4):**

> "You are a helpful assistant that tells me the next immediate task to do in Minecraft. My ultimate goal is to discover as many diverse things as possible, accomplish as many diverse tasks as possible and become the best Minecraft player in the world. […]
>
> You must follow the following criteria:
> 1) You should act as a mentor and guide me to the next task based on my current learning progress.
> 2) Please be very specific about what resources I need to collect, what I need to craft, or what mobs I need to kill.
> 3) The next task should follow a concise format, such as 'Mine [quantity] [block]', 'Craft [quantity] [item]', 'Smelt [quantity] [item]', 'Kill [quantity] [mob]', 'Cook [quantity] [food]', 'Equip [item]' etc.
> 4) The next task should not be too hard since I may not have the necessary resources or have learned enough skills to complete it yet.
> 5) The next task should be novel and interesting. I should look for rare resources, upgrade my equipment and tools using better materials, and discover new things. I should not be doing the same thing over and over again.
> 6) I may sometimes need to repeat some tasks if I need to collect more resources to complete more difficult tasks. Only repeat tasks if necessary."

**Action-agent code-generation guideline (Sec 2.2):**

> "Your function will be reused for building more complex functions. Therefore, you should make it generic and reusable."

**Critic agent (informally, paraphrased from Sec 2.3):** Given (task description, post-execution agent state including inventory, equipment, nearby blocks/entities, biome, position) — return JSON `{success: true/false, critique: <natural language hint if false>}`. Voyager treats this critic as more comprehensive than Reflexion's self-reflection precisely because it both checks success *and* generates next-step guidance.

**Skill-retrieval query construction:** Take the curriculum-proposed task, ask GPT-3.5 "How to [task] in Minecraft?", concatenate the GPT-3.5 answer with current environment feedback, embed the concatenation with `text-embedding-ada-002`, and retrieve top-5 by cosine similarity against stored skill descriptions.
