# EverMemOS: A Self-Organizing Memory Operating System for Structured Long-Horizon Reasoning

**Authors:** Chuanrui Hu, Xingze Gao, Zuyi Zhou, Dannong Xu, Yi Bai, Xintong Li, Hui Zhang, Tong Li, Chong Zhang, Lidong Bing, Yafeng Deng (EverMind / Shanda Group)
**Published:** 2026-01 · [Source](https://arxiv.org/abs/2601.02163)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

EverMemOS is a memory operating system for LLM agents that replaces "flat record + retrieve" with an explicit **three-phase lifecycle** modelled on biological engrams:

1. **Episodic Trace Formation** — a sliding-window Semantic Boundary Detector segments raw dialogue, rewrites each segment into a coreference-resolved third-person Episode (E), and extracts Atomic Facts (F) + time-bounded Foresight (P, with `[t_start, t_end]` intervals) plus metadata (M). The bundle is a **MemCell**.
2. **Semantic Consolidation** — new MemCells are embedded and incrementally clustered into thematic **MemScenes**; scene summaries are then used to update a compact User Profile with explicit time-varying facts and implicit traits, with conflict tracking.
3. **Reconstructive Recollection** — at query time, MemScenes are scored via dense+BM25 RRF fusion over their Atomic Facts, episodes are re-ranked, expired Foresight is filtered by current time, and an **LLM sufficiency checker** decides whether to trigger a query-rewrite loop (fires on 31% of LoCoMo questions).

On LoCoMo (GPT-4.1-mini), overall accuracy hits **93.05%**, beating Zep by **+9.2%** with comparable token cost; multi-hop jumps **+12.1%** and temporal **+16.1%**. On LongMemEval, **83.0% overall (+6.7% vs MemOS)**, with **+20.6% on knowledge-update**. PersonaMem-v2 shows the User Profile adds **+9.3 points** over episodes-only (53.25 vs 43.93). Code is open-source at github.com/EverMind-AI/EverMemOS.

## Key Takeaway

**The biggest unlock in agent memory is write-time consolidation, not query-time retrieval.** EverMemOS's ablation makes this concrete: removing MemScenes (the consolidation layer, while keeping MemCells) drops LoCoMo accuracy from 93.05 → 89.16, and removing MemCells (falling back to raw dialogue retrieval) drops it further to 81.82. The whole architecture is anchored on a small composable atomic unit — `c = (E, F, P, M)` — where each field has a distinct retrieval role (E = semantic anchor for reranking, F = high-precision fact match, P = time-valid forward inference, M = provenance), and a higher-level scene aggregator that creates the "thematic context bundle" the answering LLM actually needs. The architectural lesson: design memory so that **the hard reasoning has already happened by the time a query arrives**, and so that the retrieval unit matches the granularity of the question (scenes for multi-hop, atomic facts for single-hop precision, foresight for temporal-validity questions).

## Implications

**ENGRAM-tagged findings for memory-architecture work:**

- **[E — Encode]** Write-time LLM distillation pays for itself. EverMemOS spends ~9.4M tokens building memory for 1,540 LoCoMo questions (~6.1k/question on the add path) and recovers it via better answer accuracy with smaller retrieval contexts. **Cost split:** Phase I (memory build) ≈ Phase III (retrieve+answer), so build cost is *not* negligible — it's roughly half the bill. Plan capacity accordingly.

- **[E — Encode]** The MemCell tuple `(E, F, P, M)` is a transferable design pattern: a single atomic write unit that simultaneously serves narrative retrieval (E), precision matching (F), temporal/forward reasoning (P), and provenance (M). Worth borrowing as the v2 schema target for Flow OS atomic memories.

- **[E — Encode]** **Foresight with validity intervals is the most under-imitated piece.** Tagging forward-looking inferences (e.g. "[3 days] need to prepare ID" vs "[long-term] improve photography") with explicit `[t_start, t_end]` and filtering at retrieval by `t_now ∈ interval` is what makes the IPA-vs-antibiotics example in Figure 2 work — and what almost no other system in this competitive set does.

- **[N — Network]** Memory shape decisions matter independently of retrieval quality. MemScenes are a **graph-of-clusters** sitting above flat MemCells, not a vector store, not a knowledge graph, not a doc tree. The structural choice — incremental online clustering with a similarity threshold τ (0.70 on LoCoMo, 0.50 on LongMemEval) and a per-dataset `max_time_gap` (7 / 30 days) — is what enables scene-level aggregation. Dataset-specific τ is a quiet warning: there is no universal clustering temperature.

- **[G — Ground]** Provenance is preserved through the entire lifecycle: M (metadata with timestamps + source pointers) survives consolidation; explicit-fact profile updates carry recency annotations and conflict tracking (Appendix B.3). The waist-circumference example shows time-varying explicit facts maintained as a sequence with deltas (104 → 95 cm, Δ = −9), not as overwrites. **Cross-dimensional cost:** consolidation that smooths conflicts away (like simple "newest wins" upserts) loses the provenance G needs.

- **[R — Retrieve]** Hybrid dense+BM25 with **Reciprocal Rank Fusion (RRF)** over Atomic Facts (not over Episodes) is the retrieval primitive. Reranking happens on Episodes (with Qwen3-Reranker-4B), so the score-and-rerank pipeline operates on different granularities for different stages — a non-obvious choice that exploits the (F)-for-matching, (E)-for-context split.

- **[R — Retrieve]** The two-stage retrieval (Scene → Episode) is a generalisable pattern: score at the cluster level, then drill into constituents. Hits saturate around N=10 scenes / K=10 episodes; brute-force expansion of either burns tokens without adding accuracy (Figure 5).

- **[R — Retrieve]** **Agentic sufficiency check + query rewrite** triggers a second retrieval round on **31% of LoCoMo questions** (GPT-4.1-mini). This is a deliberate "AI as memory maintainer" pattern — the system *introspects* on whether it has enough, then composes targeted complementary queries by strategy (Pivot, Temporal Calculation, Concept Expansion, Constraint Relaxation). Cost is real but bounded by the binary check.

- **[A — Aggregate]** Online incremental clustering (vs offline batch) is the consolidation default — every new MemCell triggers a similarity check against existing MemScene centroids; assimilate if above τ, otherwise instantiate a new scene. This means MemScenes evolve in real time without a separate consolidation pass.

- **[A — Aggregate]** **Scene-driven profile evolution** is a clean pattern: don't extract profile fields from individual turns; extract them from scene summaries. This filters noise twice and tends to surface stable traits vs transient mentions. Likely the right design for any "user model" component.

- **[A — Aggregate]** Surprising empirical finding: **semantic segmentation beats ground-truth session boundaries** (Table 3 — EverMemOS 89.16/89.78 vs Session-Oracle 87.66/80.63 on LoCoMo with two answer backbones). Sessions defined by the data collector are not always the right retrieval unit; topic boundaries are. This validates write-time semantic segmentation as a primitive, not a hack.

- **[M — Maintain]** Foresight filtering at recall time (`t_now ∈ [t_start, t_end]` → discard expired) is a lightweight maintenance mechanism that runs at query time rather than via a separate garbage-collection pass. Elegant — no background process needed.

- **[Cross-dim E × G × A]** The "Lost-in-the-Middle" reduction and conflict-resolution capability both come from consolidation rather than from retrieval. This suggests that for Flow OS — where context drift, contradiction smoothing, and "AI promoting its own inferences to facts" are live concerns — investment in a write-time consolidation phase is higher-leverage than retrieval tuning.

## How to Apply It (method)

If borrowing the EverMemOS architecture for a real system, the minimal viable pipeline is:

### Phase I — Episodic Trace Formation (write path)

1. **Sliding-window topic-boundary detector.** LLM-prompted: feed K recent turns, ask "is there a topic shift here?" Output: boundary location, used to encapsulate the preceding turns as a raw episode history. Boundary detection is imperfect but robust downstream.
2. **Narrative synthesis.** Rewrite the segment as a third-person past-tense narrative with coreferences resolved. This becomes `E`. Stable anchor for retrieval.
3. **Structural derivation.** Single LLM call over E producing a constrained-schema JSON:
   - `atomic_facts: [string]` — discrete verifiable statements
   - `foresight: [{statement, t_start, t_end}]` — forward-looking inferences with validity windows (distinguish "[7 days] taking antibiotics" from "[long-term] graduation")
4. **Bundle as MemCell** `c = (E, F, P, M)` with M = `{timestamp, source_pointer, session_id, ...}`.

### Phase II — Semantic Consolidation

1. **Embed** the new MemCell (Qwen3-Embedding-4B in the paper).
2. **Nearest-scene lookup.** Find the MemScene whose centroid is closest in embedding space. Optionally enforce a **max time gap** between the new cell and the closest-in-time existing cell in that scene (7 days for short conversations, 30 days for long ones).
3. **Threshold-based assimilation.** If cosine similarity > τ (0.70 / 0.50), assimilate and incrementally update the centroid; otherwise instantiate a new MemScene.
4. **Scene summary refresh.** When a scene grows, regenerate its summary (LLM call over the constituent MemCells).
5. **Profile update.** Use scene summaries (not raw turns) to update a compact User Profile with two fields: `explicit_facts` (time-varying values stored with deltas, plus conflict tracking on inconsistent evidence) and `implicit_traits` (preferences, habits).

### Phase III — Reconstructive Recollection (read path)

1. **Score MemCells** against query via dense+BM25 RRF fusion over their Atomic Facts (`F`).
2. **Score MemScenes** by max constituent-cell relevance; select top N (default N=10).
3. **Episode pooling + re-rank** Episodes from selected scenes (Qwen3-Reranker-4B); select top K (default K=10).
4. **Foresight filtering.** Retain only Foresight whose `[t_start, t_end]` contains `t_now`; drop expired.
5. **Sufficiency check.** LLM verifier with structured JSON output (`is_sufficient`, `reasoning`, `key_information_found`, `missing_information`). On insufficient → generate 2–3 complementary queries with explicit strategy tags (Pivot / Temporal Calculation / Concept Expansion / Constraint Relaxation) and three style variants (keyword combo / natural question / HyDE hypothetical). Triggered ~31% of the time on LoCoMo.
6. **Compose context.** Episodes + (in chat mode) Profile + valid Foresight → downstream answerer.

### Key hyperparameters (transferable defaults)

- Clustering similarity threshold τ: 0.70 for short-horizon, 0.50 for ultra-long
- Max time-gap for scene assimilation: 7 days (short) / 30 days (long)
- Retrieve top-N scenes: 10 (saturates beyond)
- Re-rank top-K episodes: 10 (cost-accuracy sweet spot per Figure 6)
- Sufficiency check + rewrite loop: 1 extra round max, fires ~31% of queries
- Hybrid retrieval: dense (Qwen3-Embedding-4B) + BM25 via RRF

### Where the cost lives

- Memory **build** (Phase I): ~6.1k tokens/question amortized
- Memory **read** (Phase III): ~6.7k tokens/question (with sufficiency loop)
- Phase II: ~0 LLM tokens (clustering is non-LLM compute on embeddings)

Plan for build cost being roughly equal to read cost in steady state — half the bill is write-time intelligence, which is the whole point.

## What Experts Overlook

A memory-architecture researcher skimming this paper might miss several non-obvious operational points:

1. **The 31% rewrite-trigger rate is a tunable knob, not a system constant.** It directly trades accuracy for latency and tokens. EverMemOS reports it but doesn't sweep it — for a production system with a latency budget, this is the first dial to turn.

2. **Per-dataset clustering thresholds (τ = 0.70 vs 0.50) silently signal that the system needs calibration per corpus.** This is a deployment-time gotcha: no universal default works across short-horizon chat and ultra-long-context histories. Worth building an auto-calibration routine.

3. **The Atomic-Facts-for-retrieval / Episodes-for-context split is a non-obvious wiring choice.** Most systems retrieve and rerank the same unit. Splitting them means F can be optimised for *precision* (BM25-friendly, factoid-shaped) while E stays narrative-rich for the answerer. This is the design lesson worth stealing even if you skip the rest.

4. **Memory build cost ≈ memory read cost** in steady state (Table 8: 9.42M vs 10.27M tokens on GPT-4.1-mini). Anyone reading the abstract's "outperforms with comparable tokens" framing will assume the savings are pure win — but the savings are at *read time*; you've moved the bill to *write time*. For workloads with many writes per few reads (e.g., always-on logging agents), the trade may invert.

5. **"Lost-in-the-Middle" is reframed as a consolidation failure, not a context-window failure.** The paper's implicit claim — barely surfaced — is that long-context degradation isn't really about position bias inside the LLM, it's about giving the LLM fragmented evidence when it needs synthesized scenes. This is a substantive reframing that deserves more attention than it gets.

6. **Accuracy can exceed recall at small K** (Table 10: 12–20% of zero-recall questions still answered correctly). This breaks the standard assumption that retrieval recall is a strict upper bound on answerer accuracy. The system survives missed-evidence cases via redundant facts across sessions and inference from semantically related signals. **Caveat for evaluation:** annotated-evidence recall *under-estimates* the system's true usefulness when evidence is distributed.

7. **The biological-engram framing is load-bearing for the design but not for the results.** The paper opens with engram-lifecycle language and reaches for biological consolidation as inspiration, but the actual mechanisms (segment → cluster → score → rewrite) are standard IR/ML primitives. The framing is a useful naming convention — MemCell, MemScene, Reconstructive Recollection — but a sceptical reader can extract the engineering without buying the neuroscience.

8. **No latency numbers.** The paper acknowledges latency cost in Limitations but provides zero milliseconds. For production memory-OS work, the Sufficiency-Check + Rewrite loop is a synchronous LLM call on the critical path — that's a meaningful tail-latency concern that the paper doesn't quantify.

9. **The "Foresight" mechanism is barely evaluated quantitatively.** It shows up in Figure 7 case studies (Beijing → Europe trip suggestion) but not in the main accuracy tables — because LoCoMo and LongMemEval don't have temporal-validity questions. This is a capability advertised but not benchmarked. Treat it as a hypothesis, not a validated claim, until a benchmark with time-validity-sensitive questions exists.

10. **The User Profile is treated as the "stable" layer, but it's updated online from scene summaries.** This means the "stable" representation can drift if the scene-summary generator hallucinates or if conflict-resolution defaults to recency. A monitoring layer for profile drift is implied but not specified.

## Extracted Prompts

The paper publishes two of its core agentic-retrieval prompts in Appendix C.1. Both are reusable:

### Sufficiency Check (Reconstructive Recollection, Phase III)

```
You are an expert in information retrieval evaluation. Assess whether the
retrieved documents provide sufficient information to answer the user's query.

User Query:
{query}
Retrieved Documents:
{retrieved_docs}

### Instructions:

1. **Analyze the Query's Needs**
   - **Entities**: Who/What is being asked about?
   - **Attributes**: What specific details (color, time, location, quantity)?
   - **Time**: Does it ask for a specific time (absolute or relative like "last week")?

2. **Evaluate Document Evidence**
   - Check **Content**: Do the documents mention the entities and attributes?
   - Check **Dates**:
      - Use the `Date` field of each document.
      - For relative time queries (e.g., "last week", "yesterday"), verify if
        document dates fall within that timeframe.
      - If the query asks "When did X happen?", do you have the specific date
        or just a vague mention?

3. **Judgment Logic**
   - **Sufficient**: You can answer the query *completely* and *precisely*
     using ONLY the provided documents.
   - **Insufficient**:
     - The specific entity is not found.
     - The entity is found, but the specific attribute (e.g., "price") is missing.
     - The time reference cannot be resolved (e.g., doc says "yesterday" but
       has no date, or doc date doesn't match query timeframe).
     - Conflicting information without resolution.

### Output Format (strict JSON):
{
   "is_sufficient": true or false,
   "reasoning": "Brief explanation. If insufficient, state WHY (e.g., 'Found X
                but missing date', 'No mention of Y').",
   "key_information_found": ["Fact 1 (Source: Doc 1)", "Fact 2 (Source: Doc 2)"],
   "missing_information": ["Specific gap 1", "Specific gap 2"]
}

Now evaluate:
```

**Reuse note for Flow OS:** this maps cleanly onto a "before-I-answer-do-I-have-enough" gate in any RAG pipeline. The structured `missing_information` field is the bridge to query rewriting; without it, retry attempts are blind.

### Multi-Query Generation (rewrite loop)

```
You are an expert at query reformulation for conversational memory retrieval.

Your goal is to generate 2-3 complementary queries to find the MISSING information.
--------------------------
Original Query:
{original_query}

Key Information Found:
{key_info}

Missing Information:
{missing_info}

Retrieved Documents (Context):
{retrieved_docs}
--------------------------

### Strategy Selection (choose based on why info is missing)
- Pivot / Entity Association: search related entities/categories
- Temporal Calculation: anchor relative times using document dates
- Concept Expansion: synonyms / general-specific variants
- Constraint Relaxation: remove one constraint at a time

### Query Style Requirements (use DIFFERENT styles)
1) Keyword Combo (2-5 words)
2) Natural Question (5-10 words)
3) Hypothetical Statement (HyDE, 5-10 words)

### Output Format (STRICT JSON)
{
  "queries": ["Query 1", "Query 2", "Query 3"],
  "reasoning": "Strategy used for each query (e.g., Q1: Pivot, Q2: Temporal)"
}
```

**Reuse note:** the explicit **strategy tags** (Pivot, Temporal, Concept Expansion, Constraint Relaxation) plus **style mixing** (keyword / natural / HyDE) is the rare prompt that turns "rewrite the query" from vague instruction into an enumerated decision. The combo is borrow-worthy as-is.

The paper additionally describes (but does not publish full text for) prompts for: contextual segmentation, narrative synthesis with coreference resolution, atomic-fact + foresight structured extraction, scene summarization, and profile update with conflict tracking. These are referenced in §3.3–§3.4 and Appendix B.3.
