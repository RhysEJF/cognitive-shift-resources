# SEE: Strategic Exploration and Exploitation for Cohesive In-Context Prompt Optimization

**Authors:** Wendi Cui, Zhuohang Li, Hao Sun, Damien Lopez, Kamalika Das, Bradley Malin, Sricharan Kumar, Jiaxin Zhang
**Published:** 2024-02 · [Source](https://arxiv.org/abs/2402.11347)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

SEE is a prompt-optimization framework from Intuit AI Research and Vanderbilt that treats the instruction AND the few-shot examples as one joint search target — rejecting the prevailing split where prior work optimizes either the instruction (APE, APO, OPRO, EvoPrompt) or the example set (MoP, EASE) but not both at once. The core move is a quad-phased metaheuristic schedule: Phase 0 generates a diverse initial pool of 15 candidates via a Lamarckian reverse-engineering operator (or a Semantic mutator over human seeds); Phase 1 hits each candidate once with a Feedback operator (an LLM examiner + improver, like APO's gradient descent) to drag it to a local minimum; Phase 2 escapes those minima via Fusion operators (EDA + Crossover) that prefer maximally-distant parents under Hamming distance on per-example performance vectors — not cosine on text embeddings; Phase 3 applies a Semantic mutator for the "last mile." Two design choices carry the work: (1) candidate similarity is computed on a binary vector of which dev-set items each prompt gets right (so Hamming distance directly measures "do these two prompts repeat the same mistakes?"), beating cosine on text embeddings by +5.2 (Disambiguation) and +4.6 (Hyperbaton) on BBH; (2) operator-specific stop tolerance — Feedback and Semantic get 1 try, EDA and Crossover get 4 — based on a 100-run-per-operator pre-study showing Feedback converges in step 1 (~34% of its total gains) but Crossover/EDA improve roughly uniformly across the first 4 steps. Across 35 tasks (8 BBH, 3 detection, 24 instruction-induction) SEE beats SOTA by an average of +13.94 accuracy on BBH while using ~58.67% fewer API calls; on instruction-induction it wins 87.5%–100% of head-to-head comparisons. Notably the algorithm dynamically chose few-shot prompts for 20/24 instruction-induction tasks and 4/8 BBH tasks — not zero-shot — confirming that the "joint" framing actually matters. Budget is still ~4,000 API calls and 12 iterations per task; useful takeaway: for any pipeline that re-runs the same evolutionary operator on every iteration, the easiest 2x speedup is to schedule different operators per phase and stop them at different points.

## Key Takeaway

The counter-intuitive move isn't more sophisticated mutation — it's *less* uniform mutation. Every prior metaheuristic prompt optimizer (PromptBreeder, EvoPrompt, AELP) runs the same set of operators on every iteration; SEE shows that the cheapest win is to recognise each operator has a different "personality" (Feedback converges instantly, Crossover takes a few rounds) and give each operator exactly the runway it needs — no more. The deeper lesson: don't measure similarity between candidates by what they *look like* (embedding cosine); measure it by where they *fail* (Hamming distance on per-example performance vectors) — that's what actually tells you whether two prompts are repeating each other's mistakes.

## Implications

- **[ENGRAM — Aggregate] Schedule operators by personality, not by uniform iteration**: Every memory-architecture pipeline that re-runs the same consolidation/extraction step every cycle (e.g. `/learn` running the same extractor template on every session) is leaving 50%+ efficiency on the table. SEE's pre-study (100 runs/operator across 4 BBH tasks) showed Feedback delivers 34% of its lifetime gain in step 1; EDA/Crossover spread theirs across steps 1–4. Action: profile each consolidation operator's "convergence speed" once, then assign it a tolerance budget — don't loop blindly.

- **[ENGRAM — Retrieve] Replace embedding similarity with performance-vector similarity wherever the retrieved item has a measurable downstream score**: SEE got +5.2 on Disambiguation and +4.6 on Hyperbaton by switching from cosine-on-embeddings to Hamming-on-performance-vectors (a binary vector of which dev examples each candidate gets right). For a memory system, the analog is: when ranking past memory chunks for relevance to a new task, score them by whether they previously *worked* on similar tasks rather than by what they textually resemble. Lossy embeddings smooth over the exact failure modes you care about.

- **[ENGRAM — Encode] Joint optimization beats split optimization when the components interact**: Table 4 of the paper shows that bolting two random few-shot examples onto OPRO and EvoPrompt improved performance on only 1/4 and 2/4 BBH tasks respectively — i.e., better instructions paired with naive examples *degrade* results. For an agentic memory system, this means: don't optimize "what to extract" and "how to retrieve" as separate problems. The extraction template and the retrieval ranking should be co-tuned because either one alone is suboptimal.

- **[ENGRAM — Encode + Aggregate] Reverse-engineering the prompt from I/O pairs (the Lamarckian operator) is a strong initialization beat for any synthesis-on-write architecture**: SEE-io-pair lets the LLM induce the instruction from task examples (no human seed); SEE-example uses human-written seeds and mutates them. Both work, but Table 2 shows SEE-example wins on most BBH tasks because human priors are still useful — yet for tasks where humans are bad at articulating the rule (Dyck Languages: SEE-example 46.77 vs SEE-io-pair 8.06), reverse engineering wins by ~6x. Action: for memory-extraction templates, A/B test "extract from examples" (Lamarckian) vs "use the curated template" (Semantic) per domain — neither dominates.

- **[ENGRAM — Ground] Performance-vector encoding gives provenance for free**: The binary "which-examples-this-prompt-got-right" vector is also a literal audit trail of where each candidate succeeded and failed. For a memory architect, this generalises: any synthesized memory that carries an explicit "which source items this was distilled from, and which it correctly captured" vector becomes simultaneously a retrieval signal and a contradiction-detection signal. Two memories with identical content but inverted performance vectors are flagging a real contradiction — not a near-duplicate to merge.

- **[ENGRAM — Maintain] Adaptive stop criteria as the lifecycle primitive**: SEE's "performance gain OR operator tolerance" stop rule is a clean recipe for any maintenance loop. Don't run consolidation until a fixed iteration count; run until no gain *or* the operator's known patience limit, whichever comes first. For a memory system this maps to: don't re-summarize stable patterns every session — let the maintenance pass exit early when no signal change is detected.

- **[ENGRAM — Network] The shape of "memory" here is a pool of 15 ranked candidates, not a single best**: SEE keeps a pool throughout — Phase 0 = 15, Phases 1–3 = 5. The pool *is* the memory. Single-best memory architectures lose the ability to recombine; pool-based architectures (analog: keeping the top-K extraction candidates from each session, not just the chosen one) preserve future fusion potential.

- **[Cost realism] ~4,000 API calls and 12 iterations is the floor — not the ceiling**: SEE is the cheapest baseline tested but still costs ~4k calls per task. Any memory architecture that wants to run SEE-style optimization on its own consolidation prompts must budget accordingly. The realistic deploy pattern is to run SEE once per memory-pipeline template, then freeze; not per session.

## How to Apply It (method)

**Scenario:** You're running the Flow OS memory pipeline and have noticed `/learn`'s pattern-extraction template gives uneven results across session types — it crushes engineering-decision sessions but produces bland summaries on coaching/strategy sessions. You suspect the extraction template's instructions AND its few-shot demonstrations both need tuning, but doing them separately ("optimize the prompt, then optimize the examples") has hit a local optimum. SEE lets you jointly optimize both as one search.

**Steps:**

1. **Frame the extraction template as a joint search target**: Treat the entire `/learn` extraction prompt — instruction text + the few-shot example pairs of "session transcript snippet → extracted memory" — as a single candidate `P = (I, E)`. The optimization will mutate both parts in one search.

2. **Build the three datasets** the paper requires:
   - `D_train` (~50 examples): pairs of (session snippet, human-curated correct memory extraction). Used by the Lamarckian operator only.
   - `D_dev` (~50 examples): held-out pairs used to score every candidate during search.
   - `D_test` (~50 examples): final evaluation, untouched until the end.

3. **Define the scoring function `F`**: For memory extraction, score = exact-match-or-LLM-judge agreement between the candidate template's output and the curated correct extraction. Returns a 0/1 per dev example so you can build performance vectors.

4. **Phase 0 — Initialize a diverse pool of 15 candidates** via the Lamarckian operator (reverse-engineer the template from I/O pairs):

   ```
   I gave a friend an instruction and some input. The friend read the
   instruction and wrote an output for every one of the inputs. Here are
   the input-output pairs:

   ## Example ##
   {session_snippet_1} → {extracted_memory_1}
   {session_snippet_2} → {extracted_memory_2}
   ...

   The instruction was:
   ```

   Run this 15 times with different sampled I/O pairs to get 15 diverse candidate templates. Score each on `D_dev`.

5. **Phase 1 — Apply the Feedback operator once to each of the 15 candidates** (LLM examiner + LLM improver, two API calls per candidate):

   *Examiner prompt:*
   ```
   You are a quick improver. Given an existing prompt and a series of cases
   where it made mistakes. Look through each case carefully and identify
   what is causing the mistakes. Based on these observations, output ways
   to improve the prompts based on the mistakes.

   ## Existing Prompt ##
   {existing template}

   ## Cases where it gets wrong: ##
   {dev examples the candidate failed}

   ways to improve the existing prompt based on observations of the mistakes
   in the cases above are:
   ```

   *Improver prompt:*
   ```
   You are a quick improver. Given an existing prompt and feedback on how it
   should improve. Create an improved version based on the feedback.

   ## Existing Prompt ##
   {existing template}

   ## Feedback ##
   {feedback from examiner}

   ## Improved Prompt ##
   ```

   Stop tolerance = 1 (don't loop — Feedback converges in step 1). Keep the top 5 candidates by `D_dev` score.

6. **Build performance vectors for the surviving 5 candidates**: For each candidate, evaluate on all `D_dev` items and record a binary vector e.g. `[1,1,0,1,0,...]` — 1 where the extraction matched the curated memory, 0 where it didn't.

7. **Phase 2 — Fusion operators (EDA + Crossover) using Hamming distance on those performance vectors**:
   - To select 2 parents for Crossover: pick the best candidate and the candidate with maximum Hamming distance from it (i.e., the one that fails on the most-different dev items — these two are *complementary*, not similar).
   - Then run Crossover on those two parents:
     ```
     You are a mutator who is familiar with the concept of cross-over in
     genetic algorithm, namely combining the genetic information of two
     parents to generate new offspring. Given two parent prompts, you will
     perform a cross-over to generate an offspring prompt that covers the
     same semantic meaning as both parents.

     ## Given ##
     Parent prompt 1: {parent_1}
     Parent prompt 2: {parent_2}
     Offspring prompt:
     ```
   - Also run EDA (Estimation of Distribution) on a subset of candidates selected for diversity (low pairwise performance-vector similarity):
     ```
     You are a mutator. Given a series of prompts, your task is to generate
     another prompt with the same semantic meaning and intentions.

     ## Existing Prompts ##
     {3-5 diverse candidates}

     The newly mutated prompt is:
     ```
   - Stop tolerance = 4 (Crossover/EDA take longer — don't give up after one bad iteration). Minimum 8 applications in Phase 2.

8. **Phase 3 — Semantic mutator for the last mile** (apply once to the surviving pool of 5):

   ```
   You are a mutator. Given a prompt, your task is to generate another
   prompt with the same semantic meaning and intentions.

   current prompt: {existing template}
   mutated prompt:
   ```

   Stop tolerance = 1. Keep the best candidate by `D_dev` score.

9. **Evaluate the winner on `D_test`** and ship it as the new `/learn` extraction template.

**Expected outcome:** A pattern-extraction template that has been jointly optimized over instruction + few-shot demos, with explicit knowledge of where it works and where it fails (the performance vector is your provenance trail). On the paper's BBH benchmark this kind of joint search beats instruction-only optimization by ~13 points on average while burning ~4,000 API calls (cost-realistic for a one-time template tune, not for per-session use). The artifact you actually want is the optimized template plus the test-set performance vector — together they form the operational contract for the extractor going forward.

## What Experts Overlook

The detail most reviewers will skim past is the **Hamming-distance-on-performance-vectors** trick in Section 3.4 design 1. On the surface it looks like a small implementation choice for the EDA/Crossover operators. What it actually does is replace a *semantic* notion of "similar prompts" (cosine on text embeddings) with an *operational* notion of "prompts that repeat each other's mistakes." Two prompts with totally different wording but the same failure pattern get treated as duplicates; two prompts with similar wording but opposite failure patterns get treated as maximally diverse. The performance-vector representation is also a 100% interpretable artifact — you can look at the vector and immediately see which dev examples each candidate handles.

**Why it matters:** This is the move that makes the fusion operators actually escape local minima. If you select parents by text similarity, you keep merging candidates that already make the same mistakes — the offspring has no new failure mode to exploit. By selecting parents by *complementary failure patterns*, you force the offspring to combine non-overlapping strengths. The same principle applies to any memory architecture where you want to identify "useful diversity" rather than "surface diversity" — what matters is differential behavior on downstream tasks, not differential representation in embedding space.

**Example of good use:** A Flow OS memory architect wants to keep their pattern-extraction templates diverse to cover edge cases. Instead of clustering past templates by sentence embeddings (which would group all "extract decision" templates together regardless of whether they actually succeed on different session types), they build a performance vector per template — `[did it extract correctly from session 1, session 2, session N?]` — and use Hamming distance to identify templates with *complementary failure modes*. These become the templates to keep alive in the candidate pool. The result: a small library of 5-7 templates that collectively cover the failure space, rather than 50 surface-different templates that all fail on the same hard cases.

**Example of misapplication:** A team builds the SEE loop but keeps cosine-on-text-embeddings as their similarity metric (it's the default in most vector stores, after all). Their fusion operators dutifully run, but every offspring inherits the same blind spots as its parents because "parents that look different in embedding space" turn out to fail on the same examples. After 4,000 API calls they have a marginally-better template that still fails on the same 20% of cases. They conclude SEE doesn't work — when in fact they bypassed the load-bearing design decision in the paper.
