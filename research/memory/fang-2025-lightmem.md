# LightMem: Lightweight and Efficient Memory-Augmented Generation

**Authors:** Jizhan Fang, Xinle Deng, Haoming Xu, Ziyan Jiang, Yuqi Tang, Ziwen Xu, Shumin Deng, Yunzhi Yao, Mengru Wang, Shuofei Qiao, Huajun Chen, Ningyu Zhang
**Published:** 2025-10 (ICLR 2026; arXiv v4 Feb 2026) · [Source](https://arxiv.org/abs/2510.18866)
**Lens:** `generic` · **Digested:** 2026-05-20

## TLDR

LightMem is a memory system for LLM agents that explicitly maps the three-stage Atkinson–Shiffrin human-memory model — sensory → short-term → long-term — onto three engineering modules and adds an offline "sleep-time" consolidation step. Light1 (sensory) uses LLMLingua-2 to drop ~30–60% of raw dialogue tokens before they ever reach an LLM. Light2 (topic-aware STM) buffers the compressed turns and only fires a summarization call once the buffer fills, segmenting it into topic chunks via the intersection of an attention-peak boundary set and a semantic-similarity boundary set. Light3 (LTM with sleep-time update) writes new entries with a "soft" insert at test time, then runs the expensive consolidation/merge/delete pass offline in parallel across independent update queues.

On the two standard long-term-memory benchmarks (LongMemEval-S and LoCoMo) and three backbones (GPT-4o-mini, Qwen3-30B-A3B-Instruct, GLM-4.6), LightMem strictly dominates four strong baselines (LangMem, A-MEM, MemoryOS, Mem0). Headline numbers: +2.09% to +29.29% accuracy improvement; total (online + offline) token usage cut by 6.9–38× vs. baselines; API calls cut by 13.3–55.5×; runtime cut by 1.18–12.4×. If you only count the online (test-time) cost — what the user actually waits for — the ratios blow out further: up to 105.9× fewer total tokens and 309.9× fewer API calls than the best baseline. The cost is a small bolt-on: LLMLingua-2 adds <2 GB of GPU memory and its runtime is already included in the reported wall-clocks.

The contribution is mostly architectural rather than algorithmic — every individual piece (token-level compression, attention/semantic chunking, batched offline updates) has precedent — but the paper's clean separation of online vs. offline cost and the consistency of the wins across two datasets × three backbones × four baselines is what makes it notable. Code is on GitHub at zjunlp/LightMem.

## Key Takeaway

The paper's central claim is that current LLM memory systems spend most of their compute on the wrong thing: re-summarising raw dialogue at every turn (or every session) using the most expensive LLM in the loop, and then re-summarising again during inference to resolve write conflicts. LightMem argues the human memory pipeline — quick sensory filter → topic-aware short-term consolidation → offline long-term reorganisation during "sleep" — solves all three problems at once, and it shows this is not just a metaphor: the pipeline, when actually instantiated with a small BERT-class compressor, a buffer-with-topic-boundaries trigger, and a parallel offline update queue, beats four production-grade systems by large margins on the two main long-term-memory benchmarks. The most load-bearing single design choice is decoupling memory consolidation from inference; that alone is what gives them 100× online-cost reductions, and it generalises beyond their specific compressor or chunker.

## Implications

For LLM-agent practitioners building any persistent-memory layer, the paper makes one prescription very hard to ignore: do not perform LLM-driven memory updates synchronously on the request path. Even if you keep everything else the same — same summariser, same retriever, same vector DB — moving updates to an offline queue with timestamp- and similarity-filtered candidates is the single biggest lever on user-perceived latency. The paper's numbers (159–309× fewer API calls online for the same task) are roughly an order of magnitude larger than any other reported optimisation for memory-augmented agents in 2024–2025.

For research, the result reframes "memory systems" as a layered scheduling problem rather than a representation problem. Most prior work (Mem0, A-MEM, MemoryOS, MemGPT, Zep, HippoRAG) competes on *what* is stored — graph vs. flat, hierarchical vs. tree, biologically-inspired indexing. LightMem competes on *when* it is stored, and wins anyway. That suggests representation work that ignores the scheduling axis is leaving most of the cost-quality frontier untapped.

For the prompt-compression line of work, LightMem is a strong existence proof that LLMLingua-2-style hard-prompt compression survives the round trip through downstream summarisation. The often-cited concern about compressed prompts being "lossy" doesn't show up: at r = 0.5–0.8 the LLM-as-judge accuracy on QA over compressed contexts matches uncompressed within noise. This unblocks a class of pipelines (RAG, long-context QA, agent traces) where compression has been resisted on accuracy grounds.

A caveat the paper itself does not foreground: the wins are measured on dialogue benchmarks (LongMemEval-S, LoCoMo). It's an open question whether topic-aware chunking with attention-peak boundaries transfers to non-dialogue settings — code traces, document collections, multi-agent traces — where the natural "turn" unit doesn't exist. The complexity analysis (Section 4) is generic but the empirical evidence is dialogue-only.

## How to Apply It (method)

The pipeline has three modules; each can be adopted independently.

**Light1 — Sensory module (pre-compression + topic boundaries).** For each new dialogue turn, run it through LLMLingua-2 (or any token-level compressor that emits a per-token retain/discard probability). Keep only tokens whose retain-probability exceeds a percentile threshold (the threshold is computed dynamically from the per-document score distribution and corresponds to a target compression ratio `r` ∈ {0.4, 0.5, 0.6, 0.7, 0.8}). Push the compressed turn into a fixed-size sensory buffer (the paper uses 512 tokens). When the buffer fills, segment it into topic chunks by computing two boundary sets and intersecting them:
- B1 (attention-based): from LLMLingua-2's layers 8–11, derive a turn-level attention matrix, then mark a boundary at any local peak of the sub-diagonal sequence `{M_{k,k-1}}` (the attention each turn pays to its immediate predecessor). A peak signals that turn k pays unusually little attention to turn k−1, suggesting topic shift.
- B2 (semantic-similarity): for each candidate boundary in B1, compute cosine similarity between adjacent turns using a sentence embedder. Keep boundaries where similarity drops below τ.
- Final boundaries B = B1 ∩ B2.

**Light2 — Topic-aware STM.** Accumulate topic-tagged turns in a second buffer of capacity `th` tokens (the paper sweeps th ∈ {0, 256, 512, 768, 1024}). When `th` is hit, call your summariser once per topic and produce an entry `{topic, summary, embedding, raw_user_turns, raw_model_turns}`. Save to LTM. This is the only place a strong LLM gets called during memory construction — it fires roughly `N · r^x · T / th` times for a dialogue of N turns × T avg tokens, versus N times for naive turn-level systems.

**Light3 — LTM with sleep-time update.** At test time, new entries are inserted into the LTM vector store as-is (no merge, no overwrite — just an append, with timestamp). After insertion (or on a periodic offline trigger), compute for each entry `e_i` an update queue `Q(e_i) = top-k entries e_j` where (a) cosine similarity above threshold and (b) `t_j ≥ t_i` (only later entries can update earlier ones — a deliberate temporal constraint that prevents "Tokyo trip" being deleted by a later "Kyoto inquiry"). Since each queue's `f_update` operation is independent, all queues run in parallel — the paper measures this as the single biggest contributor to its runtime advantage.

**Hyperparameters.** Optimal `r` depends on `th`: small `th` ∈ {0, 256} → r = 0.6; large `th` ∈ {512, 1024} → r = 0.7. The paper's recommended default for GPT-4o-mini is (r = 0.7, th = 512); for Qwen3 (r = 0.6, th = 768).

**What to use if you don't have LLMLingua-2.** The paper mentions a fallback: any generative LLM can serve as the compressor by scoring per-token cross-entropy under conditional context; high-entropy tokens are retained. This is slower (one forward pass per turn) but architecture-agnostic.

## What Experts Overlook

Four things in the paper deserve more attention than they get:

1. **The temporal-direction constraint on updates (t_j ≥ t_i) is doing more work than the paper credits it for.** It's mentioned in two sentences in Section 3.3, but in the Case Study (Section 5.6) it's clearly the mechanism that prevents "Tokyo trip" from being clobbered by "Kyoto inquiry". Most baseline systems (Mem0, A-MEM, MemoryOS) update bidirectionally and *do* lose earlier context in the same scenario. This is a one-line fix that any existing memory system could adopt independently of the rest of LightMem.

2. **The accuracy regression on Single-Assistant queries (Table 7) is large and unaddressed.** On LongMemEval-S Single-Assistant, LightMem scores 32.14% (GPT) and 31.25% (Qwen), versus 89.29% / 87.50% for FullText and 96.43% / 96.43% for A-MEM. That's a 50–65 percentage-point gap on one query category. The paper doesn't discuss why — the most likely culprit is that pre-compression is dropping verbatim assistant outputs that the queries need to recall exactly. This is a real failure mode of token-level compression that anyone copying the architecture should know about.

3. **Compression ratios are not free — the compressor is itself an LLM call.** The paper says LLMLingua-2 has "negligible" runtime impact and uses <2 GB GPU. That's true on the authors' hardware (4× RTX 3090). On API-only deployments or smaller edge devices, the per-turn compressor pass is no longer free, and the cost analysis in Section 4 (which counts only the summariser and updater LLM calls) understates the real overhead. The fallback "use a generative LLM as compressor" path is much more expensive.

4. **The "sleep-time update" framing oversells the biological analogy and undersells the engineering insight.** Atkinson–Shiffrin is invoked four times; the actual mechanism is "batched parallel updates with timestamp- and similarity-filtered candidate queues" — a standard scheduling pattern in databases (deferred index maintenance, write-behind caching). Framing it as a brain-memory analogy makes it sound novel and risky; framed as deferred batched maintenance it's a well-understood optimisation that the field should have adopted years ago.

One thing the paper handles unusually well: it reports the offline cost separately from the online cost in every table. Most prior work on memory systems either reports only end-to-end cost (which advantages systems that pre-compute heavily) or only test-time cost (which advantages systems that defer everything). LightMem's two-row format (online soft-update row + OP-update row) makes it cleanly comparable on either axis.

## Extracted Prompts

The paper does not publish memory-construction prompts in detail. The only fully-quoted prompts are the LLM-as-judge evaluation prompts in Appendix E.1, which are reusable for anyone running similar memory benchmarks:

**Standard QA judge (single/multi-session):**
> I will give you a question, a correct answer, and a response from a model. Please answer yes if the response contains the correct answer. Otherwise, answer no. If the response is equivalent to the correct answer or contains all the intermediate steps to get the correct answer, you should also answer yes. If the response only contains a subset of the information required by the answer, answer no.
> Question: {question}
> Correct Answer: {answer}
> Model Response: {response}
> Is the model response correct? Answer yes or no only.

**Temporal reasoning judge (with off-by-one tolerance):**
> [as above, plus] In addition, do not penalize off-by-one errors for the number of days. If the question asks for the number of days/weeks/months, etc., and the model makes off-by-one errors (e.g., predicting 19 days when the answer is 18), the model's response is still correct.

**Knowledge-update judge:**
> [as above] If the response contains some previous information along with an updated answer, the response should be considered as correct as long as the updated answer is the required answer.

**Single-session preference judge (rubric-based):**
> I will give you a question, a rubric for desired personalized response, and a response from a model. Please answer yes if the response satisfies the desired response... The model does not need to reflect all the points in the rubric. The response is correct as long as it recalls and utilizes the user's personal information correctly.

**Abstention judge:**
> I will give you an unanswerable question, an explanation, and a response from a model. Please answer yes if the model correctly identifies the question as unanswerable. The model could say that the information is incomplete, or some other information is given but the asked information is not.

These prompts are interesting in their own right because they encode a permissive grading policy (off-by-one tolerance, partial credit for rubric coverage) that visibly inflates ACC scores relative to a stricter judge. Anyone reproducing these numbers should be aware.
