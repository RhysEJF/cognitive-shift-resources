# EvoPrompt: Connecting LLMs with Evolutionary Algorithms Yields Powerful Prompt Optimizers

**Authors:** Qingyan Guo, Rui Wang, Junliang Guo, Bei Li, Kaitao Song, Xu Tan, Guoqing Liu, Jiang Bian, Yujiu Yang
**Published:** 2024-05 (ICLR 2024) · [Source](https://arxiv.org/abs/2309.08532)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

EvoPrompt is a gradient-free framework that uses an LLM as the mutation/crossover operator inside a classic evolutionary algorithm (either Genetic Algorithm or Differential Evolution) to search the discrete space of natural-language prompts. Starting from a population of N=10 prompts (a mix of hand-written instructions and LLM-generated variants), GPT-3.5 generates new candidates by following step-by-step instructions that imitate GA crossover+mutation or the DE recipe of "find the different parts between two prompts, mutate them, then combine with the current best". The dev-set score selects survivors; after T=10 iterations the best prompt is shipped. Across 31 datasets — 7 understanding (SST-2/CR/MR/SST-5/AG's News/TREC/Subj), 2 generation (SAMSum, ASSET), and 22 BIG-Bench Hard reasoning tasks — EvoPrompt beats human-written prompts and prior auto-prompt baselines (APE, APO) on both Alpaca-7B and GPT-3.5. Headlines: +5% on Subj (DE variant 75.55 vs GA 70.55, vs human 49.75), +3 SARI points on simplification, ROUGE-1 46.49 vs 43.95 on SAMSum summarization with GPT-3.5, up to 25% improvement on individual BBH tasks with a 3.5% average gain. The DE variant beats GA when initial prompts are weak (it explores by mutating only the *differences* between two parents) while GA is slightly better when seeds are already strong; choose roulette-wheel selection over tournament/random; population size 6 is enough for easy tasks, ~10 for complex ones. The compute cost is comparable to APE (same number of API calls, only ~3% more tokens), and the optimized prompts are human-readable English so you can audit them.

## Key Takeaway

The fastest way to optimize a discrete prompt isn't gradient descent in the embedding space or hand-tweaking — it's to treat prompts as DNA and use the LLM itself as the mutation/crossover operator inside a textbook evolutionary algorithm. Counter-intuitively, the "differential evolution" variant — which finds the *differences* between two prompts, mutates only those, then grafts them onto the current best — outperforms simpler genetic-algorithm crossover precisely *because* it preserves the shared (already-good) parts and only perturbs the candidates' disagreements. Two old ideas (1975 GA, 1997 DE) plus one new substrate (an LLM that can read English instructions for "crossover" and "mutate") is enough to beat the entire 2022–2023 stack of gradient-based prompt-tuning methods on 31 datasets, with human-readable outputs and no model access required.

## Implications

- **ENGRAM-A (Aggregate / Consolidation): use the LLM as the consolidation operator over a population of memory items.** EvoPrompt's core move — "give the LLM two artefacts and ask it to crossover/mutate them" — is directly the consolidation primitive a memory architect needs. Instead of hand-writing rules for how two contradictory memos get reconciled, define a Diff-mutate-graft instruction and let the LLM execute it, scored against a held-out dev set of queries the memory has to answer correctly.
- **ENGRAM-G (Ground / Trust): population-with-fitness gives you provenance for the *winning* synthesis.** Because every retained prompt has a numeric dev-set score and a parent lineage, you get auditable evolution — "this prompt scored 75.55 on Subj, descended from these two parents at iteration 7." Apply the same scaffold to memory consolidation: each consolidated memory carries its score and its source-memory IDs, so you can roll back a bad consolidation.
- **ENGRAM-E (Encode / write-time): seed the write-path with human knowledge, then let LLM diversify.** EvoPrompt's Table 6 ablation shows that "top-5 manual + 5 LLM-generated variations" beats either pure-manual or pure-LLM seeding for GA. Mirror this in memory ingestion: keep human-authored canonical entries as seeds, then let the LLM generate paraphrastic variants for retrieval robustness — don't replace human entries, augment them.
- **DE-style "mutate only the differences" is the right consolidation recipe when source memories disagree.** Table 5 shows that mutating *all* of two prompts (instead of only their different parts) drops Subj accuracy from 75.55 → 69.87. For a memory architect: when consolidating two near-duplicate notes that conflict on a few facts, don't paraphrase the whole thing — preserve the agreed-upon content and only ask the LLM to reconcile the disagreement. This is the algorithmic version of "surface the contradiction, don't smooth it away".
- **Always keep a "current best" anchor in the consolidation pool.** EvoPrompt (DE) injects the current-best prompt as "Prompt 3"; ablating it (the "eliminate" row in Table 5) drops Subj from 75.55 → 69.07. Translation: a memory consolidator should always ground new syntheses against the current best canonical entry on that topic, not just synthesise from the source pair. Without this anchor the system drifts.
- **Cost is the same as the dumb baseline.** Table 13 shows EvoPrompt uses 5.40M tokens vs APE's 5.39M for the same iteration count and *much* better scores. Translation: better consolidation algorithms don't have to cost more — the savings come from the algorithm's structure, not from buying more compute.
- **Don't conflate write-time and query-time optimization.** EvoPrompt is purely write-time: the prompt is optimised offline against a fixed dev set, then frozen. This is the right paradigm when (a) the task is stable and (b) you can construct a dev set. If queries are open-ended or drifting, you need a query-time variant (e.g., select-best-from-population at inference) — the paper doesn't address this and that's a real gap for production memory systems.
- **Population size scales with task complexity, not with corpus size.** Figure 6 shows N=6 is enough for the simpler simplification task while N=10 helps on harder Subj. For memory consolidation: don't run a 50-way ensemble synthesis on every memory cluster — calibrate population size to the difficulty of the consolidation, measured by inter-source disagreement.

## How to Apply It (method)

**Scenario:** You run a Flow OS instance that has accumulated 80 paper digests in `memory/knowledge-sources/papers/`. The `paper_details` extraction prompt was hand-written 6 months ago and you suspect it's leaving structured-field accuracy on the table. You have a held-out set of 30 papers where you've manually annotated the correct authors/year/venue/DOI. You want to evolve a better paper_details prompt using EvoPrompt-DE without touching any model weights.

**Steps:**

1. **Build a dev-set scoring function `f(prompt, D)`**: For each of the 30 held-out papers, run the candidate prompt against GPT-3.5, parse the structured output, compare to ground truth, and return a 0-1 accuracy. The score on the population is this metric averaged across the dev set. The paper used a single number per prompt — your equivalent is `correct_fields / total_fields` averaged across the 30 papers.

2. **Seed the initial population P₀ of size N=10**: Take your current production `paper_details.md` prompt plus 4 human-written variants you'd consider plausible. Generate the other 5 with GPT-3.5 using the resampling template from Figure 4:

   ```
   Generate a variation of the following instruction while keep the semantic meaning.
   Input: <your current paper_details prompt>
   Output:
   ```

   Score all 10 against the dev set. This is t=0.

3. **Pick the DE variant** (because your initial prompts are mixed-quality and Table 6 shows DE wins under those conditions). Identify the current best prompt `p_best` in the population.

4. **Run T=10 evolution iterations** — each iteration loops over every prompt `pᵢ` as the "basic prompt" and constructs a new candidate by sending GPT-3.5 the following DE instruction (this is the verbatim prompt from Figure 2/5 of the paper, swap in your prompts):

   ```
   Please follow the instruction step-by-step to generate a better prompt.
   1. Identify the different parts between the Prompt 1 and Prompt 2:
      Prompt 1: <randomly sampled prompt p_r1 from current population>
      Prompt 2: <randomly sampled prompt p_r2 from current population, r1≠r2≠i>
   2. Randomly mutate the different parts
   3. Combine the different parts with Prompt 3, selectively replace it with the
      different parts in Step 2 and generate a new prompt.
      Prompt 3: <p_best — the current top-scoring prompt>
   4. Cross over the prompt in the Step 3 with the following basic prompt and
      generate a final prompt bracketed with <prompt> and </prompt>:
      Basic Prompt: <p_i — the prompt being evolved this turn>
   ```

5. **Selection / update**: Score the new prompt `pᵢ'`. If `f(pᵢ', D) > f(pᵢ, D)`, replace `pᵢ` with `pᵢ'` in the population. Otherwise keep `pᵢ`. Population size stays constant at N=10. Update `p_best` if needed.

6. **Stop when converged** (paper's definition: average dev-set score change < 0.3% over two consecutive iterations) or at T=10 iterations, whichever is sooner. Total budget: ~N × T × (1 + |D|) = 10 × 10 × 31 = 3,100 API calls plus 100 generation calls.

7. **Ship the best survivor** of the final population back into `skills/digest-paper/prompts/paper_details.md`. Keep the previous version in git so you can roll back if regressions show up on real papers.

8. **Audit the winner**: Read the evolved prompt. If it's drifted from English-readable form or relies on something brittle (e.g., a specific phrasing the dev set rewards but production won't), throw it out — EvoPrompt's claim is that prompts stay human-readable, but you still verify before shipping.

**Expected outcome:** A new `paper_details.md` prompt that scores higher on your 30-paper validation set than the current production one, with an audit trail of every generation in the population, every parent pair that produced each survivor, and the dev-set score for each. Cost is roughly the same as running APE — only ~3% more tokens for substantially better quality (Table 13). The win is bounded by your dev set: if it's narrow, the prompt overfits; if it's representative, the gains transfer.

## What Experts Overlook

The detail most readers skip past is in Section 5.2 / Table 5: the **"mutate only the different parts"** design choice. Most experts read "we use differential evolution" and assume the LLM is doing some sophisticated vector arithmetic; in fact the entire DE-ness lives in *one English instruction* — "Identify the different parts between Prompt 1 and Prompt 2; mutate only those." The ablation that replaces this with "Randomly mutate Prompt 1 and Prompt 2" (the "All" row) drops Subj accuracy from 75.55 → 69.87 and ASSET SARI from 46.21 → 45.73. So the entire performance gap between EvoPrompt-DE and EvoPrompt-GA — the gap that makes DE the recommended default in the paper's conclusion — is created by one phrase in the instructional prompt that says "different parts" instead of "all contents." Combined with the "eliminate Prompt 3" ablation (which drops Subj further to 69.07), it's clear the win isn't "LLMs can do evolutionary algorithms" — it's "LLMs can do *this specific operator design* that exploits the structure of the existing population."

**Why it matters:** This is the difference between *consolidation that preserves agreed-upon content* and *consolidation that paraphrases everything*. The paper shows empirically that when you re-write what the sources agreed on, you destroy signal; when you only mutate the disagreements and graft them onto the current best, you preserve signal. For a memory architect this is the design principle for any LLM-driven consolidation step: hold constant what the sources agree on, mutate only the contested fields, and always anchor against the current canonical entry.

**Example of good use:** A Flow OS memory consolidator receives two slightly different captures of "Marcus Webb's role at Flow" from yesterday's call and last week's email. Instead of asking the LLM to "merge these two notes," it diffs them, finds the disagreement (one says "advisor," the other says "investor"), and asks the LLM to mutate *only that field* in the context of the current canonical contact entry. Result: the existing entry's structure and language are preserved, only the disputed field gets reconciled, and the change is auditable.

**Example of misapplication:** Same consolidator just sends both notes plus "please reconcile" to GPT-4. The model produces a fluent, plausible-sounding paraphrase that subtly rewrites the agreed-upon parts ("Marcus Webb — a key contact" becomes "Marcus Webb — a strategic partner") and the contested field gets averaged out into "advisor-investor." Now you've corrupted the agreed-upon content, the change isn't traceable to a specific input, and the next consolidation will compound the drift. This is the exact failure mode the EvoPrompt ablation predicts.
