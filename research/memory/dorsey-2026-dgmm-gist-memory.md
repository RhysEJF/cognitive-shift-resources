# The Dynamic Gist-Based Memory Model (DGMM): A Memory-Centric Architecture for Artificial Intelligence

**Authors:** Terry Dorsey, Kevin Huggins
**Published:** 2026-05 · [Source](https://arxiv.org/abs/2605.02106)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

DGMM (Dorsey & Huggins, Harrisburg University, May 2026) is an *architectural theory* — no implementation, no benchmarks, no algorithms — that proposes a memory substrate for AI in which experience is stored as a typed episodic graph $M_t = (V_t, E_t, S)$ with a fixed, time-invariant relational grammar $S$ and a small closed vocabulary of node types (Concept, Element, Time, Interaction, Source) and relation types (HAS_SUBJECT, HAS_ACTION, HAS_OBJECT, MODIFY_SUBJECT, ACQUIRED_AT, RECOUNTS). Critically, storage operates at the level of **gist** — defined as "the structured conceptual representation of an experience, that is, its essential relational content expressed through the node and relation types of the fixed schema, independent of the surface linguistic or syntactic form" — never at the verbatim form *and never as a pre-interpreted semantic fact*. All operations on $M_t$ are partitioned into four mutually exclusive regimes — **Ingestion** (strictly additive, schema-conformant; cannot modify, retype, or remove existing nodes), **Consolidation** (transformative but schema- and provenance-preserving; offline, decoupled from recall), **Recall** (read-only; constructs a working-memory subgraph $W_q = \psi(q, M_t) \subseteq M_t$ governed by 5 axioms R1–R5: subgraph, non-triviality, cue-sensitivity, boundedness, read-only), and **Analysis** (post-recall only, takes $W_q$ as sole input, produces transient outputs like embeddings/propositions/surprise/attribution without writing back) — with no operation spanning more than one regime. Three architectural invariants follow as proofs: (Prop 5.1) Episodic Persistence — $V_{t_1} \subseteq V_{t_2}$ and $E_{t_1} \subseteq E_{t_2}$ for all $t_1 < t_2$, so the only way to lose access to a memory is recall failure, never structural erasure; (Prop 5.2) Provenance Preservation under Consolidation — Source and Interaction nodes must transfer to any merged Concept, with Time nodes only generalisable if temporally consistent; (Prop 5.3) Locality of Cue-Conditioned Surprise — surprise $S(q; t_1, t_2) = \Delta(R_{t_2}(q), R_{t_1}(q))$ is invariant under changes to $M_t \setminus R_t(q)$, so continuous ingestion does not produce spurious surprise. Two concrete instantiations of the divergence operator are sketched: local neighborhood divergence $\Delta_{nbr} = 1 - |N_k \cap| / |N_k \cup|$ and embedding divergence $\Delta_{emb} = \|z_v(t_2|q) - z_v(t_1|q)\|$ computed *only* on post-recall projections $\Phi_q: W_q \to Z_q$. DGMM positions itself explicitly *against* HippoRAG (Gutiérrez 2024) and Zep (Rasmussen 2025) on three axes: (1) both embed semantic representations at ingestion time, fixing interpretive standpoint; DGMM defers to post-recall; (2) neither provides axiomatic specification — they are engineering artifacts whose structural properties cannot be verified independently of implementation; (3) provenance in both is metadata, in DGMM Source nodes are first-class typed graph citizens supporting multi-source coexistence without storage-time reconciliation. The paper is the first in a planned series; consolidation policies, recall strategy performance, surprise calibration, and empirical validation are all explicitly deferred to companion papers.

## Key Takeaway

DGMM occupies the **gist-pole** of the gist-vs-verbatim axis — the exact architectural mirror of Adler & Zehavi's *Storage Is Not Memory* (2026), which sits at the verbatim pole — but for *opposite* reasons grounded in the *same* cognitive-science substrate (fuzzy-trace theory, episodic-semantic interaction, hippocampal indexing). Adler argues "preserve verbatim because any extraction discards information you can't recover at query time"; Dorsey argues "preserve gist because any *embedded semantic interpretation* fixes a standpoint you can't revisit from a different cue without modifying storage." Both reject pre-interpreted, semantically-collapsed storage. Both push interpretation to query/recall time. The disagreement is over *what counts as pre-interpretation*: for Adler, structuring a turn into facts is the bug; for Dorsey, encoding a turn into a vector embedding is the bug, but decomposing it into a typed Concept–Element–Time–Source–Interaction graph is *not* pre-interpretation because the relational grammar is fixed, finite, and content-agnostic. The shared target — "late semantic commitment" — is the architectural primitive both papers identify as the missing piece in HippoRAG/Zep/Mem0. The right reading of DGMM under the memory-architect lens is therefore not "another graph-memory paper" but "a formal characterisation of what 'gist storage' means as a structural commitment, independent of which kind of object (text string, knowledge tuple, graph subgraph, vector) actually sits in the store." Take it as the *theoretical complement* to Adler's empirical case: DGMM tells you which structural invariants you need to *prove* you've preserved, regardless of the substrate you choose.

## Implications

- **The "gist-vs-verbatim" axis is not actually one axis — it's two.** Axis A: *substrate granularity* (verbatim text vs. compressed/extracted form). Axis B: *standpoint commitment* (does storage embed a semantic interpretation that fixes how the memory can be read later?). Adler 2026 says "don't extract" — which is a position on Axis A. DGMM says "don't fix semantic standpoint at storage" — which is a position on Axis B. You can be verbatim *and* standpoint-committing (a raw transcript embedded into a fixed vector at ingest = Adler's strawman). You can be non-verbatim *and* standpoint-free (DGMM's typed-graph gist = compressed form with no semantic embedding stored). Resolve this for Flow OS by deciding *independently* on both axes — and the v2 memory layer is already gist-on-Axis-A (atomic markdown files, not raw transcripts) and partially standpoint-free on Axis-B (frontmatter is structured but embeddings are computed post-hoc). `[E, A → R]`

- **Recall is a typed read operation with provable invariants, not "vector similarity search."** DGMM Definition 3 gives 5 axioms any admissible recall operator must satisfy: R1 Subgraph ($W_q \subseteq M_t$), R2 Non-triviality (returns something when cue has a structural correlate), R3 Cue-sensitivity (different cues yield different subgraphs), R4 Boundedness ($|W_q| < |M_t|$ in general), R5 Read-only ($M_t$ unchanged). The current QMD pipeline satisfies R1, R2, R3, R5 trivially but R4 is *not* enforced — under a vague query, hybrid search can return a large fraction of the index. Adding an explicit boundedness budget (token cap, similarity floor) makes the contract testable. `[R, M]`

- **Provenance is a first-class typed node, not metadata.** The single sharpest critical claim against HippoRAG and Zep is that both treat provenance as metadata on nodes rather than as participating graph citizens. DGMM Source nodes connect *to* Concepts via typed edges and survive consolidation by construction (Prop 5.2). Mapped to Flow OS: the `source:` frontmatter field should be lifted to its own searchable entity with its own card (`memory/sources/<slug>.md`) — exactly the move that makes "what does <person> say about X?" a structural query rather than a string match. `[G, N]`

- **Surprise is structural deviation in recall, not output-level anomaly.** DGMM Def 5–6: $S(q; t_1, t_2) = \Delta(R_{t_2}(q), R_{t_1}(q))$ where $\Delta$ is calibrated to *significant* shifts only (D4 significance threshold), guaranteed by Prop 5.3 to be invariant under non-recalled growth. For Flow OS this is the missing primitive behind `/decision-history` and `/connection-trace`: instead of asking "what did the user say about X" and reading the result, ask "for cue X, how has the recalled subgraph changed between week N and week N+k, holding the cue fixed?" That is a structural surprise readout — and the existing `qmd query` history is the input. `[R, A, M]`

- **Consolidation must aggregate evidence, never discard it (weight-summing not replacement).** When two Concept nodes are structurally equivalent (same Element set, Eq. 6), DGMM merges them into $v^*$ by summing edge weights $w(v^*, e) = w(v_i, e) + w(v_j, e)$ (Eq. 7) and *reattaching* all Time/Source/Interaction nodes (Prop 5.2). This is the inverse of LLM-extractor "canonicalisation" which collapses two source statements into one fact. For `/learn`'s consolidation pass: never merge two pattern observations into one — always keep both attributions and increment a strength counter. `[A, G]`

- **Storage and interpretation are different architectural concerns and should be coded as different modules.** DGMM's most repeated structural commitment is the separation of regimes — Ingestion never reads $M_t$ to decide what to write, Recall never modifies $M_t$, Analysis takes $W_q$ as sole input and can't peek at $M_t$. The corresponding Flow OS hygiene rule: never let `/work` or `/think` write to memory mid-run (Analysis regime), and never let `/learn` retrieve from memory to decide what to extract from the current transcript (Ingestion regime can read schema, not content). The current CLAUDE.md gating ("don't write memory proactively, wait for /learn") is a behavioural enforcement of exactly this regime partition — DGMM provides the formal grounding for why this matters beyond a stylistic preference. `[E, R, A, M]`

- **An "architectural theory" is a different artifact than an implementation paper — read it for invariants, not algorithms.** The paper makes no benchmark claim, prescribes no algorithm, gives no latency or accuracy number. Its contribution is exclusively *what must be true* of any memory substrate that calls itself gist-based and supports cue-conditioned recall. This is the missing layer in the open-source memory literature (Mem0, Zep, A-MEM, MemGPT) — they all claim "episodic memory" without any axiomatic test for whether their implementation satisfies that claim. For ENGRAM's six-dimension framework, DGMM is best used as a *checklist for the Encode and Network dimensions*: does the architecture provably preserve episodic identity? Does it preserve provenance under consolidation? Does it admit cue-conditioned subgraph extraction? `[E, N, G, A]`

- **The "fixed relational grammar" is a strong constraint on extraction LLMs that the field is currently ignoring.** Eq. 1 says: for any ordered pair of node types $(\tau_i, \tau_j)$, only a fixed subset of relation types is permitted. This prevents "schema drift, arbitrary relation invention, or post-hoc reinterpretation of structure." Compared to A-MEM (Xu 2025), which lets the LLM invent tags/links at ingest time — DGMM's grammar is a hard schema constraint that the extractor is bound by. Mapping to Flow OS: the relationship-taxonomy.md file *is* the equivalent of DGMM's $T_E^{(\tau_i,\tau_j)}$ — locked vocabulary, no invented relations. The DGMM result tells us this is the architecturally correct choice, not just a stylistic one. `[E, N]`

## How to Apply It (method)

**Scenario:** You're running a Flow OS / Cognitive Shift-style stateless agent loop with persistent memory in markdown + QMD hybrid search, and you've inherited a debate between two camps inside your own head: (A) Adler-style "store verbatim, defer all extraction to query time" and (B) the existing `/learn` pipeline that compiles transcripts into atomic v2 markdown files with structured frontmatter. You want to audit which design commitments DGMM tells you are non-negotiable, and run a small theoretical-conformance audit against your own architecture. The audit is *not* a benchmark — it's a structural test: does your memory layer satisfy the DGMM invariants, and if not, where does it cheat and at what cost?

**Steps:**

1. **Locate your gist substrate.** DGMM's "gist" = "the structured conceptual representation of an experience, that is, its essential relational content expressed through the node and relation types of the fixed schema, independent of surface linguistic or syntactic form" (Section 4.0.2). In Flow OS this is the atomic v2 memory file under `memory/`, with frontmatter as the typed structure and the body as the content. **Audit question:** is your gist substrate stored *before* any task-specific or query-specific embedding is computed? **Pass condition:** the markdown file with frontmatter is the canonical artifact; embeddings are derivable but not stored as the primary representation. `[Status: PASS]`

2. **Enumerate your operation regimes and check for cross-regime leakage.** DGMM Definition 1 partitions all operations into Ingestion (additive only), Consolidation (transformative, schema- and provenance-preserving), Recall (read-only), Analysis (post-recall, takes $W_q$ as sole input). **Audit question:** does any single Flow OS operation cross a regime boundary? **Common failure mode:** a `/work` session that reads memory (Recall) *and* writes a new pattern file (Ingestion) in the same operation. **Pass condition:** writes are batched and centralised in `/learn` (Ingestion) and `/work` is read-only with respect to long-term memory. Inspect `.claude/commands/` files: any `Write` calls inside `work.md` or `think.md` to `memory/` paths is a violation. `[Status: largely PASS; verify by greping command files for Write into memory/]`

3. **Test for the additive-growth invariant (Prop 5.1).** $V_{t_1} \subseteq V_{t_2}$ and $E_{t_1} \subseteq E_{t_2}$ for all $t_1 < t_2$. **Audit question:** can any operation in your pipeline delete or modify a previously-written memory file? **Common failure mode:** `/learn` "updating" an existing memory by overwriting it. **Pass condition:** updates are append-only (new file with `supersedes:` edge to old file, both retained). Check `git log --diff-filter=D memory/` and `git log --diff-filter=M memory/`: a high modification count is a violation. If you're modifying instead of superseding, you've broken Prop 5.1 and lost the ability to compute structural surprise over time.

4. **Test for provenance preservation under consolidation (Prop 5.2).** When two memories are merged or a pattern is generated from multiple captures, all Source/Interaction/Time nodes from the constituents must be preserved or admissibly generalised. **Audit question:** when `/learn` extracts a pattern from N transcripts, does the resulting pattern file retain *N* source references or does it collapse them into a single attribution? **Common failure mode:** a `source: user` in the pattern frontmatter that erases the specific captures it was extracted from. **Pass condition:** pattern frontmatter has `derived_from: [capture-1.md, capture-2.md, ...]` listing every contributing memory, and time references are either preserved per-source or generalised to an interval that covers all originals (e.g., "2026-04 to 2026-05" rather than "2026-05" if half were April).

5. **Test for recall axioms R1–R5.** Pick three real recent cues (e.g., "what did Dana think about Flow", "how has my view on verbatim storage evolved", "Nadia's last preference for hiking routes"). For each, run `qmd query "<cue>" --json -n 10` and inspect: **R1 Subgraph** — every returned file exists in memory (no synthesised results)? **R2 Non-triviality** — at least one result returned when the cue has obvious structural correlate? **R3 Cue-sensitivity** — different cues return materially different result sets, not the same top-N? **R4 Boundedness** — the recall budget is bounded *in general* (token cap, similarity floor), not just "top 10"? **R5 Read-only** — running the query did not modify any file? **Common failure mode:** R3 fails when QMD is over-tuned to one cluster and returns the same top results for paraphrases. **Pass condition:** all 5 axioms hold; if R3 fails, the cue-sensitivity is broken and you need to inspect the BM25/vector weighting in `qmd-config.json`.

6. **Run the locality-of-surprise diagnostic (Prop 5.3).** Pick a cue $q$ you've used in two sessions $t_1, t_2$ at least a month apart. Run `qmd query "$q" --json -n 20` against the current memory state $M_{t_2}$ and against `git checkout <commit-at-t1> && qmd query "$q"` then back. Compute $\Delta = 1 - |R_{t_1} \cap R_{t_2}| / |R_{t_1} \cup R_{t_2}|$ over the returned file sets. **Audit question:** does $\Delta$ reflect *actual* change in your thinking about $q$, or does it reflect routine growth of unrelated memories? **Pass condition:** $\Delta$ correlates with content change, not raw memory growth — i.e., adding unrelated patterns to `memory/` between $t_1$ and $t_2$ should not increase $\Delta$ for an unrelated cue. If it does, you've violated the locality invariant (probably because BM25 normalisation depends on the corpus, so adding documents shifts scores even when the cue is unrelated). Fix by computing $\Delta$ in *rank space within a fixed similarity floor*, not raw retrieval set.

7. **Test for fixed relational grammar violations (Eq. 1).** **Audit question:** does `/learn` ever emit a frontmatter relation type that isn't in `docs/relationship-taxonomy.md`? **Common failure mode:** the extractor invents `discussed-with:` or `prefers:` because the canonical vocab feels limiting. **Pass condition:** every relation in every frontmatter file is drawn from the locked taxonomy. Run a one-liner: `find memory/ -name "*.md" -exec yq '.. | objects | keys[]' {} + | sort -u | comm -23 - locked-relation-types.txt` — any output is a violation. The fix is *not* to expand the taxonomy reactively; it's to either map the new relation to an existing type or to formally add it to the taxonomy file and re-run `/learn` to backfill.

8. **Decide on the post-recall-analysis-only constraint (E1, E2 of Def 4).** DGMM forbids the embedding operator $\Phi_q$ from accessing $M_t$ — it operates exclusively on $W_q$. **Audit question:** when you compute embeddings, are they computed over the full corpus (sentence-transformer indexing all of `memory/`) or *only* over the recalled subset for that query? **Status:** Flow OS currently violates this — `qmd embed` runs over the whole corpus at index time, not per-query. This is a deliberate efficiency choice (precompute once, query many times) and is *not necessarily wrong* — but it means semantic representations are *not* cue-conditioned, which is what DGMM Prop 5.6 (proposition generation) requires for the "different cues, different propositions from same memory" property. **Implication:** for the QMD pipeline, this means proposition generation must happen *after* retrieval with a fresh LLM call that takes $W_q$ as sole input and produces propositions only at that point — i.e., the existing `/think` and `/decision-history` flows are DGMM-compliant *if and only if* they don't pre-embed their conclusions back into the index.

9. **Write the audit report.** For each of the 8 checks above, score: ✓ PASS / ⚠ PARTIAL / ✗ FAIL with a one-line explanation. The output is a `experiences/solutions/dgmm-conformance-audit.md` file with structured frontmatter (`kind: audit`, `framework: dgmm-2026`) so the next session can find it via QMD. **Decision criterion:** if you have ≥1 FAIL on R1–R5 or Prop 5.1, you have a substrate-correctness bug; if you have FAILs only on Def 4 (post-recall embedding) or schema-drift checks, you have an efficiency-vs-purity trade-off, not a bug.

10. **Decide on the gist-vs-verbatim axis explicitly.** With Adler's argument on one side and DGMM's on the other, write a short ADR (architectural decision record) at `memory/ventures/cognitive-shift/decisions/gist-vs-verbatim-adr.md` stating: (i) on Axis A (substrate granularity) Flow OS chooses gist — atomic markdown files, not raw transcripts; (ii) on Axis B (standpoint commitment) Flow OS chooses *deferred* — no stored interpretation, all semantic claims generated at recall time by `/think`/`/decision-history`; (iii) the tension with `/learn`'s pattern extraction (which *does* commit a standpoint at write time by writing `pattern: ...` markdown) is acknowledged and resolved by treating pattern files as *propositions* (DGMM Section 5.6 — explicitly transient and re-derivable) rather than as canonical facts. This ADR is the thing future sessions will read first when they're tempted to "improve" memory by collapsing or fact-canonicalising it.

**Pitfalls:**
- **Don't confuse "gist" with "vector embedding."** DGMM is explicit that gist is *structural-relational*, not distributional. A vector embedding *is* a pre-committed semantic interpretation in Axis-B terms, which is exactly what DGMM forbids at storage time.
- **Don't conclude DGMM "is HippoRAG without the implementation."** The paper makes a sharp axiomatic distinction (Section 6) and the difference is the deferred-semantic-commitment axis. Conflating them loses the point.
- **Don't write the audit as a perfectionism exercise.** Flow OS is allowed to violate Def 4 (post-recall-only embedding) for efficiency — DGMM is theory, your system is shipping. The audit is for *knowing where you cheated and why*, not for refactoring everything.

- **E (Encode):** the encode step takes a raw experience ("Jack went up the hill") and decomposes it into the typed graph — *not* into a sentence, *not* into a vector, *not* into an LLM-distilled fact. The Concept node carries no semantic content of its own; meaning lives in the *configuration* of edges to Elements.

Not a flat vector store, not a hierarchical document tree, not a free-form KG — *typed and grammar-constrained*.
- **G (Ground):** every Concept node has *at least* one Source (provenance), at least one Time node (and often two: event-time + acquisition-time — note 1/1/2000 vs 11/15/2025), and exactly one Interaction (episodic scope). Provenance is structural, not annotative.
- **R (Retrieve):** the four illustrative recall classes (element-conditioned, temporally-scoped, source-conditioned, interaction-scoped, Section 4.1.2 Remark 2) are visually obvious from the figure — you can read off how each cue type would induce a different subgraph.
- **A (Aggregate):** the figure foreshadows consolidation by showing weighted Concept-Element edges; the structural-equivalence policy (Eq. 6: $E(v_i) = E(v_j) \Rightarrow$ mergeable; Eq. 7: weight-summing) would collapse two such graphs into one Concept with summed Element weights and a *merged* set of Source/Time/Interaction nodes — the figure makes it obvious why provenance preservation matters: if you merged "Jack fetched water" from the book with "Jack fetched water" from an oral retelling, you'd want to keep both Source attributions and both Time nodes.
- **M (Maintain):** the additive-growth invariant means the figure is *append-only* — new edges and nodes can grow off any existing node, but no node can be deleted. The Emotion and Space placeholder nodes show how the architecture admits new dimensions over time without changing the schema validity of any existing memory.

## What Experts Overlook

Three things working memory-architecture researchers (HippoRAG, Zep, Mem0, A-MEM teams) consistently fail to engage with — that DGMM forces into the open:

1. **Gist storage is a category claim, not a substrate claim.** Most current systems labelled "episodic memory" (HippoRAG nodes, Zep edges, Mem0 facts) store *semantically-embedded* representations: text gets vectorised at ingest, edges get typed by an LLM at ingest, facts get canonicalised at ingest. DGMM Section 4.0.2 makes a sharp argument: "A concept stored without its temporal and contextual origins has already been interpreted, reduced from specific experience to a general abstraction, and that reduction cannot be undone at recall time." The overlook: practitioners conflate "explicit structure" (graph, table, file) with "uninterpreted structure" (no semantic commitment baked in). DGMM shows these are different — you can have explicit structure that has already *embedded* a standpoint, and the cost is invisible until you try to reinterpret under a new cue and discover the storage substrate has pre-committed against you.

2. **The four-regime partition is a structural correctness property, not an implementation detail.** DGMM Definition 1 partitions all memory operations into Ingestion, Consolidation, Recall, Analysis with the explicit rule that "no operation spans more than one regime." This is treated as a passing remark, but it's actually the deep claim — most agent-memory systems blur Recall and Analysis (retrieval and synthesis happen in one LLM call) and blur Ingestion and Consolidation (extraction-at-write-time is consolidation masquerading as ingestion). Practitioners don't notice because their systems "work"; DGMM points out that without the partition, you can't prove any invariant (the locality-of-surprise proof Prop 5.3 *relies* on Read-only Recall R5; the episodic-persistence proof Prop 5.1 *relies* on Additive Ingestion). What experts overlook: invariants you can't *prove* are invariants you can't *trust*, and the implementation people building Mem0/Zep/A-MEM have written zero proofs about their own systems.

3. **The companion-paper structure is the actual contribution.** DGMM is paper 1 of a planned series. Section 4.1.2 explicitly defers recall strategy performance to "a companion paper"; Section 5.3 defers surprise calibration to "the surprise companion paper"; Section 4.1.4 defers consolidation policy analysis to "the consolidation companion paper." Practitioners read this as "incomplete work" but the architectural argument is: *the theory must be specified before the implementation can be reasoned about*. The overlook: most agent-memory papers conflate the theory and the implementation in one document, and as a result it's impossible to tell which empirical results follow from the architectural choices and which follow from the implementation's incidental properties. DGMM-style separation lets you compare HippoRAG-the-architecture to Zep-the-architecture *independently* of HippoRAG-the-codebase and Zep-the-codebase — which is the only way to do meaningful comparative work in this field.

4. **"Schema drift" is the silent killer of long-running agent memory.** Eq. 1's relational grammar constraint ($T_E^{(\tau_i, \tau_j)} \subseteq T_E$, closed type-pair admissibility) is mentioned in passing but its consequence is huge: it prevents the LLM-extractor from inventing new relation types over time. The overlook: every system that uses an LLM to extract structure at write-time has *no* schema enforcement, so the type-vocabulary drifts as the model's whims shift, and after 10,000 turns your "knowledge graph" has 3,000 effectively-synonymous relation types and no two memories of the same kind are queryable consistently. DGMM's locked relational grammar is the architectural fix — and it's the same architectural principle as Flow OS's `docs/relationship-taxonomy.md` lock, which is explicitly called out in CLAUDE.md as load-bearing. Most agent-memory teams don't have this lock and don't realise they need one.

## Extracted Prompts

The paper is a pure architectural theory paper — no prompts, no LLM-in-the-loop steps, no implementation details. The closest thing to "prompts" the paper offers are its **architectural specifications** (axioms, propositions, formal definitions) which can be read as design-time prompts that any implementing system must answer. Reproduced verbatim in extracted form:

**Prompt-as-design-specification #1 (Recall Operator Contract, Definition 3):**
> An operator $\psi : Q \times M_t \to W_q$ is admissible under DGMM if and only if it satisfies the following axioms: R1 Subgraph: $W_q \subseteq M_t$ for all $q$ and $t$. R2 Non-triviality: for any non-empty $M_t$ and cue $q$ that is present in memory, $W_q \neq \emptyset$. R3 Cue-sensitivity: there exist cues $q_1 \neq q_2$ such that $\psi(q_1, M_t) \neq \psi(q_2, M_t)$. R4 Recall Boundedness: $|W_q| < |M_t|$ in general. R5 Read-only Recall: $M_t$ is unchanged by the application of $\psi$.

**Prompt-as-design-specification #2 (Embedding Operator Contract, Definition 4):**
> A function $\Phi_q : W_q \to Z_q$ is an admissible embedding operator under DGMM if and only if it satisfies: E1 Post-recall domain: $\Phi_q$ takes $W_q$ as its sole input and has no direct access to $M_t$. E2 Read-only: $\Phi_q$ does not modify $M_t$ or $W_q$ during the embedding computation. E3 Transience: the output $Z_q$ is transient and is not written back to $M_t$ unless explicitly committed through a subsequent ingestion operation.

**Prompt-as-design-specification #3 (Divergence Operator Contract, Definition 6):**
> A function $\Delta$ is an admissible structural divergence operator for DGMM if it satisfies: D1 Non-negativity. D2 Zero self-divergence: $\Delta(R_{t_1}(q), R_{t_2}(q)) = 0$ if $R_{t_1}(q) = R_{t_2}(q)$. D3 Domain restriction: $\Delta$ takes as input pairs of recall-induced subgraphs $R_{t_1}(q)$ and $R_{t_2}(q)$ such that both subgraphs are constructed under the same cue $q$. D4 Significance threshold: $\Delta$ is calibrated to a notion of structural significance appropriate to the memory context.

**How to use these as actual prompts.** Treat each axiom as a one-line check in a unit-test suite over your own memory layer. For DGMM-conformance audit (Method step 5 above):

```
For each axiom R1-R5, E1-E3, D1-D4:
  Given a test cue and a test memory state, write a function
  that verifies the axiom holds, and add it to your test suite.
  The system passes iff all 12 functions return True for
  100 random (cue, state) pairs.
```

That's the entire "prompt" library this paper provides — but it's the most useful kind, because passing all 12 tests is a non-trivial guarantee about your architecture that most implementing systems cannot offer.
