# Storage Is Not Memory: A Retrieval-Centered Architecture for Agent Recall

**Authors:** Joshua Adler, Guy Zehavi
**Published:** 2026-05 · [Source](https://arxiv.org/abs/2605.04897)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

True Memory (Sauron Labs, May 2026) argues that extraction-at-ingestion is the wrong primitive for agent memory because anything an LLM-distilled schema discards before the query is unrecoverable; instead, events are stored verbatim in a single SQLite file (FTS5 + sqlite-vec, ~123 MB of model weights, runs on a Raspberry Pi 4 with under 1 GB RAM, no GPU/graph DB/vector service) and a six-layer pipeline does the hard work at retrieve-time via lexical+dense candidate generation, weighted reciprocal rank fusion (k=60, w_fts=w_vec=1, w_sep=0.8·w_vec), L3 salience reweighting, and a cross-encoder rerank (top-k=10 from a pre-rerank window of 100). On LoCoMo (1,540 questions, gpt-4.1-mini answerer, gpt-4o-mini 3-judge majority) TM Pro scores 93.0% (3-run mean) — vs 94.5% for EverMemOS (which needs a 4B-param GPU embedder + Neo4j), ~71% for Zep, 65.4% for Supermemory, 61.4% for Mem0, 86.2% for RAG-ChromaDB, 80.5% for BM25, and a 92.99% full-conversation oracle ceiling — so TM Pro hits 99.9% of oracle at ~$0.0013 per correct answer vs $0.0129 for the oracle; on LongMemEval 87.8% (beats every memory product by ≥4.8 pp) and on BEAM-1M 76.6% vs Hindsight's 73.9%. A diagnostic on 357 incorrect early-version answers showed 92.4% became correct when given the full conversation, locating errors in retrieval not storage; a 56-configuration ablation (7 embedders × 8 rerankers) spans only 3.2 pp (89.9–93.1%) with the Matryoshka-256d subfamily spanning just 1.3 pp, while query expansion (HyDE) adds 1.0 pp — i.e., architecture choice dominates component choice by an order of magnitude. The novel encoding gate combines novelty (gzip-compression-cost vs nearest stored neighbours, AUC 0.788 vs 0.484 for cosine baseline), salience (rule-based speech-act classifier for ≤50 chars, else length/numbers/dates/affect scorer), and prediction error (embedding pair-difference cosine divergence, AUC 0.730 standalone, 0.816 in three-signal combination) with weights (λ_n, λ_s, λ_π, τ)=(0.25, 0.20, 0.30, 0.30) plus per-category threshold offsets — but the gate is disabled in every benchmark because no existing eval rewards selective ingestion. **Most useful takeaway:** in this regime the retrieval architecture moves accuracy ~20–30 pp while component swaps move it 1.3–3.2 pp, so if you're designing agent memory, the highest-leverage decision is preserving the raw substrate and centralising synthesis at query time, not picking a better embedder or graph schema.

## Key Takeaway

Stop extracting at write-time. The dominant assumption in agent memory (Mem0, Zep, Graphiti, Supermemory) is that you must parse incoming conversation into structured facts/entities/graphs at ingestion so retrieval is fast and clean — but this paper shows that move is the bug, not the feature: anything the extractor discards before knowing the query is permanently unrecoverable, and that's where ~30 points of accuracy bleed out. Keep raw events verbatim, push all the interpretation to query time, and a single SQLite file on a Raspberry Pi beats every cloud-hosted graph-and-vector pipeline except one. The corollary is even sharper — on the failing questions, just handing the full conversation back to the same answer model recovers 92% of them, which proves the bottleneck was never storage or model capacity but the write-time schema deciding what mattered before the question existed. Stated as a lesson: **write-time intelligence is anti-intelligence; the smartest move at encoding is to refuse to be clever.**

## Implications

- **Stop extracting at ingest; preserve verbatim and synthesize at query time.** True Memory beats Mem0/Supermemory/Zep by ~20–30 pp on LoCoMo (93.0% vs 61–71%) precisely because content the extractor discards before the query is known cannot be recovered later. Move your `/learn` extractor's role from "compress conversation into canonical facts" toward "tag and index a verbatim event substrate," and defer claim-shaping to retrieval time. `[E → R, A]`

- **Use an encoding gate, not an extraction step, as your write-time filter.** The paper's three-signal gate (novelty via gzip compression cost, salience via speech-act classifier, prediction-error via embedding pair-difference) hits AUC 0.816 and decides whether to *admit* an event verbatim — it never rewrites it. This is the right shape for a QMD-gated pipeline: cheaply score whether a turn is worth keeping, then store it raw with the signal tags as metadata. `[E]`

- **Treat novelty as a query against existing memory, not a property of the new event.** Two of the three gate signals (novelty, prediction error) interrogate the same stored substrate the retriever uses, so admission and recall share one representation rather than being separated by a schema boundary. Concretely: your gate should call `qmd query` against existing memories before deciding to write — this also kills the duplication that motivated centralizing writes in `/learn`. `[E ↔ R]`

- **Hybrid (BM25 + dense) with RRF fusion + cross-encoder rerank is the floor, not the ceiling — but the architecture matters far more than component choice.** Across 56 embedder×reranker combinations the spread was only 3.2 pp (1.3 pp within the top family), while the gap to extraction-based competitors was ~20–30 pp. Stop tuning your embedder; instead invest in the *pipeline shape* (lexical+dense fuse → salience reweight → cross-encoder rerank). The existing QMD hybrid already has the right bones — add a reranker stage before deciding what to inject into context. `[N, R]`

- **Build consolidation as post-ingestion batch artifacts that point back to verbatim events, never as replacements.** L4 (summaries, contradiction records, timelines with `superseded-by` links) and L0 (per-speaker engrams) are computed *after* ingestion and live alongside the raw substrate, so any future scoring function can be re-evaluated retroactively against the full history. For Flow OS this means atomic pattern files in `memory/patterns/` should reference source captures by path/ID, and contradictions should be recorded as paired-row artifacts rather than smoothed into a single "current truth." `[A, G]`

- **Retrieval is the bottleneck, not storage — instrument it directly.** When the same answer model was given the full conversation instead of retrieval results, it recovered 92% of previously-wrong answers, locating failures in the retrieval pipeline rather than in what was stored. Build the analogous diagnostic for your brain: a periodic eval where you replay user questions with (a) current retrieval and (b) full unfiltered memory, and measure the gap — that gap is your retrieval debt. `[R, M]`

- **Knowledge-update / contradiction is the hardest category — surface it, don't smooth it.** Per-category recovery showed Cat 3 (knowledge-update) was both the smallest and worst-recovered class, because retrieval-only systems surface stale info even when corrections exist in storage. Add explicit `supersedes` / `contradicts` edges to the relationship taxonomy, and have `/think` and `/decision-history` explicitly fetch *both sides* of a contradiction pair rather than relying on recency. `[G, A → R]`

- **Selective ingestion can't be scored by current benchmarks — design your own offline eval for it.** The authors disable their gate in all reported numbers because LoCoMo/LongMemEval/BEAM reward total recall and penalize selectivity, leaving "does the gate help end-to-end?" unanswered. If you want to claim Flow OS's `/learn` gate adds value (vs. an "admit everything" baseline), build a private benchmark with adversarial noise injected into transcripts and a downstream task that *penalizes* memory bloat — otherwise you're flying blind on whether gating helps or hurts. `[E, M]`

- **Run a single-file SQLite stack — polyglot (graph + vector + relational) buys ~1.5 pp at huge ops cost.** True Memory Pro (single SQLite, CPU) hits 93.0%; EverMemOS (Neo4j + GPU embedder + multi-service cloud) hits 94.5%. For a personal/team second-brain at this scale, the polyglot tax (auth, drift, ops) is not worth 1.5 pp — keep memory in flat markdown + SQLite-FTS5 + sqlite-vec, and resist the urge to add a graph DB unless you can show a class of query that BM25+dense+rerank provably can't serve. `[N]`

## How to Apply It (method)

**Scenario:** You are running the memory layer for an agentic OS (Flow OS-style stateless loop + persistent memory) and have inherited a write-time pipeline that runs an LLM extractor over every transcript turn, distilling it into atomic facts, entity profiles, and pattern memos before storage. Retrieval is currently a vector-only nearest-neighbor lookup over those distilled artifacts. Users keep complaining that the assistant "forgot" details they clearly said. You suspect the LLM-distillation step is destroying the substrate the retrieval needs, and want to A/B test a True-Memory-style "raw-store + multi-stage retrieval" path against your current "extract-on-write + similarity-search" path on your own data. This maps directly to ENGRAM's Encode and Retrieve axes and is the kind of write-time-vs-query-time-synthesis question your team is actively investigating.

**Steps:**

1. **Freeze your evaluation set**: Export 10 multi-session conversations from your current users (or use the public LoCoMo set if user-data is sensitive) and ~1,500 question/answer pairs where you know the ground truth (gold answer + the originating utterance). Tag each Q by category: single-session-recall, multi-session-recall, knowledge-update (the user later corrected something), and temporal. You need the category split to expose where extraction-on-write fails hardest, which the paper shows is the knowledge-update bucket.

2. **Stand up Arm A (your existing extract-on-write stack) unchanged**: Keep your current LLM-distillation extractor, your vector DB, and your similarity-only retrieval. Document the exact pipeline (model versions, top-k, prompt) and freeze it. This is the control.

3. **Stand up Arm B (True Memory Pro replica) on the same hardware**: Clone the TrueMemory open-source repo. The whole persistent layer is one SQLite file — no Neo4j, no Pinecone, no GPU. Three tables that matter for the test: `messages` (verbatim event substrate, L1), `messages_fts` (FTS5 BM25 lexical index, L1), `vec_messages` (sqlite-vec dense index at 256 dims, L2). Replay every event from your test corpus through `truememory.ingest` with the encoding gate **disabled** (`tau = -infinity`, admit everything) so the comparison is purely about write-time extraction vs verbatim retention, not about selective ingestion. Use the Pro tier config: Qwen3-Embedding-0.6B truncated to 256 dims via Matryoshka, gte-reranker-modernbert-base cross-encoder, HyDE query expansion on.

4. **Wire both arms to the same answer model and judge**: This is non-negotiable for a clean read. Use `gpt-4.1-mini` (temperature 0, max 200 tokens) as the answer model behind both arms, top-k=10 after rerank into context. Use `gpt-4o-mini` (temperature 0) as a 3-run majority judge with the prompt below. Run each arm 3 times end-to-end so you can report 3-run means and detect run-to-run variance.

   ```
   You are a strict semantic-match judge. Given a QUESTION, a GOLD ANSWER, and a CANDIDATE ANSWER, output exactly one token: CORRECT if the candidate conveys the same factual content as the gold (paraphrase allowed, extra commentary allowed if it does not contradict), otherwise INCORRECT. Do not explain.
   QUESTION: {q}
   GOLD: {gold}
   CANDIDATE: {candidate}
   ```

5. **Compute the headline accuracy + 95% Wilson CI per arm**: Report the 3-run mean accuracy with Wilson CIs over N. The paper's gap is ~30 pp between True-Memory-Pro (93.0%) and extraction-based competitors (Mem0 61.4%, Supermemory 65.4%) on LoCoMo — if your gap looks similar on your data, that alone is the decision. If your gap is < 5 pp, your extractor is unusually well-tuned and the rest of the experiment will tell you why.

6. **Run the retrieval-bottleneck diagnostic**: For every question Arm A got wrong, send the **full conversation** (not your retrieved chunks) to the same answer model with the same prompt. Compute recovery rate. The paper saw 92% of wrong answers recover under full context — meaning the bottleneck was retrieval, not the answer model. If your Arm A recovers >80% under full context, the LLM extractor is throwing away substrate the model could have used; if it recovers <50%, your problem is upstream of memory (answer-model reasoning) and switching architectures won't help much. Do the same for Arm B's wrongs, to identify True Memory's residual ceiling on your data.

   ```
   Below is the full transcript of a conversation. Answer the QUESTION using only what the transcript states. If the transcript is silent, say "INSUFFICIENT INFO."
   TRANSCRIPT:
   {full_transcript}
   QUESTION: {q}
   ANSWER:
   ```

7. **Break out per-ENGRAM-dimension** by mapping question categories to ENGRAM stages:
   - **Encode** → does the substrate contain the answering utterance at all? (utterance present in store y/n)
   - **Retrieve** → given utterance present, was it returned in top-k? (retrieval hit y/n)
   - **Ground** → given top-k included it, did the answer model use it? (cited correctly y/n)
   - **Aggregate** → multi-session questions where evidence spans turns
   - **Maintain** → knowledge-update questions where a later utterance overrides an earlier one; contradiction-handling
   - **Network** → temporal/ordering questions that require relations between events

   For each arm × dimension, report accuracy + Wilson CI. The paper shows knowledge-update (Maintain) and temporal (Network) are where extraction-based systems collapse hardest because the extractor's commit-on-write choice can't be undone.

8. **Cost-and-latency Pareto plot**: For each arm, record per-query retrieval latency, monthly compute cost at your real query volume, and storage footprint. Plot accuracy (y) vs monthly $ (x, log scale). The paper's Figure 3a is the template — your decision should be whether Arm B sits above and to the left of Arm A.

9. **56-cell mini-ablation (only if Arm B wins)**: Sweep True Memory's embedder × reranker grid (7 embedders × 8 rerankers) on a 500-question subset. The paper's finding: 3.2 pp spread across the full 56-cell grid, 1.3 pp within the Matryoshka-256d subfamily. If your grid shows the same narrow spread, the answer is: component choice barely matters compared to the architectural choice of preserving the substrate. If your grid shows >10 pp spread, your domain is component-sensitive in a way the paper's domain wasn't.

10. **Ablation: turn the encoding gate ON (your selective-ingestion question)**: Re-run Arm B with the gate enabled (weights λ_n, λ_s, λ_π, τ = 0.25, 0.20, 0.30, 0.30, salience floor 0.10, category offsets correction −0.06 / decision −0.04 / relationship −0.04). Measure admission rate, accuracy delta vs gate-off, and per-category accuracy delta. The signal formulas to implement:

    ```
    novelty:   n_t = (|gz(M || e_t)| - |gz(M)|) / |gz(e_t)|
               where M = concatenated text of nearest stored messages by L2,
               gz = gzip level 6.

    salience:  if len(e_t) <= 50 chars: rule-based speech-act score
                                       (commitment=0.8, correction=0.6,
                                        question=0.2, noise=0.02)
               else: L3 retrieval-salience scorer over length, numbers,
                     dates, emotional markers.

    pred_err:  pi_t = 1 - cos( embed(e_t [SEP] m_1), embed(m_1 [SEP] m_1) )
               where m_1 = nearest stored memory.

    admit iff: (lambda_n*n_t + lambda_s*s_t + lambda_pi*pi_t) /
               (lambda_n + lambda_s + lambda_pi)  >=  tau + delta_c
               AND s_t >= 0.10
    ```

11. **Drift / provenance check (Maintain axis)**: Pick 30 questions where your user later contradicted an earlier statement. For each arm, inspect what got returned in top-k: did it surface the *latest* correct version, the *earliest* (now stale) version, or both? Arm A (extract-on-write) typically locks in the first version. Arm B preserves both verbatim and uses the L4 consolidator's contradiction-records + temporal `supersedes-by` links. This is the most important qualitative read for your "AI as maintainer not oracle" question.

12. **Decision and writeup**: Tabulate accuracy + cost + latency + per-ENGRAM-dimension for both arms, plus the gate-on/gate-off delta. Decision rule: keep the LLM-distillation step only if Arm A is within 3 pp of Arm B AND the retrieval-bottleneck diagnostic shows the LLM extractor isn't where information is being lost. Otherwise, migrate to raw-store + multi-stage retrieval and treat the extractor's output as *derived* artifacts computed post-ingestion in batch (consolidation, summaries, entity profiles), not as the substrate.

**Expected outcome:** A head-to-head on your own data, with 3-run means and Wilson CIs, decomposed along every ENGRAM dimension. The retrieval-bottleneck diagnostic localizes any remaining errors to either storage, retrieval, or answer-model reasoning, so you'll know whether the next investment is in the substrate, the pipeline, or the model. The 56-cell sweep tells you whether your domain is component-sensitive or architecture-dominated. The gate-on/gate-off ablation answers a question no public benchmark currently answers — whether selective ingestion improves end-to-end accuracy on your real workload. The drift/provenance pass surfaces whether your memory layer is currently acting as an oracle that picks winners silently or as a maintainer that preserves contradictions for human adjudication.

## What Experts Overlook

Most readers will fixate on the headline finding — "store verbatim, decide what matters at query time" — and treat the encoding gate as a separable noise filter you can bolt on. The detail almost everyone will miss is buried in Section 4.1, Stage 1: of the gate's three signals, **two of them (novelty and prediction error) compute their score by retrieving from the same L1/L2 indices that serve query-time retrieval**. Novelty (`n_t`) is a gzip-compression cost of the new event concatenated against its nearest stored neighbours — i.e., the gate runs a retrieval against the verbatim store *before deciding whether to admit*. Prediction error (`π_t`) does the same: it embeds (event ‖ nearest stored memory) and compares it to (nearest ‖ nearest). Only salience scores the event in isolation. This is what the paper means when it says "ingestion and retrieval share a common representation rather than being separated by a schema boundary" — it isn't a slogan, it's an implementation invariant. The corresponding ablation evidence makes this visible: when they tried the obvious thing (cosine-similarity-inversion as a novelty proxy), AUC was 0.484 — worse than a coin flip on conversational data, because "ok" is semantically far from facts while genuine updates are semantically close. Replacing that with gzip-cost-against-retrieved-neighbours pushed AUC to 0.788. The gate works because it reuses the retriever, not because it has good heuristics.

**Why it matters:** This collapses what most architectures treat as two independent subsystems — the write-side filter and the read-side ranker — into one closed loop where every admission decision is a tiny query against everything already known. It makes the gate **self-calibrating with the corpus**: as memory grows, "novelty" automatically means "novel relative to *this* user's history," not "novel relative to some pretrained prior." It also explains why the system survives the disclosed limitation that the gate is disabled in benchmarks: even with the gate off, the retrieval substrate is doing the same work it would have done at write-time, just deferred. The architectural property the paper is actually defending is **representational symmetry between encode and retrieve**, not verbatim storage per se. Verbatim is a consequence; the cause is "don't commit to a representation the retriever can't speak."

**Example of good use (memory architectures for agentic OSes):** In Flow OS / QMD, when `/learn` is about to write a new memory, run the candidate text through `qmd query` against the existing memory first and use the BM25+vector hit profile as a write-time signal. If the candidate compresses cheaply against its top-5 neighbours, downgrade it to a frontmatter edge on the existing memory rather than a new file; if it diverges from its nearest topical neighbour (the prediction-error analogue — "same entity, different claim"), flag it as a contradiction-candidate *before* it lands, attaching the conflicting file path in frontmatter. The retriever and the dedup/contradiction-detector are now the same component, which means improving QMD's ranking automatically improves write-time deduplication — exactly the compound-learning property the brain is supposed to have. This also gives you a free provenance handle: every admitted memory carries a record of which existing memories it was scored against.

**Example of misapplication:** A team reads the paper, decides "great, we'll add a novelty gate to our extraction-based memory system" — but they compute novelty against a *separate* embedding store dedicated to the gate, or worse, against a frozen pretrained similarity prior (the cosine-inversion trap the paper explicitly warns about, AUC 0.484). What breaks: the gate starts rejecting genuine updates because real corrections phrased in familiar vocabulary look "non-novel" to a generic embedder, while admitting high-perplexity noise ("hjdshfk hello??") because it's lexically unusual. Worse, because the gate's index drifts away from the retriever's index over time (different embedder versions, different chunking, different recency), the system silently develops a class of memories that were admitted under one representation and are unfindable under another — the exact failure mode the paper attributes to extraction-based systems, reintroduced through the back door. The lesson the team missed: the gate isn't a classifier, it's a retrieval call.
