# Continuum Memory Architectures for Long-Horizon LLM Agents

**Authors:** Joe Logan (Mode7 GK, Tokyo)
**Published:** 2026-01-14 · [Source](https://arxiv.org/abs/2601.09913)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

Logan names **Continuum Memory Architecture (CMA)** as an *architectural class*, not a specific system: any LLM-agent memory worthy of the name must satisfy six behavioral requirements — persistence across sessions, selective retention (decay + competition), retrieval-driven mutation, associative routing (spreading activation), temporal continuity (episodic chains), and consolidation/abstraction. RAG fails all six. The paper deliberately withholds implementation details and instead specifies the *checklist*. A reference instantiation (graph substrate + activation engine + retrieval scorer + background consolidation jobs over a Supabase pgvector store) is evaluated against a recency-weighted RAG baseline on four behavioral probes (Knowledge Updates, Temporal Association, Associative Recall, Disambiguation). CMA wins **82 of 92 decisive trials** with large effect sizes (Cohen's d=1.84 on updates, h=2.06 on temporal, h=0.99 on associative, h=1.55 on disambiguation), at the cost of **~2.4× latency** (1.48s vs 0.65s mean). The framing is the contribution: position CMA as a category against which existing systems (A-MEM, Hindsight, MemGPT, MemoryBank) can be scored, rather than as another point solution.

## Key Takeaway

The contribution is **a falsifiable checklist for what counts as agent memory**. By defining CMA as six necessary-and-collectively-sufficient behavioral conditions, Logan converts "memory" from a marketing term into a property you can probe for: if your system can't retrieve a fragment from days-old interactions without transcript replay (persistence), if it can't show *measurable rank changes after repeated queries* (mutation), if it can't return events lacking lexical overlap with the query (associative routing), or if it can't pull *temporally-adjacent semantically-dissimilar* events around an anchor (temporal continuity) — you do not have a CMA, you have a RAG variant with heuristics on top. The behavioral-probe methodology (40 updates / 30 temporal / 30 associative / 48 disambiguation queries, GPT-4o-judged with permutation tests at p<0.01) is itself a contribution: it gives the field a *diagnostic* battery that targets memory dynamics rather than recall fidelity, where LongBench and LoCoMo currently sit. **[ENGRAM: spans all six dimensions — the paper is explicitly an architectural taxonomy.]**

## Implications

**For my Flow OS memory layer:**

- **The checklist gives me a self-audit.** Run my own system against the four probes and grade it. My current QMD + frontmatter v2 + `/learn` extraction stack clearly satisfies persistence and selective retention (via the watermark + Stop-hook queue) and partial associative routing (entity-slug edges + wiki-links). It **does not yet implement retrieval-driven mutation** — query results don't update reinforcement, and there's no "interference penalty" on near-misses. That's a concrete next experiment. **[ENGRAM: R × M cross-dim — retrieval feedback loop into maintenance state]**
- **The latency cost is the real news.** A 2.4× latency hit (1.48s vs 0.65s) for CMA-class behavior is the explicit price of "memory as active system." This calibrates the design space: if your retrieval budget per agent turn is <500ms, you cannot afford full CMA — you have to either (a) move the consolidation work asynchronously (Logan's "Consolidation Jobs" as background workers) or (b) accept that only a subset of queries warrant the full activation spread. My QMD hybrid query at ~10s is already over budget for tight loops; the implication is **either pre-compute activation maps at write-time, or admit two retrieval modes (fast-RAG for normal, slow-CMA for memory-stress queries).** **[ENGRAM: E × R — encode-time work amortizes recall cost]**
- **"Stewards can rewind or dampen runaway updates" is the only safety mechanic mentioned for memory drift.** This is a gap — Logan flags drift as a limitation but offers only "log provenance, reinforcement history, and anomaly scores." This is a thin answer relative to the severity (reinforcement loops compounding incorrect memories). The orbit-discovery hypothesis here: **CMA needs a contradiction-surfacing protocol baked in**, not a post-hoc audit. My `.flow/contradictions/` folder is the prototype of that protocol. **[ENGRAM: G — ground/trust; under-specified by Logan]**

**For the wider field:**

- **The framing wins.** Even if the implementation is hand-wavy ("upon request"), the *naming + checklist* gives the field a vocabulary. The same maneuver Karpathy did for "software 2.0" — invent a category boundary that forces classification.
- **A-MEM (Xu 2025) and Hindsight (Latimer 2025) are explicitly graded against CMA in the related work** — A-MEM satisfies retrieval-driven mutation via "memory evolution"; Hindsight satisfies consolidation via "reflect." Neither satisfies all six. This is the *use case* of the framework: it's a benchmark for taxonomy.

## How to Apply It (method)

If you want to **implement or audit** a CMA-class system, the operational decomposition (from Sec 3 + Appendix A) is:

1. **Pick a substrate that exposes relationships for activation to exploit** (graph, polyglot store with edges, learned attention over embeddings). Pure flat vector stores are excluded *by definition* — they can't carry FOLLOWED_BY edges or co-activation links.
2. **Build an ingest service that attaches metadata at write-time:** timestamps, session IDs, salience score (Logan derives this from sentiment analysis), temporal classifier label (episodic / habitual / timeless), and runs novelty detection (merge-similar-fragments rather than duplicate, strengthening reinforcement). Add a capacity manager that evicts low-salience, low-reinforcement nodes when storage is tight. **[ENGRAM: E + M — encode forces a maintenance discipline]**
3. **Layer an activation engine over the substrate.** Seed activation with top-k semantic matches from a query, then propagate along semantic + temporal + associative edges with damping. Log the activation trace.
4. **Build a multi-factor retrieval scorer.** Combine vector similarity, activation level, recency decay, structural reinforcement, and contextual relevance into a single scalar. *Semantic similarity is only one vote among many.* **[ENGRAM: R — recall composition]**
5. **Wire retrieval-induced mutation into the scorer.** Every returned node gets a reinforcement increment; every near-miss gets a suppression penalty. This is the single mechanic that makes the system not-RAG. **[ENGRAM: R × M — retrieval mutates store]**
6. **Run consolidation jobs as background workers.** Three jobs: (a) replay walks that strengthen temporal chains by traversing recent sequences, (b) abstraction via LLM-summarized clusters that link back to source fragments, (c) gist extraction that converts repeated episodes into surviving semantic knowledge. Dormant memories must remain recoverable under strong cues (preventing catastrophic forgetting). **[ENGRAM: A — aggregate; explicit two-phase write-time + offline]**
7. **Instrument heavily.** Structured logs per node: fragment ID, reinforcement delta, activation trace, provenance. Without this you can't debug drift or run probes.

To **evaluate** any candidate system, use Logan's four-probe battery as a baseline diagnostic:

- **Knowledge Updates (selective retention)** — 40 fact-then-correction scenarios across 8 domains. Look for d ≥ 1.0 on per-query score differences vs RAG. Permutation test (10k shuffles) for p<0.01.
- **Temporal Association (temporal continuity)** — 10 episode sets of semantically diverse but temporally-linked events; query with "what happened around X?" Look for Cohen's h ≥ 1.5.
- **Associative Recall (associative routing)** — 5 project knowledge graphs requiring multi-hop retrieval where the answer has no lexical overlap with the query.
- **Disambiguation (contextual partitioning)** — 8 ambiguous terms (Python, Apple, Java, Bug, Mercury, Jaguar, Shell, Trunk) in distinct contexts; system must not contaminate across contexts.

GPT-4o as judge, anonymized A/B with three randomized seeds for prompt order, McNemar's test on win/loss counts.

### Extended recipe — running a CMA-vs-RAG A/B on your own vault

**Scenario:** A two-person memory-architecture team runs Flow OS as a markdown-vault second brain: ~3,000 notes across `memory/`, `experiences/`, and `brain-health/`, retrieved via QMD (BM25 + `text-embedding-3-small` vectors) feeding an LLM agent. Over six months they have noticed the assistant keeps recommending a deprecated API version a customer migrated away from, can't answer "what else was going on around the Marcus Webb pilot kickoff?", and gets derailed when the user mentions "Python" (the venture context) vs. "Python" (a real snake spotted on a hike). They want to stand up a CMA prototype on the same corpus and A/B test it against their current RAG pipeline using GPT-4o as judge before committing engineering time to a full rebuild. Mapping to ENGRAM: this exercise stresses **Encode** (salience/temporal tagging at ingest), **Network** (associative + temporal edges), **Retrieve** (multi-factor scoring vs. cosine top-k), **Aggregate** (consolidation/gist jobs), and **Maintain** (selective retention, retrieval-driven mutation).

1. **Lock the baseline (RAG-with-recency)**: Freeze the current QMD pipeline as System A. Keep the same `text-embedding-3-small` embeddings and top-k retrieval, but add the paper's recency-weighted scoring on top so the baseline is a *fair* RAG, not a strawman.

   ```
   score(doc, q) = cosine(doc, q) * exp(-λ * Δt_days)
   # Suggested starting λ: 0.01 (half-life ~70 days). Tune on a small dev set
   # so baseline beats vanilla RAG on at least the Knowledge Updates probe —
   # this proves you're testing CMA vs. a strong RAG, not a weak one.
   ```

2. **Stand up System B (CMA instantiation)**: Build the four services from Appendix A on top of the same markdown vault. Don't replace QMD — wrap it. (a) **Ingest service**: derive salience (LLM call), classify temporal scope (episodic / habitual / timeless), and run a novelty check — if cosine to nearest existing node > 0.92, merge and increment reinforcement instead of duplicating. (b) **Activation engine**: SQLite + edges table with three types — `SEMANTIC` (cosine > threshold at ingest), `FOLLOWED_BY` (same session/day, consecutive), `ASSOCIATIVE` (co-retrieved ≥ 3 times). Seed activation from top-k vector hits, then propagate two hops with damping. (c) **Retrieval scorer** (multi-factor — see formula below). (d) **Consolidation jobs**: nightly cron that walks recent `FOLLOWED_BY` chains, clusters them, and writes an LLM-summarized "gist" node back into the vault under `memory/patterns/_gists/` linked to source fragments.

   ```
   final_score(node, q) =
       w1 * cosine(node, q)              # semantic similarity
     + w2 * activation(node)             # spread from seeds, damped per hop
     + w3 * exp(-λ * Δt_days)            # recency decay
     + w4 * log(1 + reinforcement)       # how often previously retrieved
     + w5 * context_match(node, session) # session/episode tag overlap
   # Start with w = [0.35, 0.25, 0.15, 0.15, 0.10], λ = 0.01.
   ```

3. **Build the four probe corpora on your own vault**: 40 Knowledge-Updates triples (initial-fact, correction, query) across 8 domains; 30 Temporal-Association "what was happening around X?" queries with gold-truth temporally-adjacent-but-semantically-different answers; 30 multi-hop Associative-Recall queries where the answer noun never appears in the query; 48 Disambiguation queries using 6–8 ambiguous tokens from your vault in clearly-different contexts.

4. **Run both systems through every query, identically**: For each of the 148 queries, capture an *evaluation packet* — the prompt sent, the retrieved memories with timestamps + metadata, the expected-information reference, the rubric for that probe. Three randomized seeds per query to control for judge position bias. Anonymize system identity from the judge.

5. **Score with GPT-4o-as-judge using the paper's anonymized A/B template.** The paper does not publish a verbatim judge prompt; this skeleton is a faithful reconstruction of the §5 protocol, not a quoted artifact.

   ```
   You are an expert evaluator scoring two retrieval systems on a memory task.

   QUERY: {query}
   EXPECTED INFORMATION: {ground_truth_reference}

   SYSTEM A RETRIEVED: {system_a_chunks_with_timestamps}
   SYSTEM A ANSWER: {system_a_answer}

   SYSTEM B RETRIEVED: {system_b_chunks_with_timestamps}
   SYSTEM B ANSWER: {system_b_answer}

   RUBRIC ({probe_name}):
   - accuracy (0-1): does the answer match expected information?
   - ordering (0-1): are temporally/structurally adjacent items returned together?
   - context_fidelity (0-1): does retrieval stay within the right context cluster
     and avoid contamination from unrelated meanings of ambiguous terms?

   Return JSON:
   {
     "system_a": {"accuracy": _, "ordering": _, "context_fidelity": _},
     "system_b": {"accuracy": _, "ordering": _, "context_fidelity": _},
     "verdict": "A_wins" | "B_wins" | "tie" | "both_wrong",
     "rationale": "<one-paragraph explanation citing specific retrieved items>"
   }
   ```

6. **Run statistical tests exactly as the paper does**: Cohen's d on continuous score differences; Cohen's h on win-rate proportions; two-sided permutation test (10,000 shuffles) on per-query score differences; McNemar's test on (A_wins, B_wins) discordant pairs. Target p < 0.01 per probe. Ignore "tie" and "both_wrong" verdicts in the win-rate computation — the paper reports decisive trials only (e.g., 14 of 19 decisive in Associative Recall; 14 of 16 in Temporal Association).

7. **Measure latency honestly**: Record p50/p95 wall-clock per query. The paper reports ~2.4× slowdown for CMA (1.48s vs 0.65s); if you see 10×, your activation propagation isn't damped or capped properly (§6 mitigation: cap activation fan-out per hop).

8. **Audit failure modes before declaring victory**: Sample 10% of System-B wins and inspect the judge rationale for plausibility (analog of the paper's "30 random spot-checks"). Probe the three named risks: (a) **memory drift** — query a known-stable fact 20× in a row; does its rank shift? If yes, dampen the reinforcement update; (b) **episode-boundary brittleness** — manually inspect Temporal-Association "both_wrong" cases and check whether your session/day boundary heuristic split a single continuous episode; (c) **interpretability** — verify the activation engine logs node IDs, reinforcement deltas, and which edges fired.

9. **Compile results in Table 1's format and write a go/no-go memo.** Decision rule: if CMA wins ≥ 2 of 4 probes with Cohen's effect size > 0.8 and p < 0.01, and latency overhead < 3×, ship behind a feature flag and route ENGRAM-Maintain-sensitive queries (updates, temporal) to CMA while keeping RAG for cheap factual lookups. Otherwise: diagnose which of the six CMA requirements is failing its probe and iterate only on that subsystem.

**Expected outcome:** A reproducible four-probe behavioral test suite anchored to your own vault, two side-by-side retrieval pipelines you can swap behind a flag, a Table-1-style results matrix with per-probe wins/effect-size/p-value plus latency, and a folder of GPT-4o judge rationales you can quote when arguing for or against the rebuild. Most importantly, a *structural* diagnosis: instead of "CMA is better" you'll know which ENGRAM stages your current stack is failing on, giving a prioritized engineering roadmap.

## What Experts Overlook

Three things that even careful memory-systems readers will miss on a first pass:

1. **The "Statistical Testing" paragraph is doing heavy lifting that nobody talks about.** Logan reports permutation tests (10k shuffles) on per-query score differences *and* McNemar's test on win/loss counts, both at p<0.01. This is unusually careful for an arXiv preprint, and it matters because GPT-4o-as-judge is notoriously noisy — the permutation test sidesteps any distributional assumption on the judge scores. Most memory-architecture papers report only win counts (or cherry-picked qualitative examples). Stealing this protocol is a free upgrade for any memory eval.

2. **"Corpora, prompts, and rubric templates are available upon request" + "withholding direct publication temporarily because several corpora contain user-like scenarios that require redaction"** is a polite way of saying *we used real user data, can't release it, and we know that hurts reproducibility*. The honest experimentalist's read: the eval is suggestive, not definitive, until someone reconstructs equivalent probes on a releasable corpus. Logan signals he knows this — Section 7 explicitly downgrades the work to "architectural framework with preliminary empirical signal rather than a definitive benchmark result." Treat the 82/92 number as **directional evidence of CMA-class advantage**, not as a SOTA claim. **[ENGRAM: G — provenance of the eval itself is partial]**

3. **The "high both-wrong rate (47%) on Temporal Association"** is buried in §5.2 and easy to miss because the headline (CMA wins 13/14 *decisive* trials) sounds dominant. The decisive denominator is 14 out of 30 temporal queries — meaning **on 47% of temporal queries, both systems failed**. The honest reading: even Logan's CMA cannot reliably do the temporal-chaining behavior cognitive science says memory needs. Episode segmentation, long-range chains, and boundary detection are still genuinely unsolved. This is the most actionable failure mode in the paper, and it's the one most likely to be ignored by readers who only read the abstract's "consistent advantages" framing. **[ENGRAM: A × N — episode segmentation is a network-shape decision that consolidation depends on; nobody has cracked it]**

4. **Retrieval-induced mutation is *two-sided* — winners reinforce AND near-misses are actively suppressed — and the suppression-on-miss arm is plausibly what does most of the Knowledge-Updates work, not recency.** The detail sits in Appendix A's Retrieval Scorer description ("increments reinforcement for returned nodes and **applies suppression penalties to near misses**, thereby implementing selective retention"). It's easy to read this as flavour, or as a nod to Anderson et al. 1994 on retrieval-induced forgetting. It's not flavour. The paper itself credits the *collective* dynamics of "recency, interference, and activation" in §5.1, and runs no ablation that isolates suppression. But here is the inference available to a careful reader: the RAG baseline *also* has recency-weighted scoring (§5: `e^−λΔt`), so recency alone cannot explain the d=1.84 gap. What CMA has that RAG doesn't is the suppression arm — every time the new fact gets retrieved, the old fact (a semantically near-identical near-miss) gets actively pushed down. After a handful of queries the superseded fact has been suppressed below the retrieval floor. Read this way, the most plausible load-bearing mechanism for selective retention is not that the new fact is fresher; it's that the old fact has been *taught to lose*. This collapses the gap between write-time and query-time synthesis: contradiction resolution is *emergent from retrieval pressure*, requiring no write-time reconciliation pass or LLM-as-judge over conflicting fragments. The same mechanism that gives you free contradiction handling is the one that produces the drift §6 warns about — a single bad retrieval (a popular query grabbing the wrong fragment) actively damages the correct memory. **Implication for our experiments:** turning off suppression-only while keeping reinforcement-on-hit would test whether the asymmetric update is what drives the result. The paper doesn't run that ablation; we should. **[ENGRAM: R × M — retrieval is *competitive* not just *positive* mutation; this is the single mechanic that makes CMA not-RAG]**

> You will see two anonymized system outputs, System A and System B, in response to a query. You have access to:

> 2. The retrieved memories each system surfaced, with timestamps and metadata
> 3. An "expected information" reference compiled from the ground-truth corpus
> 4. A rubric describing scoring criteria
>
> For each system, assign per-dimension scores on a 0-1 scale along: accuracy, ordering, context fidelity. Then issue a verdict (A wins / B wins / Tie / Both wrong) and provide textual justification.

**Selective-Retention probe pattern:** Inject an initial fact, then a contradicting correction, then query for the current information. (Example domains: API versions, schedules, preferences, debugging steps, configuration.)

**Temporal-Association probe pattern:** "What happened around [event X]?" — testing whether the system returns *temporally adjacent* events even when they are *semantically dissimilar*.

**Associative-Recall probe pattern:** Build a knowledge graph linking people → projects → technologies → milestones. Query for technologies-associated-with-a-person *without* mentioning specific technology names. Tests multi-hop retrieval through associative edges.

**Disambiguation probe pattern:** Embed an ambiguous term (Python, Apple, Java, Bug, Mercury, Jaguar, Shell, Trunk) in two distinct context clusters. Query in one context; system must not contaminate from the other context.
