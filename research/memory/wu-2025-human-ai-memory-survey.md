# From Human Memory to AI Memory: A Survey on Memory Mechanisms in the Era of LLMs

**Authors:** Yaxiong Wu, Sheng Liang, Chen Zhang, Yichao Wang, Yongyue Zhang, Huifeng Guo, Ruiming Tang, Yong Liu (Huawei Noah's Ark Lab)
**Published:** 2025-04 (arXiv v2, 23 Apr 2025) · [Source](https://arxiv.org/abs/2504.15965)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

Wu et al. (Huawei Noah's Ark Lab) survey memory in LLM-driven AI systems and argue the field has been mis-arguing about it by collapsing memory onto a single axis (short-term vs long-term). They propose a 3-dimensional / 8-quadrant (3D-8Q) taxonomy organised by **Object** (personal vs system), **Form** (non-parametric vs parametric) and **Time** (short-term vs long-term), then map ~130 systems into the eight cells — including ChatGPT Memory, Apple Intelligence, Microsoft Recall, mem0, MemoryScope, MemGPT, Letta, Cognee, HippoRAG / HippoRAG 2, MemoryBank, A-MEM, MemoryLLM, WISE, Titans, vLLM, StreamingLLM, H2O, ChunkKV and the LOCOMO / BABILong / MADial benchmarks. The survey is explicit that human memory provides the analogy ladder: sensory→working→episodic→semantic→procedural maps onto raw tokenisation→KV-cache/chat-history→retrieved user memory→pretrained parametric knowledge→fine-tuned skills. They flag six open problems framed as "from-X-to-Y" transitions — unimodal→multimodal, static→stream, specific→comprehensive, exclusive→shared, individual→collective privacy, rule-based→automated evolution — that collectively sketch the agenda for memory work in the next 1-3 years. The most useful takeaway for a memory architect: most of what your team calls "memory" lives in only 2-3 of these 8 cells, and the cells you ignore are usually where your hardest production failures originate.

## Key Takeaway

The dominant "short-term vs long-term" framing of LLM memory is the wrong axis to argue about. Once you split memory along three orthogonal axes — **what** is being remembered (Object: about the user vs about the system's own reasoning), **where** it lives (Form: in weights vs in external stores) and **how long** it persists (Time) — the field's "competing" approaches mostly stop competing and start tiling an 8-cell map. ChatGPT Memory, vLLM's PagedAttention, Reflexion's self-reflection traces, and HippoRAG's neuro-inspired knowledge graph are not rivals; they each occupy a different quadrant. The architectural sleight-of-hand is that **most production memory systems silently cover only 2 or 3 quadrants** and leave the others to whatever the LLM happens to do by default — and that's where the surprises come from.

## Implications

- **[E + N] Stop choosing "the" memory store — design six interacting decisions, not one**: The 3D-8Q matrix maps directly onto Encode and Network in ENGRAM. The paper's own discussion (§3.1.2 Construction) notes that key-value, graph and vector formats coexist in production systems because they're optimal for *different quadrants*. Audit your own stack against the 8 cells: any cell with no entry is a silent failure mode (e.g. no Quadrant-VI = no self-reflection layer = agent repeats yesterday's mistakes).
- **[A + M] Treat consolidation as a first-class lifecycle stage, not a cron job**: Section 3.1.2 explicitly maps four-stage personal-memory processing (construction → management → retrieval → usage) onto human consolidation/reconsolidation/reflection/forgetting. MemoryBank's adoption of the Ebbinghaus forgetting curve and A-MEM's Zettelkasten-inspired self-organising memory are concrete proof that maintenance logic (decay, merge, conflict resolution) sits *between* write and read — designing it as an afterthought is what causes drift.
- **[G] The survey is honest about what it doesn't address: provenance and trust**: There is no Ground dimension in the paper's taxonomy. Across all 8 quadrants and ~130 cited systems, none of the surveyed systems is praised for source-attribution or contradiction-surfacing. That silence is informative — if you're building a memory layer where trust matters (clinical, legal, financial), you can't crib the architecture from this survey; you have to add G yourself.
- **[E] Write-time vs query-time synthesis maps cleanly onto non-parametric vs parametric**: Non-parametric long-term memory (Quadrants II, VI) defers synthesis until query (cheap to write, expensive to retrieve, easy to audit). Parametric long-term memory (Quadrants IV, VIII — Character-LLM, MemoRAG, MemoryLLM, WISE, Titans) front-loads it via fine-tuning or knowledge editing (expensive to write, cheap to retrieve, opaque to audit). The paper notes parametric long-term personal memory has serious scalability issues — "the need to fine-tune models on individual user data... demands substantial computational resources" — which is your direct evidence for *why* most production systems keep personal memory non-parametric.
- **[N] Shape-of-memory is determined by what you query, not what you store**: §3.1.2 retrieval section is the architecturally clearest passage — ChatDB uses SQL queries because its memory is key-value; HippoRAG uses graph traversal because its memory is a knowledge graph; MemoryBank uses FAISS dense retrieval because its memory is vectors. The shape of the retrieval call dictates the shape of the store, not the other way around. If your agents mostly do entity-lookup, a vector store is the wrong default.
- **[A] Quadrant-VI is where compound learning actually happens — and most systems skip it**: Quadrant-VI (System × Non-Parametric × Long-Term) is "Reflection & Refinement" — Buffer of Thoughts distilling thought templates, Voyager's skill library, Reflexion's self-critique. This is the cell that turns experience into reusable patterns. The paper notes this is the only quadrant explicitly aligned with "self-evolution" of the agent. Most memory frameworks ship strong Quadrant-II (user memory) and weak Quadrant-VI (system reflection), which is why agents personalise but don't actually get smarter at the task.
- **[M] The six "from-X-to-Y" open problems are a maintenance roadmap, not a research wishlist**: Static→Stream, Specific→Comprehensive, and Rule-Based→Automated Evolution map directly onto Maintain in ENGRAM. The paper frames these as the open frontier; for an operator team, treat them as a maintenance backlog — every production memory system today is rule-based and specific; if you're not building toward automated, comprehensive, streaming maintenance, you're accumulating debt.
- **[G + M] Collective privacy is the under-discussed risk in shared memory**: The "From Individual Privacy to Collective Privacy" section flags an under-recognised failure mode: aggregating personal memories into group-level structures (e.g. a household memory layer, a team agent's shared notes) creates emergent leakage that individual consent frameworks can't catch. If your roadmap includes any shared / federated memory, this is a Ground problem (provenance + scope tracking) that needs design now, not later.

## How to Apply It (method)

**Scenario:** You are running a 3-person memory-architecture team for a venture-builder OS that captures session transcripts, extracts memories, runs hybrid (BM25 + vector + entity) retrieval, and serves them back to a Claude agent on each new session. The system has been running for ~6 months and is starting to show familiar symptoms: drift (the agent re-derives facts it "should" know), bloat (the index is growing faster than useful signal), and contradiction (two memories disagree and the agent picks whichever one ranked higher). You want a structured way to audit the architecture and find the actual bottleneck.

**Steps:**

1. **Inventory your stack against the 3D-8Q grid**. Build a 2×2×2 matrix on a whiteboard. For each of the 8 cells, write the *specific component* in your stack that owns it. Use the survey's Tables 2 and 3 as reference labels:

   ```
   Quadrant         Object   Form           Time         Owns in your stack?
   I    Working   Personal Non-parametric  Short        Chat history in current session
   II   Episodic  Personal Non-parametric  Long         /learn → QMD index
   III  Cache     Personal Parametric      Short        Prompt cache (Anthropic API)
   IV   Editing   Personal Parametric      Long         (none — no fine-tuned user model)
   V    R&P       System   Non-parametric  Short        Reasoning scratchpad / tool traces
   VI   Reflect   System   Non-parametric  Long         (gap — no skill library / lesson distillation)
   VII  KV mgmt   System   Parametric      Short        Provider-managed (you don't own it)
   VIII Param mem System   Parametric      Long         Provider-managed (pretraining only)
   ```

2. **Mark which quadrants you actively design vs delegate**. The survey's central point: every memory architecture has answers for all 8 cells, even if your answer is "the LLM provider does it". Highlight quadrants where you've written code (II, V) vs delegated by default (III, IV, VII, VIII). Delegated cells are fine — but you should be able to say *why* delegation is correct for each.

3. **For each gap, ask the four ENGRAM-aligned diagnostic questions**:
   - **E (Encode)**: What triggers a write here? Who decides what to capture?
   - **N (Network)**: What shape is the data — chunk, doc, table, graph, embedding?
   - **G (Ground)**: How do we know it's true? What's the provenance chain?
   - **A (Aggregate)**: Are we consolidating raw experience into patterns, or just stacking events?
   For Quadrant-VI (Reflection) the answers in most stacks are "nothing", "n/a", "n/a", "no". That's your highest-leverage gap.

4. **Build the reflection layer (Quadrant-VI) by lifting concrete recipes from the survey**. Three production-tested recipes:

   ```
   Buffer-of-Thoughts pattern: after each completed session, distil the
   reasoning trace into a 1-paragraph "thought template" tagged with
   problem-type. Store in a small (~few-hundred-entry) library keyed
   by problem-type embedding.
   
   Voyager skill-library pattern: after each task with a verifiable
   success signal, save the working playbook as a named skill with
   pre-conditions ("when X, do Y because Z"). Retrieve by similarity
   to current task description.
   
   Reflexion self-critique pattern: at session end, run a small model
   pass that asks "what would I do differently? what did I miss?" and
   stores the critique as a memory tagged self-reflection.
   ```

5. **Audit your Quadrant-II construction stage against the four-stage model** (construction → management → retrieval → usage). Most stacks under-invest in management: deduplication, merging, conflict resolution. Concrete check: pull 100 random memories from your store and ask Claude to flag duplicates or contradictions. If >10% are flagged, your write-time deduplication is the bottleneck, not your retriever.

6. **Pick one "from-X-to-Y" transition from §5 as your 6-month roadmap target**. For a session-based brain, "static → stream" (move from batch-extract-on-Stop to incremental update during the session) and "rule-based → automated evolution" (let the system propose new memory-type taxonomies rather than hand-coding them) are usually the highest-value picks. Don't try to do all six.

7. **Re-score every 90 days**. The 8-quadrant audit is a cheap, repeatable diagnostic — run it as a quarterly architectural review. New systems and benchmarks land in this space monthly (the paper cites Titans, M+, WISE, A-MEM, HippoRAG 2 all from late-2024/early-2025); a fresh audit will tell you which cells now have new state-of-the-art recipes worth lifting.

**Expected outcome:** You exit the audit with a labelled 8-cell map of your stack, an explicit list of gaps (typically Quadrants III/IV/VI), a prioritised set of recipes to fill the highest-leverage gap (usually VI), and a single roadmap-level transition from §5 to chase over the next two quarters. The audit itself takes ~2 hours and is the cheapest concrete diagnostic in the survey.

## What Experts Overlook

The non-obvious detail is that the **Form dimension (parametric ↔ non-parametric) is not symmetric in cost** — and the paper is one of the few that says so plainly. Most memory-architecture discussions treat the two as a designer's preference: "store it in the weights, or store it in a database". But §3.2.2 ("Personalized Knowledge Editing") quietly drops the actual constraint: personal parametric long-term memory (Quadrant-IV — fine-tuning per user via PEFT) "demands substantial computational resources [which] significantly hinders the scalability and practical deployment". Meanwhile §4.2.2 (system parametric long-term memory — Quadrant-VIII) is treated as a normal design space because *one* set of weights serves all users. The asymmetry is the reason production systems all converged on non-parametric personal memory + parametric system knowledge, even though no one writes that decision down explicitly. The paper makes the asymmetry legible by separating the Object dimension from the Form dimension.

**Why it matters:** Once you see this, "should we fine-tune for personalisation?" stops being a research question and becomes an economics question. The cost of Quadrant-IV scales O(users × edits), while Quadrant-VIII scales O(edits). A team that proposes per-user fine-tuning without crossing that asymmetry is proposing a system whose unit economics break at scale, regardless of how well it works in evals on 50 users.

**Example of good use:** A memory architect designing the second-brain system reads the 3D-8Q matrix, notices Quadrant-IV is empty in their stack, and *deliberately leaves it empty* — using prompt caching (Quadrant-III) for fast access to user history and non-parametric long-term memory (Quadrant-II) for personalisation, while reserving fine-tuning (parametric) strictly for shared/system knowledge (Quadrant-VIII, things like extracting domain-specific entities). The architect can defend this decision with the survey's cost asymmetry, not just intuition.

**Example of misapplication:** A team reads the same survey, gets excited about "AI-Native Memory / Lifelong Personal Models" (Quadrant-IV, ref [36]), and proposes shipping a per-user fine-tuned model as the personalisation strategy. They benchmark it on 100 users with promising results, then hit a wall at 10k users where the GPU cost of nightly per-user LoRA updates eats the gross margin. The misapplication wasn't choosing parametric — it was failing to see that the survey's taxonomy *already encodes* why nobody else has shipped this at scale.
