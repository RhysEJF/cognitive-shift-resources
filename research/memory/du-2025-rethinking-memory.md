# Rethinking Memory in LLM based Agents: Representations, Operations, and Emerging Topics

**Authors:** Yiming Du* (CUHK + Edinburgh), Wenyu Huang* (Edinburgh), Danna Zheng* (Edinburgh) — equal contribution; Zhaowei Wang (HKUST); Sebastien Montella (Huawei UK); Mirella Lapata (Edinburgh); Kam-Fai Wong (CUHK); Jeff Z. Pan (Edinburgh + Huawei UK)
**Published:** 2025-05 (v3 24 Dec 2025) · [Source](https://arxiv.org/abs/2505.00675) · [Code/Dataset/Tools](https://github.com/Elvin-Yiming-Du/Survey_Memory_in_AI)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

Du et al. (CUHK + Edinburgh + HKUST + Huawei, May–Dec 2025) deliver the long-needed *operational* survey of agent memory, distilling a curated corpus of **3,923 high-relevance papers** (filtered from 30,000+ at NeurIPS/ICLR/ICML/ACL/EMNLP/NAACL 2022–2025 via a GPT-4o-mini relevance pipeline with threshold ≥8/10, manually validated) into a clean two-axis framework. **Axis 1 (Representation):** Parametric Memory (weights) vs Contextual Memory {Unstructured: text, vectors, images, audio, video, KV-cache, memory buffers, retrieval DBs, episodic storage; Structured: knowledge graphs, relational tables, experiences, ontologies}. **Axis 2 (Six Operations, in three groups):** Memory Encoding {**Consolidation** M_{t+Δt} = Consolidate(M_t, E_{[t, t+Δt]}), **Indexing** I_t = Index(M_t, φ)}; Memory Evolving {**Updating** M_{t+Δt} = Update(M_t, K_{t+Δt}), **Forgetting** M_{t+Δt} = Forget(M_t, F)}; Memory Adapting {**Retrieval** Retrieve(M_t, Q) = {m_Q ∈ M_t : sim(Q,m_Q) ≥ τ}, **Condensation** M_t^{comp} = Compress(M_t, α)}. The taxonomy is overlaid with **functional types from cognitive psychology** (Episodic, Semantic, Procedural, Working) and a **temporal axis** (Long-term vs Short-term). Four high-impact research topics are mapped to operation-clusters: **Long-Term Memory** (temporal, multi-session; Contextual; emphasises encoding+evolving+adapting), **Long-Context Memory** (contextual & parametric; emphasises Compression + Retrieval — KV cache eviction H2O / StreamingLLM / SnapKV, context compression RECOMP / LLMLingua), **Parametric Memory Modification** (model-internal; covers Editing — ROME / MEMIT / AlphaEdit, Unlearning — DEPN / MemFlex, and Lifelong Learning — TaSL / Memento / ReasoningBank), and **Multi-Source Memory** (cross-textual integration — StructRAG / DelTA / ChatDB, multi-modal coordination — VISTA / IGSR / MMLongBench). The survey introduces the **Relative Citation Index (RCI)** — a log-log regression metric (R²=0.97) that age-normalises citation counts so 2025 papers can be fairly ranked alongside 2022 papers. Section 4 catalogues commercial products (ChatGPT, Claude, Grok, DeepSeek as parametric-dominant; Replika, Character.AI, Tencent ima.copilot, Doubao as contextual-personal; GitHub Copilot, Cursor, Coze, DeepResearcher as task-oriented; Siri / Doubao / Xiaoyi as multi-modal) with their memory limitations explicitly tabled. Section 5 compares human-vs-agent memory; Section 6 charts future directions (conflict-aware memory, self-maintaining architectures, multi-modal long-context). **Most useful takeaway:** the **six-operation taxonomy** (Consolidation / Indexing / Updating / Forgetting / Retrieval / Condensation) is the **shared vocabulary** the field has been missing — every existing system can now be characterised by *which operations it implements and how*, and every new system can be designed by *deciding what to do for each of the six*.

## Key Takeaway

Before this survey, agent-memory papers each invented their own vocabulary (MemGPT's "main context vs external context", Hindsight's "retain/recall/reflect", MIRIX's "Meta Memory Manager / Memory Manager", MemVerse's "slow LTM + fast parametric", Memory OS's "STM/MTM/LPM"). Each architecture looked unique because it was named uniquely. Du et al.'s contribution is showing they're all instances of the same six-operation framework: every memory system makes choices for **Consolidation** (how short-term experiences become persistent), **Indexing** (how memories are made retrievable), **Updating** (how existing memories absorb new knowledge), **Forgetting** (how memories are removed), **Retrieval** (how memories are accessed), and **Condensation** (how memories are compressed for inference). Once you have this vocabulary, comparison becomes possible — "Hindsight emphasises Consolidation (narrative facts) + Indexing (four typed networks) + opinion-style Updating; MIRIX emphasises Indexing (six components) + Active Retrieval; MemoryOS emphasises Indexing (segment-page) + heat-based Updating + Forgetting; MemVerse emphasises Consolidation (KG) + Condensation (parametric distillation)." Stated as a lesson: **memory architectures aren't competing — they're each filling in different cells of the same operation × representation matrix, and the field's progress depends on naming those cells consistently.**

## Implications

- **Adopt the six-operation taxonomy as the shared vocabulary for Flow OS's memory layer.** Every component of the memory stack (`/learn`, `/capture`, `qmd query`, the future MTM/LPM tiers from MemoryOS, the entity-resolution from Hindsight) is some combination of Consolidate/Index/Update/Forget/Retrieve/Condense. Tag each component explicitly: "`/learn` runs Consolidation + Indexing"; "`qmd recall` runs Retrieval"; "the nightly entity-summary regeneration is Condensation"; "the heat-based segment eviction is Forgetting." This makes architectural conversations precise — when a teammate asks "what does your memory layer do?" you can answer in six dimensions, not free text. `[E, N, A, R, M]`

- **The Consolidate/Index/Update/Forget/Retrieve/Condense split is sharper than the three-group "Encoding/Evolving/Adapting" cover.** The three-group cover (Encoding, Evolving, Adapting) is convenient for prose but loses the operational precision. The six operations are what map to actual code paths. Use the six in implementation discussions; use the three only in narrative overviews. `[E, N, A]`

- **The Parametric vs Contextual {Structured, Unstructured} representation split is orthogonal to type/tier splits.** Hindsight cuts by epistemic type; MemoryOS cuts by temporal tier; MemVerse cuts by speed; MIRIX cuts by functional role; Du et al. cut by *representation form*. A memory item can simultaneously be (a) Episodic (functional type), (b) Mid-Term (temporal tier), (c) Opinion (epistemic type), (d) Contextual-Unstructured-Text (representation). All four splits are valid and complementary — the v3 memory schema for Flow OS should index every memory cell on **all four** axes simultaneously. `[N]`

- **The retrieval-generation disconnect is a real bottleneck — high Recall@5 ≠ good F1.** §3.1.5 ("Discussion"): on 2Wiki and MemoryBank, state-of-the-art retrievers achieve Recall@5 > 90 but generation F1 lags by **>30 points**. The diagnosed causes: compact memory formats support generation better than verbose ones; longer temporal distance between memory and query degrades generation even with accurate retrieval; retrieving more items introduces noise that impairs decoding. **Lesson for Flow OS:** don't optimise QMD retrieval in isolation; co-design the retrieval AND the format of injected context (compact narrative summaries beat verbose chunks). `[R, A]`

- **Forgetting is dramatically underexplored.** §3.1 publication trend: "forgetting remains underexplored" in the literature relative to retrieval/consolidation/indexing. This is an opportunity space — most personal-second-brain systems hoard rather than forget. The paper distinguishes *passive decay* (cognitive psychology) from *active unlearning* (LLM agents, driven by safety / privacy / compliance — DEPN, MemFlex, WAGLE, NeuMuter for parametric; FLOW-RAG, MemoryBank for contextual). For Flow OS, implementing genuine forgetting (not just FIFO eviction) is a competitive differentiator — e.g. when a user explicitly requests "forget this conversation about X," the system should both delete contextual entries AND verify no parametric residue persists. `[M]`

- **Condensation ≠ Consolidation, and the distinction matters.** Consolidation = write-time transformation of short-term experiences into persistent memory (eq. 1, happens during memory construction). Condensation = inference-time reduction of retrieved memories to fit context (eq. 6, happens at query). Two different operations with different optimisation targets — Consolidation optimises for future retrievability + provenance; Condensation optimises for context-window efficiency + response quality. Many systems conflate them and write retrieval-side compression code that's identical to write-side summarisation, which causes both to underperform. For Flow OS: keep `/learn`'s summarisation (Consolidation) and `qmd recall`'s packing (Condensation) as separate functions with separate prompts. `[A]`

- **Indexing is doing more work than people credit.** §3.1.1 distinguishes three indexing paradigms: **graph-based** (HippoRAG — lightweight KGs mapping relational structure), **signal-enhanced** (LongMemEval — enriching keys with timestamps/summaries), and **timeline-based** (Theanine — temporal/causal chain organisation). Most current personal-AI systems just use vector indexing (HNSW), which captures only semantic similarity. Adding graph / timeline / signal indexing dramatically improves multi-hop and temporal retrieval — which §3.1.5 confirms is where generation F1 currently lags retrievers. `[R]`

- **The Relative Citation Index (RCI) is a useful methodological tool to borrow.** §1.1 introduces RCI: a log-log regression model fitting expected-citations against publication-age, with R²=0.97. Papers above the regression line are "punching above their weight" given their age; papers below are under-cited. This solves the survey-vs-survey citation-bias problem (newer papers haven't had time to accumulate citations). For Flow OS's own research-cycle skill: when ranking candidate papers for `/citation-walk --canonical`, use RCI rather than raw citation count to surface "hot but recent" papers that flat counts would miss. `[—]`

- **Personalization currently treats long-term memory as a passive buffer.** §3.1.4: "External Memory Augmentation personalizes responses by retrieving user-specific information from an external repository at inference time. ... these approaches scale well, they often treat long-term memory as a passive buffer, leaving its potential for proactive planning and decision-making largely untapped." This is the frontier — memory should *drive* what the agent does next (proactively raise relevant context, surface contradictions, plan based on prior decisions), not just be consulted on demand. For Flow OS, this maps to building a `/agenda` skill that *reads* memory and *proposes* actions, not just one that responds to user-initiated queries. `[R, M]`

- **The product-tools table (§4) is a deployment-architecture reference.** §4.1 Table 1 enumerates ChatGPT (parametric-dominant, Consolidation + Retrieval + Condensation, struggles with hallucination + limited personalization), Replika (contextual, Updating + Retrieval, struggles with privacy + memory drift + slot-based limits), GitHub Copilot (parametric, Condensation only, no cross-session continuity), Doubao (parametric, multi-modal, session-bound + hallucinations). §4.2 Table 2 enumerates tools: EasyEdit (parametric editing, ripple-effect risk + cost), Zep (temporal-KG construction, controllability+info-loss), Mem0 (personalized memory layer, lossy condensation), MemOS (hierarchical scheduling, control overhead + latency), Graphiti (graph construction, brittleness + high token cost). For Flow OS's positioning, this is the field map — Flow OS sits between Mem0 (personal memory layer) and MemOS (hierarchical scheduling) but distinguishes itself via **provenance discipline + multi-venture support + Claude-native integration**. `[—]`

- **Procedural memory is underexplored relative to Episodic and Semantic.** The functional-type taxonomy in §2.3 covers Episodic (events, dialogue histories), Semantic (concepts, KGs), Procedural (skills, task execution, tool use), and Working (control mechanism). The survey notes that Procedural memory is "formed in two ways: stored explicitly in external skill repositories for reuse, or encoded implicitly through large-scale training." For Flow OS, `.claude/commands/` is the explicit Procedural Memory layer — workflows the agent can re-execute. This is one of Flow OS's strongest assets and the survey validates that this layer is under-built in the field generally. `[N, E]`

- **Working Memory as a control layer, not a tier, is a useful reframe.** §2.3 reframes Working Memory not as "short-term storage" but as "a dynamic control mechanism that not only temporarily stores information but also actively manipulates and updates it." It "acts as the control layer for the agent context window, dynamically assembling the necessary inputs, including retrieved reasoning experience, tool outputs, and user data, to support complex reasoning, planning, and goal-directed behavior." For Flow OS, this is the right framing for the *Claude session context itself* — the working memory is the in-context assembly that combines retrieved chunks, the user's current query, the recent conversation, and tool outputs into a coherent reasoning substrate. Don't treat working memory as a tier; treat it as the assembly logic. `[N]`

## How to Apply It (method)

**Scenario:** Same Flow OS context. You've digested 49 papers including Hindsight, MIRIX, MemVerse, MemoryOS — each with its own taxonomy. Now you want a unifying schema that lets the v3 frontmatter capture **all four orthogonal splits** (representation, functional type, temporal tier, epistemic type) in a single memory file, so retrieval and analysis can filter on any axis. This survey provides the missing third axis (Representation: Parametric / Contextual {Structured, Unstructured}) and the operation vocabulary that lets you tag each component of the memory stack precisely. This maps to ENGRAM Encode (which representation does each memory live in), Network (which graph/index supports which retrieval), Aggregate (which Consolidation step produced this), Maintain (which Updating/Forgetting policy governs this).

**Steps:**

1. **Extend the v2 frontmatter schema with the four-axis tags.**

   ```yaml
   ---
   kind: <existing kind discriminator>
   representation: contextual-unstructured-text  # parametric | contextual-unstructured-{text,vector,image,audio,video,kv-cache} | contextual-structured-{kg,table,ontology,experience}
   functional_type: episodic                      # episodic | semantic | procedural | working
   temporal_tier: long-term                       # short-term | mid-term | long-term
   epistemic_type: experience                     # world | experience | opinion | observation
   ---
   ```
   
   Every existing memory file gets a one-time migration pass — `/learn --reindex` runs a classifier over all files and adds the four tags to frontmatter. The classifier uses the file's existing `kind:` + content as input.

2. **Tag every memory-layer component with the six operations it implements.** Maintain a `memory/ARCHITECTURE.md` table:

   ```
   | Component       | Consolidation | Indexing | Updating | Forgetting | Retrieval | Condensation |
   |-----------------|---------------|----------|----------|------------|-----------|--------------|
   | /learn          | yes (extracts)| yes (qmd)| yes (dedup)| no       | no        | no           |

## What Experts Overlook

Most readers will fixate on the six-operation taxonomy as the survey's contribution. The detail almost everyone will miss is in §1.1 (Research Methodology): **the survey's curated corpus of 3,923 papers was filtered from 30,000+ via a GPT-4o-mini relevance pipeline that scored each abstract on a 1–10 scale against taxonomy-aligned task definitions, with threshold ≥8 used to retain, manually validated on randomly sampled subsets.** This is a methodological contribution that's at least as important as the taxonomy itself: it operationalises **survey-construction-as-a-skill** — instead of a small expert team reading thousands of abstracts manually (the traditional survey methodology, which limits coverage and biases toward what the team already knows), they used an LLM-as-scorer with a clearly defined rubric, validated against expert annotation, and reproducibly released the corpus + scorer. The whole pipeline (corpus + GPT scoring prompts + RCI regression code + tools tables) is published at github.com/Elvin-Yiming-Du/Survey_Memory_in_AI.

**Why it matters:** Surveys age fast in fields moving as quickly as LLM memory. A traditional survey publishes a static snapshot of the literature as of its writing date and is partially obsolete within months. The Du et al. survey's methodology is *re-runnable*: pull the latest 30,000 papers from NeurIPS/ICLR/etc., re-run the GPT-4o-mini scorer with the same threshold, re-fit the RCI regression with the new citation data, and you have an updated survey snapshot. For Flow OS specifically, this means the survey isn't just a reference — it's a *recipe* for building a continuously-updated knowledge map of any rapidly-evolving research field. Implement the same pipeline against your own corpus (Flow OS's papers wiki currently at ~49 entries) and you get a self-updating taxonomy that grows as you digest more papers.

**Example of good use (memory architectures for agentic OSes):** Implementing the Flow OS retrofit, build a `/survey-refresh` skill that:
1. Pulls the latest papers from the four high-impact topics (Long-Term, Long-Context, Parametric Modification, Multi-Source) via Exa search on the topic queries the Du et al. survey defines
2. Runs each abstract through a GPT-5-Haiku scoring pipeline using the same threshold-≥8 rubric, with task definitions adapted from the survey's Table 4 (Appendix A)
3. Adds high-scoring papers to a `experiences/survey-refresh-<YYYY-MM-DD>/candidates.json` queue
4. Reruns the RCI regression including newly-added papers to refresh the impact ranking
5. Auto-digests the top-N RCI candidates via `/digest-paper`
6. Updates a `experiences/survey-refresh-<YYYY-MM-DD>/six-operation-coverage.md` matrix showing which operations Flow OS's wiki now covers in depth vs which are thin
7. Output a one-paragraph delta: "Since last refresh, the field has produced N new high-impact papers, M of which Flow OS wiki has digested; remaining gaps concentrate in Forgetting (under-investment field-wide) and Multi-Source Multi-Modal Coordination."

The result is a wiki that doesn't drift out of date — every refresh advances both the digest count AND the field-map of where coverage is strong vs thin.

**Example of misapplication:** A team adopts the survey's taxonomy but treats it as a *fixed* taxonomy — they label all their memory papers with the six operations and the three representation types, then never re-run the corpus filtering or RCI scoring as the field evolves. What breaks: within 6 months the field has produced new operation patterns the original taxonomy didn't anticipate (e.g. "Reflection" as a distinct operation between Updating and Consolidation, which several 2026 papers argue for); the original "Long-Context Memory" topic has bifurcated into "KV cache management" vs "context engineering for long agents"; new representation forms (sparse-feature circuits, mech-interp-derived memory) don't fit the original Parametric/Contextual split. The team's taxonomy becomes a Procrustean bed — they keep forcing new papers into old categories rather than evolving the categories. The lesson missed: **the methodology (re-runnable GPT-scorer + RCI regression + published corpus) is the contribution, not the static taxonomy.** Treat the taxonomy as a living artifact, re-run the pipeline quarterly, let the categories evolve.

For the abstract below, output a single integer relevance score from 1 to 10:
  10 = the paper is directly and centrally about the task
  8-9 = the paper is closely related and contributes meaningful methods or
        findings on the task
  6-7 = the paper is adjacent — the task is a motivation or secondary contribution
  4-5 = the paper is tangentially related — the task appears as context only
  1-3 = the paper is off-topic for the task

TARGET TASK: {task_name}
TASK DEFINITION: {task_definition_from_Table_4}
ABSTRACT: {paper_abstract}

```

**Prompt explanation:** Relative Citation Index (RCI) computation (§1.1) — a log-log regression that age-normalises citation counts. Conceptual recipe, not a prompt per se:

```
For each paper p in the curated corpus:
  age_p = current_year - publication_year_p + 1   (avoid log(0))
  raw_citations_p = paper.citation_count

Fit a log-log regression over the corpus:
  log(expected_citations) = β_0 + β_1 * log(age) + ε

Compute residuals:
  RCI_p = log(raw_citations_p) - (β_0 + β_1 * log(age_p))

  Papers with RCI > 0 are "punching above their weight" given their age
  Papers with RCI < 0 are under-cited
  Papers with |RCI| ≈ 0 are at the field's expected impact for their age

In the published survey, β_1 ≈ 0.97 (R²=0.97), meaning citations grow
approximately linearly in log-time over the 2022-2025 corpus.
```

**Prompt explanation:** Memory operation classifier (reconstructed from the six-operation framework in §2.4) — a prompt to classify which of the six operations a paper or system implements. This is what enables the Figure 2 hierarchical decomposition.

```
You are classifying which of six memory operations a research paper or
system implements. The six operations are:

1. CONSOLIDATION — transforming short-term experiences into persistent
   memory representations. M_{t+Δt} = Consolidate(M_t, E_{[t, t+Δt]})
   Examples: dialogue summarization, KG construction from text, fine-tuning
   on past data.

2. INDEXING — constructing auxiliary codes (entities, attributes, temporal
   tags) that serve as access points to stored memory. I_t = Index(M_t, φ)
   Examples: vector embedding, BM25 indexing, graph construction, timeline
   indexing.

3. UPDATING — modifying existing memory representations to incorporate new
   knowledge. M_{t+Δt} = Update(M_t, K_{t+Δt})
   Examples: knowledge editing, opinion confidence reinforcement, fact
   replacement, summarization-based refresh.

4. FORGETTING — selectively suppressing memory content. M_{t+Δt} = Forget(M_t, F)
   Examples: unlearning, time-based deletion, semantic filtering, FIFO eviction
   by frequency / recency / importance.

5. RETRIEVAL — accessing relevant information from memory in response to a
   query. Retrieve(M_t, Q) = {m_Q ∈ M_t : sim(Q, m_Q) ≥ τ}
   Examples: vector search, BM25, graph traversal, cross-encoder reranking.

6. CONDENSATION — reducing memory size at inference while retaining salience.
   M_t^{comp} = Compress(M_t, α)
   Examples: prompt compression (RECOMP, LLMLingua), KV cache eviction
   (H2O, StreamingLLM), context summarisation.

Given the paper/system description below, output the operations it
implements, with a 1-sentence justification per operation. Multiple
operations per paper are allowed.

PAPER/SYSTEM: {name + description}

OUTPUT:
{
  "consolidation": {"implements": true|false, "justification": "..."},
  "indexing": {"implements": ..., "justification": "..."},
  "updating": ...,
  "forgetting": ...,
  "retrieval": ...,
  "condensation": ...
}
```
