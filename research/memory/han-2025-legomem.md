# LEGOMem: Modular Procedural Memory for Multi-agent LLM Systems for Workflow Automation

**Authors:** Dongge Han, Camille Couturier, Daniel Madrigal Diaz, Xuchao Zhang, Victor Rühle, Saravan Rajmohan (Microsoft)
**Published:** 2025-10 · [Source](https://arxiv.org/abs/2510.04851)
**Lens:** `generic` · **Digested:** 2026-05-20

## TLDR

LEGOMem (Microsoft, to appear at AAMAS 2026) extends procedural memory from single-agent agents to multi-agent LLM systems built on the Magentic-One orchestrator-plus-task-agents pattern. Successful past task trajectories are distilled into two reusable memory types — full-task memories (high-level plan + reasoning trace) injected into the orchestrator, and subtask memories (per-agent tool-use traces) injected into each specialized agent — and stored in a FAISS vector bank indexed by OpenAI text-embedding-3-large. On the OfficeBench benchmark (300 office-automation tasks across Word/Excel/Email/Calendar/System/OCR-PDF agents, split 148 train / 152 test, success measured by exact/fuzzy match of the final environment state), the vanilla LEGOMem variant lifts overall success from 45.83% to 58.44% on a GPT-4o-only team (+12.61 pts), 35.31% to 48.03% on a GPT-4o-orchestrator + GPT-4o-mini-agents hybrid (+12.72), and 24.78% to 38.16% on an all-GPT-4o-mini team (+13.38), beating both prior procedural-memory baselines (Synapse and Agent Workflow Memory) — with the SLM-only memory team (38.16%) actually beating the no-memory hybrid (35.31%). Ablations are unusually clean: removing memory from the orchestrator drops performance far more than removing it from task agents, so orchestrator memory is the dominant lever; fine-grained subtask retrieval (Dynamic and QueryRewrite variants) helps only when orchestrator memory is absent or task agents are small. Execution becomes ~16% shorter (26.5 → 22.2 steps on Level-3 tasks) and per-step failure rate drops from 0.275 to 0.225. The useful takeaway: if you only have budget for one memory layer in your multi-agent system, put it on the planner, and you can downsize the workers.

## Key Takeaway

The counter-intuitive lesson is that in a multi-agent system, **the planner — not the doers — is where you most need memory**. Conventional intuition says you'd give each specialist agent its own procedural cookbook so it stops fumbling the tool calls it has already fumbled. LEGOMem's ablations flip that: the orchestrator-only memory variant beats the task-agent-only variant across every team configuration, and even when smaller language models are used as the doers, the biggest gains come from feeding the planner full prior trajectories so it decomposes and delegates better — not from teaching the doers new tricks. Translation for builders: skill memory for the workers is a complement, not a substitute, for plan memory at the top.

## Implications

- **Build planner-level memory before per-tool memory**: If you have a Magentic-One-style multi-agent setup, the single highest-leverage thing you can do is store and retrieve past successful end-to-end plans for the orchestrator. Per-agent skill libraries are a real but secondary lever — don't ship them first.
- **You can downgrade your workers if the planner has memory**: A team of GPT-4o-mini agents with LEGOMem (38.16%) beat a memory-less hybrid team using GPT-4o as orchestrator (35.31%) and matched a memory-less hybrid that had GPT-4o-mini as agents. Procedural memory is a cost lever — use it to push specialist roles down to cheaper/smaller models without losing accuracy.
- **Curate memory only from successful runs (for now)**: LEGOMem builds its bank from 148 training tasks, kept only the 93 that succeeded, and extracted 93 full-task + 250 subtask memories from those. The authors flag continual learning from *failed* trajectories as explicit future work — which means today, you should treat the memory bank as a success-only library and not poison it with failure traces.
- **Retrieval sophistication is overrated when planner memory is rich**: Vanilla LEGOMem (top-K nearest by task description) performs as well as Dynamic (per-subtask just-in-time retrieval) and QueryRewrite (LLM-rewritten subtask queries) in the full-memory setting. Skip the complexity unless your orchestrator memory is weak or your agents are small.
- **Don't pre-bake "reasoning" into stored memories**: Augmenting memory units with extra LLM-generated reasoning changed scores by less than two points in either direction — sometimes worse. The structured plan + subtask trace is already enough; don't burn tokens annotating it.
- **Procedural memory shrinks execution, not just lifts success**: Beyond raw task-success gains, LEGOMem cuts Level-3 task execution from 26.5 to 22.2 steps (-16.2%) and lowers per-step failure rate from 0.275 to 0.225. Faster runs + fewer botched tool calls means lower latency and lower cost per task, even before counting wins.
- **The architecture pattern is reusable beyond OfficeBench**: Two memory types (full-task at the orchestrator, subtask per agent), a FAISS index keyed on task descriptions, top-K = 5 for orchestrator + 3 per agent, three optional retrieval strategies. This is roughly 200 lines of plumbing on top of any orchestrator-and-tools framework (AutoGen, Magentic-One, LangGraph) and is the most actionable take.
- **Caveat: only office tasks, only 152 test cases, only one base team architecture**: All numbers come from the OfficeBench split. The framework is plausibly general, but no cross-benchmark evidence is provided. Be cautious about extrapolating the exact +12pt headline lift to your own workflow.

## How to Apply It (method)

**Scenario:** You're running a multi-agent customer-onboarding system: an orchestrator LLM that breaks down an incoming onboarding task into subtasks like "look up the company in CRM," "draft the welcome email," "schedule a kickoff meeting," "create the project folder in Drive," each handled by a specialist tool-using agent. After a few weeks of production traffic, you have hundreds of task logs but the agents still re-discover the same plans from scratch on every new customer. You want to turn those past logs into a reusable procedural memory.

**Steps:**

1. **Audit your current orchestrator + specialist split**: Confirm you have a clean Magentic-One-shaped architecture — one planner that does decomposition and delegation, N specialists each owning a tool surface (CRM, Gmail, Calendar, Drive…). If your stack is monolithic, LEGOMem doesn't add the modular value yet — first split into orchestrator + agents.

2. **Collect successful trajectories from production logs**: Filter your task logs to only fully-successful runs (the paper used 93 of 148 training tasks ≈ 63% success). For each, capture: the natural-language task description, the orchestrator's high-level plan, each subtask description delegated to which agent, the tool-use action stream that agent emitted, and the observations returned.

3. **Distill each log into a structured LEGOMem unit** using a curation LLM (GPT-4o works). Use this prompt template (Prompt 1 from the paper appendix):

   ```
   From the following agent trajectory, generate memory that can be useful for future LLM agents' reference.
   # Trajectory: {full_trajectory}
   # Example: { ...the paper's example JSON skeleton... }
   # Instructions: extract structured memory with clear thinking and well-formed actions. Use:
     <think>reasoning</think><action>structured_tool_call</action>
   # The memory object format:
   { "high_level_plan": "<numbered string of steps with which agent does what>",
     "subtasks": [ { "agent": "<exact agent name>",
                     "description": "<subtask given by orchestrator>",
                     "steps": "<think>…</think><action>…</action> pairs>",
                     "observations": "<concise summary of key results>" }, ... ],
     "final_answer": "<orchestrator's final response>",
     "reflections": "<what worked, what failed, root cause if any>" }
   # Rules: group related actions into subtasks; only include successful actions; remove function-call IDs; truncate repetitive runs; keep observations concise; don't include orchestrator coordination as subtasks.
   ```

4. **Decompose each unit into one full-task memory + N subtask memories**: The full-task memory keeps the whole structure (plan + subtasks + final answer + reflections) and is indexed by the embedding of the task description. The subtask memories are extracted per-agent and indexed by the embedding of their subtask description.

5. **Index everything in a vector DB**: Use OpenAI `text-embedding-3-large` (or any equivalent) and FAISS. Keep one global full-task index for the orchestrator and one per-agent subtask index for each specialist.

6. **At inference time, augment the planner first**: When a new task `d_new` arrives, embed it, retrieve the top-K = 5 full-task memories, and inject them into the orchestrator's prompt before it generates an initial plan. This is "vanilla LEGOMem" — the simplest and best-performing variant.

7. **Augment each specialist with its 3 most relevant subtask memories**: Either statically extract from the full-task memories you already retrieved (vanilla, cheapest), or query each agent's per-agent subtask index just-in-time when a subtask is delegated (LEGOMem-Dynamic, more precise but slower), or have an LLM rewrite the new task into a draft plan and use each draft-subtask to retrieve from the per-agent index up front (LEGOMem-QueryRewrite, the paper's most elaborate variant). Default to vanilla unless your orchestrator memory is weak.

8. **Wire in re-planning if execution stalls**: If the orchestrator detects looping or repeated states, retrieve memories again with the updated state and re-plan. The paper shows this matters more for harder (Level 3) tasks.

9. **Measure**: Track task-success rate, average steps per task, and per-step failure rate (the paper's three reported metrics). Compare against a no-memory baseline you've kept frozen. Expect roughly +12 absolute points on success and ~16% fewer execution steps on multi-app workflows if your setup mirrors theirs.

10. **Keep the memory bank growing — but only with successes**: New successful trajectories should be curated and added periodically. Do not yet add failed trajectories — the paper explicitly leaves continual learning from failure as future work, and there's no evidence yet that failure memories help (they may actively hurt).

**Expected outcome:** A production multi-agent system that gets faster and more accurate as it runs more tasks, with the orchestrator-level memory delivering most of the gain and a clear cost-saving lever (downsize specialist agents to smaller models without losing accuracy because they're now guided by prior successful executions). You'll also be able to point at concrete numbers — % task success delta, step count reduction, failure-rate reduction — to justify the architecture in postmortems.

## What Experts Overlook

The detail most experts skip is that LEGOMem's vanilla retrieval is keyed entirely on the **task description embedding** at the global level — there is no query expansion, no agent-side reranking, and the subtask memories handed to each specialist are simply the subtask blocks lifted out of the retrieved full-task memories, not independently retrieved. The Dynamic and QueryRewrite variants exist precisely to fix the cases where this naive coupling fails — when the retrieved full-task memories happen to have a different subtask structure from the new task, the vanilla path silently hands the wrong subtask trace to the wrong agent. The paper shows (Table 2, task-agent-only memory rows) that this matters: Dynamic and QueryRewrite beat vanilla by 4–5% when only agent memory is used. But in the full-memory setting, the orchestrator memory compensates for the mismatch by re-planning around bad subtask hints, and the variants converge. So the "all three perform similarly" headline hides a structural dependency: vanilla works because the orchestrator is doing implicit error correction over the noisy per-agent retrieval, not because the retrieval is actually good.

**Why it matters:** It tells you the system is more fragile than it looks. If you weaken the orchestrator — smaller model, less context, fewer top-K memories, or a domain where plans diverge wildly from task descriptions — vanilla LEGOMem's failure mode is "wrong subtask memory goes to the right agent" with no signal that it happened. The Dynamic variant exists for a reason and you should default to it the moment your orchestrator gets cheaper or your task space gets more diverse.

**Example of good use:** A platform team running a multi-agent code-review system across many repositories starts with vanilla LEGOMem (cheapest). They notice that for unusual languages (Rust, OCaml), the orchestrator retrieves Python-shaped full-task memories and the linter agent gets the wrong tool-call subtask. They switch to LEGOMem-Dynamic for the linter agent only — keeping vanilla for the others — and recover the gap without paying the full per-subtask retrieval cost everywhere.

**Example of misapplication:** A startup deploys vanilla LEGOMem with a GPT-4o-mini orchestrator to save cost, sees a 5pt drop vs the paper's reported numbers, and concludes "procedural memory doesn't work for us." What actually broke was the implicit error correction: the small orchestrator couldn't re-plan around mismatched subtask traces. They should have either kept the orchestrator on GPT-4o or switched to LEGOMem-Dynamic before downsizing.
