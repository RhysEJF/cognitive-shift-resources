# Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory

**Authors:** Prateek Chhikara, Dev Khant, Saket Aryan, Taranjeet Singh, Deshraj Yadav
**Published:** 2025-04 · [Source](https://arxiv.org/abs/2504.19413)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

Mem0 is a write-time-extraction memory architecture for multi-session LLM agents: every new user/assistant message pair is summarised by GPT-4o-mini into salient facts, then each fact is routed through a tool-call to one of four operations (ADD / UPDATE / DELETE / NOOP) against the top-10 vector-similar existing memories, producing a compact natural-language store of ~7k tokens per conversation. A graph variant (Mem0g) layers a Neo4j entity/relationship graph on top, doubling the footprint to ~14k tokens. On the LOCOMO benchmark (10 conversations × ~600 dialogues × ~26k tokens × ~200 questions each), Mem0 beats every memory-augmented baseline tested — LangMem, Zep, OpenAI ChatGPT memory, MemGPT, A-Mem, MemoryBank, ReadAgent — across single-hop (J=67.13), multi-hop (J=51.15), and temporal (J=55.51) questions, scoring 26% relative J-improvement over OpenAI's memory feature overall (66.88% vs 52.90%). The graph variant adds ~2 points overall (J=68.44) and dominates on temporal queries (J=58.13). Mem0 hits p50 search latency 0.148s and p95 0.200s — 91% lower p95 than the full-context baseline (17.1s p95) which is the only system to beat it on accuracy (J≈73%) at the cost of 26k tokens fed per query and 20× the token footprint of Zep's bloated graph (>600k tokens). Practical implication: dense LLM-distilled natural-language memories outperform both chunk-RAG (peaks at J=60.97 with 256-token chunks at k=2) and graph-heavy commercial systems on conversational recall, and graph structure only earns its keep on tasks that need explicit temporal ordering.

## Key Takeaway

Adding a knowledge graph on top of LLM-extracted memories barely moves accuracy (Mem0g beats Mem0 by ~2 percentage points overall) and actively hurts on multi-hop reasoning — but Zep's heavy commercial graph balloons to 600k+ tokens per conversation, 85× the cost of Mem0's flat natural-language store, and fails to retrieve recently-added memories until hours of background processing complete. The lesson: shape-of-memory should match the query, and "more structure" is not free — Mem0g pays a 2.4× latency tax and a 2× token tax for a graph that only justifies itself on temporal reasoning, the one place explicit relational edges actually help.

## Implications

- **Write-time extraction with an LLM tool-call beats retrieve-then-think for conversational recall** [ENGRAM: Encode + Aggregate]: Mem0's ADD/UPDATE/DELETE/NOOP classifier — implemented as a GPT-4o-mini function call against top-10 similar memories — delivers J=66.88% vs the best chunk-RAG variant at J=60.97%. The extraction LLM does the consolidation on the write path so query-time retrieval can be cheap and small. If your agent's memories are dialogues, do the distillation work when you write, not when you read.
- **Compact natural-language memories beat both graphs and chunks on token efficiency** [ENGRAM: Network]: Mem0 stores ~7k tokens per conversation in natural language; Mem0g doubles that to ~14k with graph relationships; Zep's design uses >600k tokens (20× the raw 26k conversation) because it caches abstractive summaries at every node and facts on every edge. Token cost compounds at scale — production deployments should default to flat NL memories and reach for graphs only when temporal reasoning matters.
- **Graph memory is a temporal-reasoning specialty, not a general upgrade** [ENGRAM: Network + Retrieve]: Mem0g beats Mem0 on temporal questions (J=58.13 vs 55.51) and open-domain (J=75.71 vs 72.93), but Mem0 wins on single-hop (67.13 vs 65.71) and multi-hop (51.15 vs 47.19). The relational edges help when chronology matters; they add overhead and indirection when the answer lives in one or two facts. Match retrieval-unit shape to query type.
- **Full-context is still the accuracy ceiling but priced out of production** [ENGRAM: Retrieve]: Feeding the entire 26k-token conversation to GPT-4o-mini achieves J≈72.90%, the highest score in the paper, but at p95 total latency 17.1s vs Mem0's 1.44s — a 91% gap. The architectural decision isn't accuracy-vs-latency; it's where on a Pareto frontier you can deploy. Mem0 sits much closer to the corner than anything else tested.
- **Lexical metrics lie on conversational QA — measure with LLM-as-a-Judge over 10 runs** [ENGRAM: Ground]: F1 and BLEU-1 reward token overlap even when the answer is factually wrong (the paper's example: "Alice was born in July" vs gold "March" scores high on F1). The authors run 10 independent J evaluations per method on the entire dataset and report mean ± 1σ — a benchmarking discipline worth copying for any memory system claim.
- **Selective top-k retrieval scales worse than memory abstraction as context grows** [ENGRAM: Retrieve + Aggregate]: Increasing RAG chunk size from 128 to 8192 tokens (k=2) blows total p95 latency from 1.83s to 9.94s while peaking accuracy at J=60.97 — Mem0 holds J=66.88 at p95 1.44s. The "just retrieve more chunks" reflex fails on long conversations; explicit memory consolidation is the architectural lever.
- **Async/background graph construction breaks real-time UX** [ENGRAM: Maintain]: The paper documents that Zep memories aren't immediately retrievable — "re-running identical searches after a delay of several hours yielded considerably better results" — because graph construction involves multiple async LLM calls. Mem0g completes graph build "in under a minute even in worst-case scenarios." If your memory system can't answer a question about something the user said 30 seconds ago, you've shipped a different product than they think they're using.
- **The ADD/UPDATE/DELETE/NOOP operation set is small enough to be a useful primitive elsewhere** [ENGRAM: Maintain + Aggregate]: Algorithm 1's four operations — gated on three predicates (SemanticallySimilar, Contradicts, Augments) — is a portable contract. Any memory system distilling on the write path needs a way to retire stale facts and merge complementary ones. Borrow the schema.

## How to Apply It (method)

**Scenario:** You're building the memory layer for a customer-support agent that handles repeated multi-session conversations with the same customers — they ask about orders, give feedback, mention life events, change preferences. The agent needs to recall facts ("you said you're vegetarian", "your last delivery was late"), reconcile contradictions ("I moved to Berlin in March" overriding "I live in Munich"), and answer temporal questions ("when did I switch plans?") — over months of intermittent chats — without re-reading the entire history.

**Steps:**

1. **Define the extraction context window**: For each new message pair `(m_{t-1}, m_t)`, build the extraction prompt `P = (S, {m_{t-m}, ..., m_{t-2}}, m_{t-1}, m_t)` where `S` is a running conversation summary and `m=10` is the recency buffer. The recency buffer catches details that haven't been consolidated into the summary yet.

2. **Run the asynchronous summary refresher**: A separate background process periodically regenerates `S` from the full conversation so the extraction step always has a fresh thematic anchor. Don't block the main extraction pipeline on summary regeneration.

3. **Extract salient facts with an LLM**: Call GPT-4o-mini (or equivalent) with `P` and ask for a structured list of candidate facts `Ω = {ω_1, ..., ω_n}`. Use the extraction prompt template from Appendix A. Each fact should be a self-contained natural-language sentence.

4. **For each candidate fact, retrieve the top-s vector-similar existing memories**: Use dense embeddings (the paper uses OpenAI's `text-embedding-small-3`) with `s=10`. Concatenate them with the candidate fact into a tool-call prompt.

5. **Invoke the four-operation tool call**: Let the LLM (GPT-4o-mini with function calling) select one of ADD / UPDATE / DELETE / NOOP based on this contract:
   - ADD if the fact is semantically new (no similar memory exists)
   - UPDATE if the fact augments an existing memory with richer information (and the new fact has higher information content than the existing one)
   - DELETE if the fact contradicts an existing memory
   - NOOP if the fact is already present or irrelevant

   ```
   For each fact f ∈ F:
       operation ← ClassifyOperation(f, M)
       if operation = ADD: M ← M ∪ {(id, f, "ADD")}
       elif operation = UPDATE and InformationContent(f) > InformationContent(m_i):
           M ← (M \ {m_i}) ∪ {(id_i, f, "UPDATE")}
       elif operation = DELETE: M ← M \ {m_i}
       elif operation = NOOP: pass
   ```

6. **(Optional) Layer a graph view for temporal queries**: Spin up a Neo4j instance. Run a two-stage extraction — an entity extractor produces typed nodes (Person/Location/Event/etc), then a relationship generator produces `(source, label, destination)` triplets. Compute embeddings for source and destination, search for existing nodes above similarity threshold `t`, and create-or-reuse before establishing the relationship. Mark obsolete relationships as invalid rather than deleting them (preserves temporal reasoning).

7. **At query time, retrieve via dual strategy**: For natural-language Mem0, vector-search the memory store. For the graph variant, run (a) entity-centric: identify entities in the query, find anchor nodes, traverse incoming/outgoing edges to build a subgraph; and (b) semantic-triplet: encode the whole query, score against each relationship triplet by similarity, return triplets above threshold ranked descending.

8. **Generate the final answer with the results-generation prompt** (verbatim from Appendix A — see Extracted Prompts section below).

9. **Evaluate with LLM-as-a-Judge on a held-out test set**: Use the Appendix A judge prompt with 10 independent runs per method per question. Report mean J ± 1σ. Stratify by question type: single-hop, multi-hop, temporal, open-domain. Watch for graph variants underperforming on multi-hop — the paper found this surprising and persistent.

**Expected outcome:** You ship a memory layer where common requests ("what's my address?", "what did I order last month?") return in under 200ms of search time, multi-session continuity holds for months without context bloat, and you can answer "Mem0 or Mem0g?" by looking at the temporal-question share of your traffic — if it's a small fraction, ship the flat variant and save the graph overhead.

## What Experts Overlook

The Mem0 system doesn't just "extract facts" — it gates writes through an LLM-driven tool call that picks between four operations (ADD / UPDATE / DELETE / NOOP) by comparing each candidate fact against the **top 10 most semantically similar** existing memories already in the store. This means every write is also a partial read: the LLM is asked to reason about the relationship between the new candidate and the closest existing neighbours, and can choose to retire a stale memory, merge complementary information into an existing one, or do nothing if the fact's already present. The pseudo-code in Algorithm 1 (Appendix B) makes this explicit, but it's easy to miss when skimming the architecture diagram — the diagram shows the operations as outputs of "update phase" without making clear that the operation choice is itself an LLM call against a retrieved similarity neighbourhood.

**Why it matters:** Most memory systems either (a) never delete or merge, and accumulate contradictions silently (early conversational-memory papers), or (b) use a separate classifier or heuristic for memory operations (cheaper but less semantically aware). Mem0's design says the LLM doing the extraction is *also* the LLM doing the lifecycle decision, and it gets to see the candidate plus the nearest 10 existing memories before deciding. That collocation is why the store stays at ~7k tokens per conversation — DELETEs and NOOPs are happening continuously on the write path, gated by an LLM that can recognise semantic conflicts that a rule-based deduper would miss. The graph variant (Mem0g) adds an analogous conflict-detection mechanism for relationships — when a new triplet arrives, an LLM-based resolver decides whether existing relationships should be marked obsolete (not physically removed — they're invalidated, preserving temporal reasoning).

**Example of good use:** A memory architect building a long-running customer-support agent treats every fact write as a 4-way classification problem against the top-K neighbours, using the same LLM that does extraction. They tune K (Mem0 uses 10) to balance the LLM's working-set size against operation accuracy, and they log the operation distribution as a health metric — a sudden spike in DELETEs after a UX change means users are correcting earlier facts, a spike in NOOPs means the agent's getting repetitive input. They also keep the resolver LLM colocated with the extractor in the same model family to avoid cross-model contradiction-detection drift.

**Example of misapplication:** A team builds a "Mem0-inspired" system but skips the operation gate — they extract facts on every turn and append-only into a vector store, hoping retrieval will sort it out. Six months in, the store is 10× larger than it should be, contradictions accumulate (user says they moved cities and the old address keeps surfacing alongside the new), and answer quality degrades because the LLM retrieves both facts and equivocates. Or worse: they use a small classifier model (not the extraction LLM) for the operation choice, miss the semantic conflict detection, and end up DELETE-ing memories that were actually complementary — losing user history. The paper's design specifically uses GPT-4o-mini for both extraction and operation choice; the architecture works because the same model sees the candidate, the neighbours, and the conversation context in one prompt.

## Extracted Prompts

**Prompt explanation:** LLM-as-a-Judge evaluation prompt — labels each generated answer CORRECT/WRONG against a gold answer, adapted from Packer et al. 2023. Used to compute the J metric across all baselines and the proposed Mem0 variants over 10 independent runs.

```
Your task is to label an answer to a question as "CORRECT" or "WRONG". You will be given
the following data: (1) a question (posed by one user to another user), (2) a 'gold'
(ground truth) answer, (3) a generated answer which you will score as CORRECT/WRONG.

The point of the question is to ask about something one user should know about the other
user based on their prior conversations. The gold answer will usually be a concise and
short answer that includes the referenced topic, for example:
Question: Do you remember what I got the last time I went to Hawaii?
Gold answer: A shell necklace
The generated answer might be much longer, but you should be generous with your grading
- as long as it touches on the same topic as the gold answer, it should be counted as
CORRECT.

For time related questions, the gold answer will be a specific date, month, year, etc. The
generated answer might be much longer or use relative time references (like 'last Tuesday'
or 'next month'), but you should be generous with your grading - as long as it refers to
the same date or time period as the gold answer, it should be counted as CORRECT. Even if
the format differs (e.g., 'May 7th' vs '7 May'), consider it CORRECT if it's the same date.

Now it's time for the real question:
Question: {question}
Gold answer: {gold_answer}
Generated answer: {generated_answer}

First, provide a short (one sentence) explanation of your reasoning, then finish with
CORRECT or WRONG. Do NOT include both CORRECT and WRONG in your response, or it will break
the evaluation script.

Just return the label CORRECT or WRONG in a json format with the key as "label".
```

**Prompt explanation:** Results-generation prompt for the base Mem0 system — instructs the LLM to use timestamped memories from both conversation speakers, resolve relative time references against memory timestamps, prioritise most-recent memory on contradiction, and produce an answer in under 6 words.

```
You are an intelligent memory assistant tasked with retrieving accurate information from
conversation memories.

# CONTEXT:

You have access to memories from two speakers in a conversation. These memories contain
timestamped information that may be relevant to answering the question.

# INSTRUCTIONS:

1. Carefully analyze all provided memories from both speakers
2. Pay special attention to the timestamps to determine the answer
3. If the question asks about a specific event or fact, look for direct evidence in the
memories
4. If the memories contain contradictory information, prioritize the most recent memory
5. If there is a question about time references (like "last year", "two months ago",
etc.), calculate the actual date based on the memory timestamp. For example, if a memory
from 4 May 2022 mentions "went to India last year," then the trip occurred in 2021.
6. Always convert relative time references to specific dates, months, or years. For
example, convert "last year" to "2022" or "two months ago" to "March 2023" based on the
memory timestamp. Ignore the reference while answering the question.
7. Focus only on the content of the memories from both speakers. Do not confuse character
names mentioned in memories with the actual users who created those memories.
8. The answer should be less than 5-6 words.
```
