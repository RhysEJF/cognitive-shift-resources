# A Survey on the Memory Mechanism of Large Language Model based Agents

**Authors:** Zeyu Zhang, Xiaohe Bo, Chen Ma, Rui Li, Xu Chen, Quanyu Dai, Jieming Zhu, Zhenhua Dong, Ji-Rong Wen
**Published:** 2024-04 · [Source](https://arxiv.org/abs/2404.13501)
**Lens:** `generic` · **Digested:** 2026-05-20

## TLDR

Zhang et al. deliver the first comprehensive survey dedicated to the memory mechanism of LLM-based agents, arguing that memory — not the LLM itself — is what makes "an agent truly an agent." They organise roughly 30 named memory-equipped systems (MemoryBank, RET-LLM, ChatDB, MemGPT, Reflexion, Generative Agents, Voyager, GITM, ExpeL, Synapse, Retroformer, Character-LLM, MAC, ChatDev, MetaGPT and more) along three orthogonal design axes: (1) memory sources — inside-trial (used by all 28 surveyed systems), cross-trial (only 7 of 28: Retroformer, ExpeL, Synapse, GITM, Reflexion, MetaGPT and a handful of others), and external knowledge (12 of 28); (2) memory forms — textual (dominant; subdivided into complete, recent, retrieved, and external-knowledge variants) vs. parametric (rare; subdivided into fine-tuning and knowledge-editing); and (3) memory operations — writing, management (merging, reflection, forgetting), and reading. They formalise the unified update rule `a_{t+1}^k = LLM{ R( P( M_{t-1}^k, W({a_t^k, o_t^k}) ), c_{t+1}^k ) }`, contrast Reflexion (R, P are identities; P only fires at trial-end) against Park et al.'s Generative Agents (R uses similarity + recency + importance; P uses reflection), and review evaluation in two flavours — direct (subjective: coherence/rationality; objective: result correctness, F1 reference accuracy, time/peak-GPU cost) and indirect (conversation, multi-source QA, long-context tasks, success-rate on AlfWorld/Minecraft). Across applications (role-playing, social simulation, personal assistants, open-world games like Minecraft, code generation, recommendation, medicine, finance, science), retrieved-textual memory is the default; parametric memory appears only in narrow fine-tuning settings (Character-LLM, Huatuo, InvestLM) and online-editing systems (MAC). Four future directions: more parametric-memory progress, multi-agent memory synchronisation, memory-based lifelong learning, and humanoid-agent memory with cognitively-faithful forgetting. The associated GitHub repo (`nuster1128/LLM_Agent_Memory_Survey`) is maintained as a living catalogue.

## Key Takeaway

Memory is what differentiates an agent from a vanilla LLM — and almost every memory module in production today is a textual retrieval index over inside-trial logs, leaving cross-trial reflection and parametric (in-weights) memory as the two largest under-explored frontiers. The paper's most useful contribution is the unified three-operation update equation `a_{t+1} = LLM{ R(P(M_{t-1}, W({a_t, o_t})), c_{t+1}) }`, which lets you describe any agent's memory design as a specific choice of W (writer), P (manager/reflector), and R (reader) — making it possible to compare otherwise apples-and-oranges systems like Reflexion, MemGPT and Generative Agents on a single axis.

## Implications

- **Audit your agent stack against the three-axis taxonomy before adding more prompts**: For any agent you're building or buying, ask three questions — what's the memory source (inside-trial, cross-trial, external), the form (textual or parametric), and which of the three operations (writing, management, reading) is the bottleneck. The survey shows most failures are management bugs (no reflection, no forgetting, no merging) masquerading as retrieval bugs.
- **If you only have inside-trial memory, you're doing the easy 80% — cross-trial is where compounding lives**: Out of 28 systems surveyed, only ~7 incorporate cross-trial information (Reflexion, Retroformer, ExpeL, Synapse, GITM, MetaGPT, and a couple of others). This is where agents learn from past failures across sessions. If your agent doesn't summarise lessons from completed runs into a reusable insights store, you're rebuilding the same context every trial.
- **Don't reach for fine-tuning when knowledge editing will do**: The survey distinguishes fine-tuning (offline, expensive, risks catastrophic forgetting) from knowledge editing (targeted, cheap, online-compatible — MEND, KnowledgeEditor, MAC). For correcting individual facts or updating preferences in production agents, editing is the right tool; SFT is for one-shot domain priming.
- **Long-context is not memory**: The "complete interactions" pattern (just concatenate the whole history into the prompt) is the naïve baseline, and the paper enumerates its three failure modes — quadratic attention cost, context-window overflow, and the "lost in the middle" effect (Liu et al. 2023). If your agent design rests on "we'll just give Claude 200K", you've conflated context with memory.
- **Use the W/P/R formalism to spec memory before code**: The unified equation lets you write a memory spec on a whiteboard before implementation — what does the writer extract, what does the manager do (merge / reflect / forget), what does the reader return. Many "memory" implementations in the wild have W and R but no P, which means the memory grows linearly and never gets compressed or reorganised.
- **For role-play and persona agents, memory consistency is the differentiator**: The paper's analysis of role-playing and social-simulation work (Character-LLM, ChatHaruhi, RoleLLM, Generative Agents, S3, MetaAgents, WarAgent) converges on a single insight: memory must be consistent with the role's profile, and it should influence subsequent actions to ensure behavioural consistency. Without that loop, the agent "steps out of character."
- **Build with the future direction in mind: humanoid agents need forgetting**: Section 8.4 makes a point most builders miss — humanoid agents should have knowledge boundaries and should forget like humans do. An LLM playing a child shouldn't recall advanced mathematics; this is a memory-management problem, not a prompting problem.
- **There is no open benchmark for memory modules — direct evaluation is still DIY**: The paper explicitly states "to our knowledge, there are no open-sourced benchmarks tailored for the memory modules in LLM-based agents." If you want to compare two memory designs head-to-head, you have to build your own subjective-rating or objective-QA setup. This is a market gap for tooling.

## How to Apply It (method)

**Scenario:** You're building an AI workforce manager (like Flow) that runs long-lived agents across multiple customer engagements. Each agent has to remember context within a single project session (e.g., "we decided to skip the Stripe integration in step 3"), retain lessons across past projects (e.g., "the last three times we batched integrations the client got overwhelmed"), and tap external knowledge bases (e.g., a customer's CRM, the Flow OS skills catalogue). You want a principled memory design rather than ad-hoc prompt-stuffing.

**Steps:**

1. **Map your agent's memory needs to the three sources**: List every piece of information your agent currently consumes. Classify each as (a) inside-trial (current session log), (b) cross-trial (lessons from past sessions for this same task type), or (c) external knowledge (CRM, docs, web). If column (b) is empty, you have no compounding — fix that first.

2. **Choose forms per source**: For inside-trial, textual (retrieval over recent + retrieved chunks) is almost always right. For cross-trial, textual summaries (à la Reflexion's verbal lessons) are the cheapest start; consider parametric only if the lessons need to be implicit (e.g., persona traits). For external knowledge, parametric fine-tuning is appropriate only when the knowledge is large, stable, and high-trust (e.g., medical domain — see Huatuo); otherwise use retrieval-augmented external textual memory.

3. **Implement the three operations as named functions** (`W`, `P`, `R`), even if W and R are thin wrappers around an embedding store. Force yourself to write P, the manager. P should do at least one of: merge similar memories, reflect to produce higher-level insights, or forget low-importance entries. Without P, memory grows monotonically and inference cost balloons.

   ```
   # Pseudo-spec following Zhang et al.'s formalism
   def W(action, observation):
       # extract: structured tuples? raw text? summary?
       return memory_entry
   def P(memory_store, new_entry):
       # merge dupes, reflect on patterns, forget stale
       return updated_store
   def R(memory_store, next_context):
       # similarity + recency + importance (Park et al. 2023)
       return top_k_relevant_memories
   ```

4. **Pick a memory writing strategy per the survey's named patterns**: For raw inside-trial logs, just store. For cross-trial, follow Reflexion — let the agent self-write a verbal lesson at trial-end (a one-paragraph "what I learned"). For relations between entities (people, decisions), follow TiM and store structured (entity, relation, entity) triples.

5. **Add a reading scorer that uses similarity + recency + importance (Park et al. 2023)**, not just cosine. Importance is an LLM-judged 1-10 score assigned at write time. Recency is exponential decay. Similarity is cosine over embeddings. Combine with learned or hand-tuned weights. Top-K (K=5-20) of this combined score becomes the retrieved memory for the next prompt.

6. **Add a forgetting / merging cycle** that fires asynchronously (e.g., end-of-session or end-of-day). Per MemoryBank: distil conversations into daily summaries; per Generative Agents: trigger reflection when accumulated importance exceeds a threshold; per APP: check that adding new memories doesn't perturb neighbouring memories. Without this, you're stuck with naïve concatenation forever.

7. **Evaluate memory directly, not just via downstream task accuracy**: The survey's Section 6 lays out direct metrics — Result Correctness on a memory-dependent QA set you build yourself (e.g., "What did we decide in session 4?"), and F1 Reference Accuracy (does the retrieved memory match the gold reference?). Measure both, separately from end-to-end task success, so you can attribute failures.

8. **For the parametric-memory frontier**, prototype with knowledge editing (MEND, MAC) before SFT. Editing lets you correct individual facts (e.g., "Alice no longer watches movies at 9pm") without retraining. Reserve SFT for stable domain corpora that change slowly (e.g., your company's positioning doc).

**Expected outcome:** A memory module you can describe in 3-5 sentences along the survey's W/P/R axes, with explicit forgetting and reflection cycles. Compared with a naïve "stuff context into prompt" baseline, you should see latency drop (smaller prompts) and cross-session intelligence rise (lessons compound). You'll also have a direct evaluation harness for memory quality, which decouples memory regressions from prompt regressions.

## What Experts Overlook

The detail most readers will miss is Section 3.4's *unified update equation*: `a_{t+1}^k = LLM{ R( P( M_{t-1}^k, W({a_t^k, o_t^k}) ), c_{t+1}^k ) }`. This is treated almost as throwaway notation in the paper, but it is the survey's load-bearing insight. It says: every agent's memory module — no matter how exotic — can be decomposed into a writer W, a manager P, and a reader R, composed in a specific order. The remark immediately afterwards is even more revealing: in Reflexion, R and P are *identity functions* and P fires only at trial-end; in Park et al.'s Generative Agents, P is a full reflection pipeline and R combines similarity + time-interval + importance. That single contrast tells you why Reflexion is good at single-task improvement but bad at lifelong simulation, and why Generative Agents are the opposite. Most surveys would just list the systems; this paper gives you the algebra to derive their differences.

**Why it matters:** Without the W/P/R algebra, "memory" in LLM-agent discourse is a catch-all that smuggles in different design decisions under a single word. With it, you can ask sharp questions: Does this agent have a non-trivial P? Is its R purely similarity-based, or does it weight recency and importance? Does W extract structure (TiM-style triples) or just dump raw text (MemGPT-style)? The algebra turns memory design into a 3-dimensional design space you can grid-search instead of a buzzword.

**Example of good use:** A team building a customer-support agent uses the W/P/R lens to spec their memory: W extracts (issue, resolution, sentiment) triples from each ticket; P fires nightly to merge similar issues and reflect on top failure patterns; R combines cosine similarity, ticket recency, and an LLM-scored "issue importance" to surface the top 5 prior tickets when a new ticket arrives. Six weeks in, they can swap any of W, P, or R independently and measure the lift — which they couldn't have done if "memory" were a single monolithic component.

**Example of misapplication:** A team builds an "advanced memory" feature that's actually just retrieval-over-chat-history (W = dump raw text, P = no-op, R = cosine similarity). They call it Reflexion-style memory because they read the Reflexion abstract. Months later they wonder why their agent never compounds wisdom across sessions. The answer is in Zhang et al.'s remark: Reflexion's distinctive feature is that P (the verbal-reinforcement reflection step) runs at the end of each trial. Without P, you have retrieval, not Reflexion. The misapplication is name-checking a system without implementing its actual contribution.
