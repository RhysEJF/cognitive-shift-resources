# Evaluating Very Long-Term Conversational Memory of LLM Agents

**Authors:** Adyasha Maharana, Dong-Ho Lee, Sergey Tulyakov, Mohit Bansal, Francesco Barbieri, Yuwei Fang
**Published:** 2024-02 · [Source](https://arxiv.org/abs/2402.17753)
**Lens:** `memory-architect` · **Digested:** 2026-05-19

## TLDR

LoCoMo is a 50-conversation benchmark built by Snap/UNC/USC where two persona-grounded LLM agents — each running Park-style generative-agent architecture with reflect/respond plus image sharing, anchored to causally-linked temporal event graphs — chat across up to 35 sessions, averaging 304.9 turns and 9,209 tokens per conversation (roughly 9× MSC and 6× more turns than Conversation Chronicles). Every dialogue is then hand-edited by annotators who fixed ~15% of turns and replaced ~19% of images. The benchmark stresses memory three ways: 7,512 QA pairs across five reasoning categories (single-hop 36%, multi-hop 14.6%, temporal 20.6%, open-domain 3.9%, adversarial 24.9%), an event-graph summarization task scored with FactScore, and a multimodal-dialog generation task scored with MM-Relevance. Headline numbers: humans hit 87.9% overall F1 on QA, GPT-3.5-turbo-16K tops the LLM field at 37.8% (gain of ~22-66% over short-context base models, but still 56% below humans, 73% below on temporal questions). Long-context models hallucinate badly on adversarial questions — GPT-3.5-turbo-16K drops to 2.1% versus 70.2% for GPT-4 at 4K. RAG with the dialog stored as DRAGON-retrievable "observations" (LLM-distilled assertions about each speaker) is the most robust setup, but performance peaks at top-5 observations and degrades with more — the lesson is signal-to-noise, not coverage. The single most useful artifact for memory-architecture work: a 9K-token, 35-session, human-verified test bench that exposes long-context LLMs' temporal-reasoning and speaker-attribution failures in measurable ways.

## Key Takeaway

Long context is not memory — and write-time distillation matters more than retrieval volume. The paper's most counter-intuitive finding sits in the adversarial column of Table 2: as you extend GPT-3.5-turbo's context window from 4K to 16K, single-hop accuracy nearly doubles (31.7 → 56.4) but adversarial accuracy collapses from 13.1 to 2.1 — a model with more context becomes more confidently wrong about questions it should refuse. GPT-4 at 4K scores 70.2 on adversarial questions; expand the window and the gain disappears. Meanwhile, the best RAG configuration is observations-as-retrieval-unit at top-5 — adding more retrieved observations (top-10, top-25) drops F1, because noise overwhelms signal. The architectural lesson: shape and SNR of the retrieved unit beats raw context length. (ENGRAM tags: **E** — write-time distillation into "observations" is the highest-leverage encoding choice; **R** — retrieval unit and k are first-class design knobs; **G** — adversarial accuracy is the cleanest groundedness probe in the benchmark.)

## Implications

- **Use LoCoMo as your temporal-reasoning regression test** (ENGRAM: **R**, **A**): Temporal questions are where every model studied lags humans most — 73% gap even for the best long-context configuration. If your memory system claims temporal reasoning, you should be reporting F1 on the 1,547 temporal-reasoning questions in this dataset; anything else is hand-waving.
- **Don't trust adversarial accuracy as a free lunch from longer context** (ENGRAM: **G**): GPT-3.5-turbo-16K's adversarial F1 of 2.1% (versus 70.2% for GPT-4 at 4K) shows long-context models become more willing to fabricate when given more text. Always run adversarial-question evaluations alongside positive QA; the metrics move in opposite directions.
- **Make "observations" (LLM-distilled assertions) the default retrieval unit, not raw turns** (ENGRAM: **E**, **N**, **R**): The paper's RAG ablation (Table 3) shows observations beat raw dialog and session summaries at every k. Observations achieve overall F1 41.4 at top-5 versus 31.7 for dialog turns at top-5 — and observations *peak* at top-5, while dialog turns need top-25 to reach 35.8. Smaller, structured retrievable units win.
- **Top-k is a tunable architecture parameter, and more is not better** (ENGRAM: **R**, **A**): For observations the curve is non-monotonic — F1 drops from 41.4 → 38.8 → 38.0 → 37.8 as k goes from 5 → 10 → 25 → 50. The authors explicitly attribute this to signal-to-noise. Treat top-k as a first-class hyperparameter and search it; the default in most RAG stacks (top-10 or top-20) is probably wrong for distilled memory units.
- **Session-level summaries are a tempting but lossy compression** (ENGRAM: **A**): Summary-based RAG hits very high recall@k (top-10 → 90.7% overall recall) but answer F1 stays low (31.5). The summarization step destroys grounded facts the QA task needs — high retrieval recall masks low usable-content recall. If you compress memory via summaries, you must validate downstream task accuracy, not just retrieval metrics.
- **Speaker attribution is a distinct failure mode worth instrumenting** (ENGRAM: **G**): The Section 6.2 error taxonomy (Table 7) calls out misassignment of dialogs/events to the wrong speaker as one of five recurring error types — and long-context models are "especially prone" to it. Add an explicit speaker-attribution evaluation to any multi-agent memory system; F1-on-correct-content is not enough.
- **Hybrid human-machine data generation is a practical answer to long-conversation cold start** (ENGRAM: **E**, **G**): The pipeline generates conversations with two LLM agents conditioned on personas + causal event graphs, then has annotators fix ~15% of turns and substitute ~19% of images. This is a usable template for any team trying to build evaluation data for memory systems where months-long real conversations are infeasible to collect. Code is at snap-research.github.io/locomo.
- **Image content can usually be replaced by BLIP-2 captions without losing evaluation signal** (ENGRAM: **E**): The authors note that multimodal coreference resolution can be handled by swapping images for BLIP-2 captions and letting text-only LLMs reason over the resulting interleaved transcript — except where OCR is required. For most memory-architecture research, you can ignore the multimodal axis without compromising the QA and summarization benchmarks.

## How to Apply It (method)

**Scenario:** You're testing your team's agentic memory system (Flow OS-style: markdown vault + QMD hybrid search + write-time `/learn` extraction into atomic memories) on whether it can sustain coherent context across months of paraglider trip planning, gear-change decisions, and rolling logistics — the kind of "very long-term" conversational arc real Flow users will actually generate. You want a numeric scorecard for temporal reasoning, multi-hop synthesis across sessions, and resistance to fabricated answers, plus a clean way to A/B different retrieval-unit shapes (raw turns vs. distilled atomic memories vs. session summaries).

**Steps:**

1. **Clone the LoCoMo dataset**: Download from `snap-research.github.io/locomo` (CC BY-NC 4.0). You get 50 conversations averaging 19.3 sessions and 9,209 tokens each, 7,512 annotated QA pairs across five categories, and ground-truth event graphs for summarization scoring.

2. **Bucket questions by reasoning type and report F1 per bucket**: The 7,512 QA pairs split into single-hop (36%), multi-hop (14.6%), temporal (20.6%), open-domain (3.9%), adversarial (24.9%). Always report all five — a single overall number hides the temporal-reasoning gap that's the actual research signal. Score with token-level F1 partial match on the answer (the paper uses this because LLMs paraphrase and exact match is too strict).

3. **Run three baselines for context**:
   - **Base**: short-context model (e.g., Llama-2-Chat or GPT-3.5-turbo at 4K) with truncated history.
   - **Long-context**: same model family at 16K (the paper used `gpt-3.5-turbo-16k`).
   - **RAG (observations)**: extract per-speaker assertions from each session using the prompt below, store with turn-ID provenance, retrieve top-5 with DRAGON (or your hybrid search), answer with a 16K-window reader. This is the configuration that wins in the paper.

4. **Use the paper's observation-extraction prompt as your write-time distillation step** (the load-bearing piece — this is what makes RAG work):

   ```
   Write a concise and short list of all possible OBSERVATIONS about
   each speaker that can be gathered from the CONVERSATION. Each
   observation should contain a piece of information about the speaker.
   The OBSERVATIONS should be objective factual information about the
   speaker that can be used as a database about them. Avoid abstract
   observations about the dynamics between the two speakers such as
   'speaker is supportive', 'speaker appreciates' etc. Do not leave out
   any information from the CONVERSATION.
   ```

   Tag each observation with the source turn IDs so retrieval results carry provenance back to the original dialog — this is what makes the system auditable downstream.

5. **Sweep top-k for each retrieval-unit shape** (this is the single most informative experiment): Plot F1 vs. k for dialog-turn retrieval, observation retrieval, and summary retrieval. Expect observations to peak at k=5 and decline; dialog turns to peak around k=25; summaries to plateau low. If your curves don't look like this, your retriever or your unit-design is the bug.

6. **Run the adversarial bucket as a hallucination guard**: Adversarial questions are the cleanest single-number test of "does context length make my model more confidently wrong?" — if extending context tanks adversarial F1, you have a groundedness problem that no amount of long-context fine-tuning will fix.

7. **Score event-graph summarization with FactScore, not ROUGE**: Decompose both ground-truth events and your model's summary into atomic facts; compute precision (fraction of model facts that match ground-truth) and recall (fraction of ground-truth facts present in the model output). Report F1. The paper shows GPT-3.5-turbo-16K is worse than the 4K base model here (39.9 vs 45.9 F1) — a clean reminder that longer context ≠ better grasp of causal structure.

8. **Inspect failures using the paper's five-category error taxonomy**: For any failing summary, classify the error as (1) missing information from cross-session causal/temporal failure, (2) hallucinated detail from a different event, (3) misread humor/sarcasm, (4) misassigned speaker, or (5) saliency mistake (trivial small-talk treated as an event). Tracking which bucket your system fails in tells you which ENGRAM dimension to invest in next.

**Expected outcome:** A scorecard for your memory system that lets you say something defensible like "our atomic-memory-extraction beats raw-turn RAG by X points on multi-hop F1 at top-5, matches GPT-3.5-turbo-16K on single-hop, and avoids the 2.1% adversarial collapse seen in pure long-context approaches." You'll also see exactly where your system breaks (temporal reasoning, speaker attribution, summary lossiness) — the kind of error-typed feedback that drives architectural decisions, not just leaderboard placement.

## What Experts Overlook

The single most overlooked operational detail is that LoCoMo's RAG-observation pipeline annotates each generated observation with the **source turn IDs in the original conversation** — and the model that produces observations is explicitly instructed to indicate which turn IDs contributed to each observation (Appendix A.2.1, around the Fig. 9 prompt). This is mentioned briefly in the appendix and not in the main results, but it's the architectural choice that lets the entire RAG-with-observations setup remain *auditable* — when a downstream answer cites an observation, you can recover the exact turns the assertion was built from. Without this, the win that observations show over raw turns would be untraceable and effectively unusable in any setting where you care about provenance (legal, medical, anything with a regulator).

**Why it matters:** Most teams reading this paper will copy the "extract observations, retrieve top-5, win on F1" headline and skip the provenance-linkage step because it's buried in an appendix. But the entire ENGRAM **G** (Ground) dimension lives in that turn-ID annotation. Without it, your memory system has compressed evidence into assertions you can no longer verify against source — and the next bug you cannot reproduce will be in exactly this layer.

**Example of good use:** A Flow OS memory pipeline that extracts atomic memories (`/learn` style) attaches each memory's YAML frontmatter to a stable conversation-event ID + the specific transcript line ranges that produced it (the v2 memory schema already has slots for this). When a user later asks "where did we decide X?" and the retriever returns an observation, the UI can pop the source turns inline. Adversarial-question accuracy stays high because the model can verify its claim against the actual evidence at answer time.

**Example of misapplication:** A team builds a Mem0-style flat assertion store, ships it to production, and a customer asks "why did your agent tell me I'm allergic to penicillin?" — and the team can no longer reconstruct which past chat turn the assertion was extracted from. The Mem0-style store had high F1 in their LoCoMo internal benchmark, but their version stripped the source-turn-ID annotation as a "memory bloat" optimization. The system now hallucinates confidently, and there is no provenance trail to debug it.

## Extracted Prompts

**Prompt explanation:** Persona generation — expands a short MSC-dataset attribute list (4-5 sentences) into a fully-fleshed persona statement used to condition each virtual agent. Fig. 5 in the paper.

```
Let's write speaker descriptions from a given set of life attributes. Add crucial details in the persona about the person such as their name, age, marital status, gender, job etc. Add additional details like names of family/friends or specific activities, likes and dislikes, experiences when appropriate.
```

**Prompt explanation:** Temporal event graph — base prompt describing the JSON event-graph structure (nodes = events with `event`/`date`/`caused_by`/`id`; edges = causal links to prior events). Used in combination with the initialization and iterative-generation prompts below. Fig. 6.

```
Let's write a graph representing events that occur in a person's life based on a short summary of their personality. Nodes represent events and edges represent the influence of past sub-events on a current event.
- The graph is represented in the form of a json list.
- Each entry is a dictionary containing the following keys: "event", "date", "caused_by", "id".
- The "event" field contains a short description of the event.
- The "date" field contains a date.
- The "id" field contains a unique identifier for the event.
- The "caused_by" field represents edges and is a list of "id" of existing events that have caused this event.
Events in the "caused_by" field should occur on dates before the event they have caused. Generate as many causal connections as possible.
- An example of a causal effect is when the event "started a vegetable garden" causes "harvested tomatoes".
- Events can be positive or negative life events.
```

**Prompt explanation:** Event graph initialization — used to seed the first three independent events for a persona. Fig. 6.

```
For the following input personality, generate three independent events E1, E2 and E3 aligned with their personality. Events can be positive or negative life events and should reflect evolution in the person's relationships, state of mind, personality etc.
```

**Prompt explanation:** Event graph iterative expansion — generates new events causally connected to existing events in the graph. Fig. 6.

```
For the following input personality, generate new events that are caused by one or more EXISTING events. Events can be positive or negative life events and should reflect evolution in the person's relationships, state of mind, personality etc. Do not repeat existing sub-events. Start and end your answer with a square bracket.
```

**Prompt explanation:** Session summarization — produces the short-term-memory summary `w_k` for session k, conditioned on the previous summary `w_{k-1}` and the current session's dialog. Fig. 8.

```
In previous interactions, {previous_summary}. The current time and date are {current_date_and_time}. {speaker_1_name} and {speaker_2_name} talked today and had the following conversation: {session} Summarize the interactions between {speaker_1_name} and {speaker_2_name} so far. Include key details about both speakers and include time references wherever possible.
```

**Prompt explanation:** Observation extraction — converts a conversation into a per-speaker list of factual observations stored in long-term memory `H_l`. This is the load-bearing write-time distillation step for the winning RAG configuration. Fig. 9.

```
Write a concise and short list of all possible OBSERVATIONS about each speaker that can be gathered from the CONVERSATION. Each observation should contain a piece of information about the speaker. The OBSERVATIONS should be objective factual information about the speaker that can be used as a database about them. Avoid abstract observations about the dynamics between the two speakers such as 'speaker is supportive', 'speaker appreciates' etc. Do not leave out any information from the CONVERSATION.
```

**Prompt explanation:** Image search query generation — converts a generated image caption into search keywords for the web image crawler (icrawler), stripping out names/years/irrelevant details. Fig. 10 (top).

```
Let's write short image search queries from textual descriptions of photos shared by a user. Queries should not include names of people, years and other irrelevant details. For example:

Input: That sounds relaxing, Jeremy! As for video game suggestions, have you ever tried "The Legend of Zelda: Breath of the Wild"? It's an open-world adventure game that I absolutely love. [shares a photo of Link standing in front of a breathtaking landscape] Have a look at this stunning view!
Output: the legend of zelda: breath of wild link landscape

Input: {generated_image_caption}
Output:
```
